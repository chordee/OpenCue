## 一、升級與回滾

### 0. 更新 stack 設定（yml）

正式環境的 Portainer 追蹤的是 `studio/release` 分支。
日常修改都 push 到 `studio/main`，**不會影響正式環境**。確認要上線時：

```bash
git checkout studio/release
git merge --ff-only studio/main
git push origin studio/release
```

Portainer 在下一次輪詢時（5～15 分鐘內）自動部署。只重建設定有變動的服務。

退回上一版的 stack 設定：

```bash
git checkout studio/release
git reset --hard <上一個 commit>
git push --force-with-lease origin studio/release
```

image 的版本不在 yml 裡，這個步驟**不會升級 image**，升級 image 見下面第 1～3 步。

### 1. 產生新版本的 image

1. 修改原始碼，或把上游 `master` 的新版本 merge 進部署分支，commit 並 push
2. GitHub → Actions → **Sandbox images** → Run workflow
   （或 `gh workflow run sandbox-images.yml --ref <分支>`）
3. 完成後的 Summary 會列出新 tag，格式是 `<版本>-<commit 短 SHA>`，例如 `1.34.5-abcd1234`

- 每個版本的 tag 都會保留在 GHCR，不會被新版覆蓋，所以隨時可以回滾
- `latest` 永遠指向最後一次 build，**正式環境不要用**
- **沒有新 commit 就重跑 workflow**，會產生相同的 tag 並覆蓋原本的 image。
  發新版一定要有新的 commit
- 發新版後，記得更新 `README.md` 與 `server/env.example` 裡寫死的 tag

依據：`notes/sandbox/22` 第八節。

### 2. 升級前：檢查 DB migration 並備份

**DB migration 只會往前。** 新版本若帶有新的 flyway migration，
升級後 DB schema 就改變了，退回舊版的 Cuebot 不一定能搭配新的 schema。

同步上游時，先看有沒有新增的 migration：

```bash
git diff <舊 commit> <新 commit> --stat -- cuebot/src/main/resources/conf/ddl/postgres/migrations/
```

有的話，**升級前一定要先備份 DB**（第二節）。

### 3. 升級

Portainer → Stacks → `opencue` → 環境變數，
把五個 `OPENCUE_*_IMAGE` 的 tag 改成新版 → **Update the stack**
（勾選 **Re-pull image**）。

Repository 模式的 stack 也一樣：**push 到 git 不會升級 image**，
tag 在 Portainer 的環境變數裡，要人工修改。這是刻意保留的人工確認步驟，
因為 image 升級可能帶有只能往前的 DB migration。

- 執行中的 frame **不會被中斷**。Cuebot 不保存狀態，重啟後節點會自動重新註冊，
  frame 繼續跑完並正常回報（已實測 150 秒的 frame 跨越升級）
- 下載新 image 期間舊容器照常運作，實際中斷只有最後替換容器的約 30 秒
- 只會下載有變動的 layer，比第一次部署快很多

依據：`notes/sandbox/14`。

### 4. 回滾

把 tag 改回舊版本 → Update the stack。已實測可以回到舊版。

**例外**：升級時跑過新的 DB migration 的話，回滾 Cuebot 前要先評估 schema 相容性，
必要時還原升級前的 DB 備份。

## 二、DB 備份與還原

DB 裡存的是 job 狀態與歷史，不是算圖成果。遺失一天的資料代表
「不知道昨天哪些 job 跑過」，而不是要重算，**每日備份一次通常就夠了**。

### 備份

```bash
docker exec opencue-db pg_dump -U cuebot -d cuebot -Fc -f /tmp/cuebot.dump
docker cp opencue-db:/tmp/cuebot.dump ./cuebot-$(date +%Y%m%d).dump
```

### 還原

```bash
docker cp ./cuebot-YYYYMMDD.dump opencue-db:/tmp/restore.dump
docker exec opencue-db pg_restore -U cuebot -d cuebot --clean --if-exists /tmp/restore.dump
```

**`--if-exists` 不能省略。** 只用 `--clean` 還原到空的 DB 時，
會因為刪除不存在的物件而出現數百個錯誤（實測 474 個）並回傳 exit 1。
資料其實有還原成功，但很容易被誤判為失敗。加上 `--if-exists` 後
不論是空的 DB 還是已有資料的 DB，都是 exit 0、零錯誤（實測）。

還原前先停止 Cuebot（Portainer 的 Containers 頁面 Stop `opencue-cuebot`），
還原完成再啟動，避免 Cuebot 在還原途中寫入資料。（這個順序未實測，是一般的做法。）

還原後確認：

```bash
docker exec opencue-db psql -U cuebot -d cuebot -c \
  "select (select count(*) from host) hosts, (select count(*) from show) shows,
          (select max(version::int) from flyway_schema_history) schema_version"
```

備份檔要存到**另一台機器**，放在同一台宿主上沒有意義。
排程需要宿主權限（cron），只有 Portainer 權限的話，要另外做一個排程容器。

依據：`notes/sandbox/11` 第 6 點、`16`。

## 三、DB 歷史表清理

完成超過 72 小時的 job 會被搬到歷史表（`job_history`、`layer_history`、`frame_history`），
**但歷史表沒有任何自動清除機制**，DB 會無限成長（速度不快）。

定期刪除舊的歷史資料：

```sql
-- 先確認影響範圍
SELECT count(*) FROM job_history
WHERE int_ts_stopped > 0
  AND int_ts_stopped < EXTRACT(EPOCH FROM NOW() - INTERVAL '90 days');

-- 確認無誤後刪除（layer_history、frame_history 會連動刪除）
DELETE FROM job_history
WHERE int_ts_stopped > 0
  AND int_ts_stopped < EXTRACT(EPOCH FROM NOW() - INTERVAL '90 days');
```

**`int_ts_stopped > 0` 這個條件絕對不能省略。** 尚未結束的 job 這個欄位是 0，
而 `0 < 任何過去的時間` 永遠成立，少了這個條件會把**正在執行的 job 的歷史**一起刪掉。

依據：`notes/sandbox/11` 第 6 點、`17` 場景 12。

## 四、frame log 保留期

frame log 由節點寫到共享儲存（`CUE_FRAME_LOG_DIR`），OpenCue 本身不會清理。
請 IT 在檔案伺服器端設定保留期（例如刪除 60 天前的檔案）。

容量估算：本機實測平均每個 frame log 約 6.6 KB，但實際大小取決於 DCC 的輸出量，
**這個數字不能直接外推**。上線第一個月請觀察實際成長。依據：`notes/sandbox/15`。

## 五、常用操作

### job

| 目的 | 指令 |
|---|---|
| 暫停 / 恢復 | `cueman -pause <job>` / `cueman -resume <job>` |
| 終止並從清單移除 | `cueman -force -term <job>` |
| 重試失敗的 frame | `cueman -force -retry <job>` |
| 只重試部分 frame | `cueman -force -retry <job> -range 10-20` |
| 放棄 frame（不再重試） | `cueman -force -eat <job>` |
| 砍執行中的 frame | `cueman -force -kill <job>` |
| 列出 frame 狀態 | `cueman -lf <job>` |

**清理 job 清單要用 `cueman -term`**，`cueadmin -kill` 只砍執行中的 frame，job 會留在清單上。

frame 失敗的狀態是 **DEAD**（不是 FAILED）。上游 frame 是 DEAD 時，
相依它的下游會一直停在 DEPEND，要先處理上游。依據：`notes/sandbox/20`。

### 節點

| 目的 | 指令 |
|---|---|
| 列出節點（含 allocation、狀態） | `cueadmin -lh` |
| 鎖定 / 解鎖 | `cueadmin -force -lock -host <名稱>` / `-unlock` |
| 移動 allocation | `cueadmin -force -move <alloc> -host <名稱>` |

**移除已下線的節點**：節點關機或移除後，約 5 分鐘會被標成 DOWN，
這時才能刪除紀錄。節點還在 UP 的時候沒辦法 lock，因為 lock 要由 Cuebot 回連節點。

```python
import opencue
opencue.api.findHost("RENDER01").delete()
```

**取消某台機器上正在跑的 frame**（例如 artist 上班需要用電腦）：

```python
import opencue
for proc in opencue.api.getProcs(host=["WS01"]):
    proc.kill()
```

frame 會回到佇列由其他節點從頭重跑，不算失敗。

### show

- 新增 show：加進 `OPENCUE_INIT_SHOWS` 後 Update the stack，`init` 會建立並訂閱 allocation
- **投過 job 的 show 無法刪除，只能停用**：

  ```python
  import opencue
  show = opencue.api.findShow("projA")
  for sub in show.getSubscriptions():
      sub.delete()
  show.setActive(False)
  ```

依據：`notes/sandbox/20`。

### service

- 新增：加進 `OPENCUE_INIT_SERVICES` 後 Update the stack
- **修改既有的 service**：在 CueGUI 或 CueWeb 的 Services 頁面修改。
  `init` 不會覆寫已存在的 service

## 六、自建 registry 的清理

只有使用 `server/registry.portainer.yml` 時才需要。每個版本約 6 GB。

刪除舊版本需要兩個前提，缺一就會回 404：

1. registry 啟動時就設定了 `REGISTRY_STORAGE_DELETE_ENABLED=true`（範本已設定）
2. 刪除 manifest 時 Accept header 要包含 `application/vnd.oci.image.index.v1+json`
   （buildx 推送的是 OCI 格式）

刪除 manifest 後還要執行 garbage-collect 才會真正釋放空間。
詳細步驟見 `notes/sandbox/14`。

## 七、出問題時

先看 `notes/sandbox/17-故障排查與常見疏失速查.md` 開頭的總表，依照現象對照原因。
最常見的三種「沒有錯誤訊息、job 就是不動」：

| 現象 | 原因 |
|---|---|
| frame 卡 WAITING | tag 不符、facility 不符、show 沒訂閱節點所在的 allocation |
| frame 卡 RUNNING、沒有 log | Cuebot 連不到節點的 8444（DNS 或防火牆） |
| 節點 LOCKED | CueNIMBY 排程鎖定中，或排程寫成跨午夜 |
