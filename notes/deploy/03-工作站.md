# 03 — artist 工作站（用戶端）

artist 工作站白天是用戶端，下班後兼任算圖節點。
這一篇只講**用戶端**的部分；算圖節點的部分照 [`02-算圖節點.md`](02-算圖節點.md) 做，
其中 `OVERRIDE_IS_DESKTOP = True`、`RQD_TAGS` 以 `desktop` 開頭、`NODE_ROLE=workstation`
（範本預設是專職算圖機，這三項要改）。

---

## 一、會用到的工具

| 工具 | 用途 |
|---|---|
| **CueGUI** | 桌面監控介面。內含 Cuetopia（看 job / frame）與 CueCommander（看節點） |
| **CueSubmit** | 桌面投遞介面 |
| **CueNIMBY** | 系統列小工具，依排程在上班時段把本機鎖住、不接工作 |
| `cueadmin` / `cueman` | 命令列管理工具（TD / 管理者用） |
| CueWeb | 網頁版，不需安裝，瀏覽器開 `http://<伺服器>:3000` |

只需要看進度的人，用 CueWeb 就夠了，可以不裝桌面工具。

**CueWeb 的「Autoload Mine」在不需要登入的版本中無效。** CueWeb 以登入帳號判斷「我的」job，
沒有登入時使用者一律是 `unknown`，自動載入找不到任何 job。
要看 job 時，在 Cuetopia 的搜尋框輸入 show 名稱或 job 名稱後按 **Load**
（依據：`cueweb/app/page.tsx` 的 `getServerSession`；實測）。

和算圖節點共用 `C:\opencue\venv`。在 repo 根目錄執行：

```bat
C:\opencue\venv\Scripts\python.exe -m pip install ./proto ./pycue ./pyoutline ./cueadmin ./cuegui ./cuesubmit ./cuenimby
```

會一併裝入 PySide6。依據：[`notes/sandbox/10`](../sandbox/10-Windows用戶端工具.md)。

## 三、【陷阱】設定檔分散在三個位置

| 元件 | 設定檔位置 | 範本 |
|---|---|---|
| CueGUI / CueSubmit / cueadmin（pycue） | `%APPDATA%\opencue\opencue.yaml` | [`client/opencue-client.yaml`](client/opencue-client.yaml) |
| CueNIMBY | `%USERPROFILE%\.config\opencue\cuenimby.json` | [`node/cuenimby-workstation.json`](node/cuenimby-workstation.json) |
| RQD | `C:\opencue\rqd.conf` | [`node/rqd-windows.conf`](node/rqd-windows.conf) |

CueNIMBY 用的是 Linux 慣例的 `~/.config`，沒有做平台判斷。

### CueNIMBY 的目錄要先建立

全新的 Windows 帳號沒有 `%USERPROFILE%\.config`，CueNIMBY 建立設定目錄時
沒有連同上層一起建立，**會直接啟動失敗**。部署時先建好：

```bat
mkdir "%USERPROFILE%\.config\opencue"
copy node\cuenimby-workstation.json "%USERPROFILE%\.config\opencue\cuenimby.json"
```

依據：[`notes/sandbox/05` 第 10 項](../sandbox/05-可回饋上游的問題.md#10-cuenimby-在全新的-windows-機器上會因建立設定目錄失敗而無法啟動)、[`10`](../sandbox/10-Windows用戶端工具.md)。

## 四、設定

### `opencue.yaml`

```yaml
cuebot.facility_default: local

cuebot.facility:
    local:
        - opencue-server.studio.local:8443
```

只要改伺服器位置。`facility_default` 要與節點的 `DEFAULT_FACILITY` 一致（都是 `local`）。

### `cuenimby.json`

要改的是 `cuebot_host` 與 `hostname`（本機的單段主機名稱，與 `rqd.conf` 的
`OVERRIDE_HOSTNAME` 相同）。

排程的寫法：

```json
"schedule": {
  "monday": { "start": "09:00", "end": "18:00", "state": "disabled" },
  ...
}
```

意思是「週一 09:00–18:00 鎖住本機，其他時間開放算圖」。

**一律寫成不跨午夜的「封鎖時段」。** 寫成 `18:00-09:00 available` 這種跨午夜的時段，
CueNIMBY 會完全算反，變成上班時間開放、下班時間鎖住。
依據：[`notes/sandbox/09` 坑 #11](../sandbox/09-NIMBY與混合機隊.md#坑-11跨午夜的排程時段完全失效)（原始碼 `cuenimby/scheduler.py:78-87`）。

沒有列出的日子（例如週末），排程**不做任何切換，維持前一個狀態**。
週五 18:00 後已切成開放，所以週末會保持開放；但若 CueNIMBY 是在週末才啟動，
就沿用節點當下的狀態。依據：`cuenimby/scheduler.py` 的 `_check_schedule()`。

### 上班時鎖定，不會中斷正在跑的 frame

09:00 CueNIMBY 鎖定工作站時，**已經在跑的 frame 會繼續跑到結束**，
只是不再派新的 frame 過來（已實測）。一個要跑好幾小時的 frame 會持續佔用 artist 的電腦。

目前的決定是**不自動中斷**，由 artist 或管理者視情況手動取消。做法（擇一）：

- CueGUI → CueCommander 找到這台主機 → 對正在跑的 frame 執行 Kill
- 以 Python 取消這台機器上所有正在跑的 frame：

  ```python
  import opencue
  for proc in opencue.api.getProcs(host=["WS01"]):
      proc.kill()
  ```

被取消的 frame 會**回到佇列，由其他節點從頭重跑**，不算失敗、不增加重試次數，
但已經跑的進度會作廢。

依據：[`notes/sandbox/24` 第一節](../sandbox/24-派工行為與監控.md#一工作站與專職機同時在線)。

## 六、從 Maya 直接投遞

### 做法

repo 裡的 Maya 外掛（`cuesubmit/plugins/maya/`）是把投遞介面跑在 **Maya 自己的 Python 裡**，
每個 Maya 版本都要各自安裝 opencue 套件（Maya 2027 是 Python 3.13，與 venv 的 3.11 不相容）。
多版本並存時不好維護，所以改用自己的兩段式工具（[`client/maya/`](client/maya/)）：

```
Maya（任何版本）                          C:\opencue\venv（只有一份）
opencue_maya_launcher.py        ──>      opencue_maya_submit.py
只用 maya.cmds 收集：                      CueSubmit 投遞介面，預先填好：
  場景、相機、frame 範圍、Maya 版本           場景、相機、frame 範圍
不需要安裝任何 opencue 套件                  指令  ocrun maya <版本> Render
                                          service  tags 含 maya_<版本> 的那一個
```

- 從哪個版本的 Maya 送出，就自動用那個版本的 Maya 與 service，artist 不會選錯
- **service 以版本 tag 反查**（`maya_<版本>`，例如 2027 → `maya2027`），不依賴 service 的命名。
  找不到時視窗標題會提示，要手動選
- 啟動後不等待，Maya 可以繼續操作

### 安裝

**算圖節點**：`dcc.toml` 裡要有該 Maya 版本，見 [`02` 第五節](02-算圖節點.md#五呼叫-dccocrun)。
投遞的指令是 `ocrun maya <版本> Render ...`，參數與 `Render.exe` 相同。

**伺服器**：每個 Maya 版本要有對應的 service，tags 包含 `maya_<版本>`，例如 `maya2027`（`OPENCUE_INIT_SERVICES`）。

**pipeline 工具區**（網路空間，只放一份）：

- 把 [`client/maya/`](client/maya/) 的兩個檔案放到 `P:\pipeline\opencue\client\maya\`（位置依工作室而定，路徑不能有空白）
- 之後更新工具只要改這裡，所有工作站立刻生效。Maya 的 job 算圖時只執行 `Render`，
  不會讀這裡的檔案，所以可以直接覆蓋（Houdini 不同，見第七節）

**工作站**：

1. 在 `Maya.env`（`%USERPROFILE%\Documents\maya\<版本>\Maya.env`）加上：

   ```
   PYTHONPATH=P:\pipeline\opencue\client\maya
   ```

   已經有 `PYTHONPATH` 的話，用 `;` 接在後面。工作室若已由 pipeline 統一管理 Maya 環境，
   加在那裡即可，不必逐台修改。
2. 建立 shelf 按鈕，類型選 Python，指令：

   ```python
   import opencue_maya_launcher; opencue_maya_launcher.submit()
   ```

預設的 show 取自環境變數 `PROJECT`（pipeline 通常已經設定）。

### 使用前提與注意事項

- **專案路徑不能有空白。** CueSubmit 把指令組成字串後用空白切開，加引號也無效
  （[`sandbox/17` 場景 24](../sandbox/17-故障排查與常見疏失速查.md#場景-24路徑含空白時-frame-失敗)）。本工作室由 pipeline 強制專案路徑不含空白
- **輸出位置由場景的 Maya project 決定。** 指令沒有指定輸出目錄，場景要放在有
  `workspace.mel` 的 project 裡，否則圖檔會寫到算圖節點本機的
  `Documents\maya\projects\default\images`（實測）
- **不要選 Cuebot 內建的 `maya` service**，它的 tag 是 `general | desktop`，版本綁定會失效。
  工具會預先選好對應版本的 service
- 工具只提供 Maya 這一種 job 類型
- **相機只能選一台**；沒有選時不指定相機，由 Maya 算場景中所有 renderable 的相機。
  場景只有一台 renderable 相機時會預先選好（上游 CueSubmit 在沒選相機時會送出 `-cam [None]`，
  工具已修正，見 [`sandbox/25` 第五節](../sandbox/25-Maya內投遞.md#五人工測試中發現的問題)）

### 驗證狀態

- 在 Maya 2027 環境下完整跑通：mayapy 裡沒有 opencue 套件，啟動器照常運作；
  投遞介面預先填入的 service、指令、frame 範圍正確；10 個 frame 全部算圖成功
- 改用 `ocrun` 後重新以程式送出，2 個 frame 全部成功（[`sandbox/26`](../sandbox/26-ocrun取代wrapper.md)）
- **在 Maya 介面中人工操作**：第一次發現 `-cam [None]` 的問題並修正；修正後重新送出，
  3 個 frame 全部成功（由 Script Editor 呼叫 `submit()`，與 shelf 按鈕執行的是同一段程式）
- 改用 `ocrun` 與 tag 反查 service 後，在 Maya 介面中重新投遞，指令與 service 正確。
  這次發現農場上的 Arnold 一直拿不到授權、卻顯示成功，已修正（[`02` 第五節](02-算圖節點.md#五呼叫-dccocrun)、[`sandbox/30`](../sandbox/30-Arnold授權與假成功.md)）
- 本機只有 Maya 2027。啟動器的寫法相容 Python 2.7，但**舊版 Maya 未實測**

依據：[`notes/sandbox/25`](../sandbox/25-Maya內投遞.md)。

## 七、從 Houdini 直接投遞

### 做法

與 Maya 相同的兩段式，另外加一支在算圖節點上執行的算圖腳本（[`client/houdini/`](client/houdini/)）：

| 檔案 | 在哪裡執行 | 內容 |
|---|---|---|
| `opencue_houdini_launcher.py` | Houdini 內，任何版本 | 只用 `hou` 收集 hip 檔、可算的節點與各自的 frame 範圍、Houdini 版本 |
| `opencue_houdini_submit.py` | `C:\opencue\venv` | CueSubmit 投遞介面，選節點、frame 範圍、是否整段一個 task |
| `opencue_houdini_render.py` | 算圖節點的 hython | 開啟 hip，算指定節點的這個 task 的 frame |

送出的指令：

```
ocrun houdini <版本> hython P:/pipeline/opencue/releases/<工具版本>/client/houdini/opencue_houdini_render.py <hip> <節點> #FRAMESPEC#
```

- **可選的節點**：所有 ROP（`hou.RopNode`：`/out` 底下、SOP 裡的 ROP Geometry、LOP 的 USD Render ROP 等），
  以及白名單中的非 ROP 節點：File Cache SOP（`filecache::2.0`）、Karma LOP（`karma`）。
  白名單在 `opencue_houdini_launcher.py` 的 `_OTHER_RENDER_TYPES`，新增類型前要先實測
- 選了節點就自動帶入該節點的 frame 範圍，layer 名稱改為節點名稱；打開工具時預先選好 Houdini 裡目前選取的節點
- **service**：以版本 tag `houdini_<版本>` 反查（例如 22.0.429 → `houdini2204`）。
  找不到時視窗標題會提示，要手動選
- 一次投一個節點。有相依時（例如先快取再算圖）分兩次投，或在 CueGUI 設定相依

### 模擬要整段一個 task

投遞介面有 **Whole range as one task (simulation)** 開關：

| 開關 | 行為 | 用在 |
|---|---|---|
| 關 | 每格一個 task，平行算 | 算圖、只是轉換格式的 File Cache / ROP Geometry |
| 開 | 整段 frame 在一個 task 內依序算（chunk = frame 數） | 模擬 |

節點開了 **Cache Simulation**（File Cache）或 **Initialize Simulation OPs**（ROP）時，預設打開。
**這只是預設值，不保證正確**：DOP、TOP 與第三方的快取節點都不會被認出來，
**投遞前由 artist 確認這個開關**。

模擬被拆開算時，結果仍然正確（solver 會從起始格重算），但第 N 格的 task 要重算 N 格，
總計算量約為 n²/2，而且每個 task 只寫出自己那一格（實測）。

### 安裝

**算圖節點**：`dcc.toml` 裡要有該 Houdini 版本，見 [`02` 第五節](02-算圖節點.md#五呼叫-dccocrun)。
算圖腳本放在網路空間，節點要看得到 `P:`。

**伺服器**：每個 Houdini 版本要有對應的 service，tags 包含 `houdini_<版本>`（`OPENCUE_INIT_SERVICES`）。

**pipeline 工具區**（網路空間）：

- 把 [`client/houdini/`](client/houdini/) 的三支 `.py` 放到**版本目錄**
  `P:\pipeline\opencue\releases\<工具版本>\client\houdini\`（例如 `2026.09.25`，路徑不能有空白）
- 算圖腳本的位置由投遞工具自己所在的目錄決定，所以 **job 會記住送出當下的版本目錄**。
  排隊中的 job 不會因為之後的更新而改用新版的算圖腳本
- **版本目錄發布後不再修改**。更新工具時建立新的版本目錄，再把 package 指向它，
  見 [`04` 的「pipeline 工具的發布」](04-維運.md#八pipeline-工具的發布)

**工作站**：

1. 把 Houdini package [`client/houdini/opencue.json`](client/houdini/opencue.json)（改成實際的版本目錄）放到
   工作室共用的 `HOUDINI_PACKAGE_DIR`（一份給所有機器與 Houdini 版本，切換版本只改這一處），
   或個別的 `%USERPROFILE%\Documents\houdini<版本>\packages\`。它把工具目錄加進 Houdini 的 `PYTHONPATH`
2. 建立 shelf tool，Script 分頁選 Python，內容：

   ```python
   import opencue_houdini_launcher; opencue_houdini_launcher.submit()
   ```

### 使用前提與注意事項

- **專案路徑不能有空白**，理由同 Maya
- hip 檔要先存檔；有未儲存的變更時會詢問是否存檔
- 輸出路徑、相機、算圖設定一律照 hip 內節點的設定

### 驗證狀態

- hython 下啟動器收集正確（File Cache 兩種、ROP Geometry、Karma LOP、Mantra ROP），模擬快取的預設判斷正確；
  帶有 execute / frame 範圍參數的一般節點、沒有 frame 範圍的 merge ROP 都會被排除
- 以程式操作投遞介面送出四種節點，全部成功；模擬快取 10 格在一個 task 內依序算完，逐格結果正確
- package 安裝方式已在 hython 確認可 import
- 在 Houdini 介面中人工投遞四種節點，全部成功。換節點時 layer 名稱會自動改成節點名稱
- 本機只有 Houdini 22.0.429

依據：[`notes/sandbox/27`](../sandbox/27-Houdini內投遞.md)。

## 八、從 Nuke 直接投遞

### 做法

與 Maya 相同的兩段式（[`client/nuke/`](client/nuke/)）：

| 檔案 | 在哪裡執行 | 內容 |
|---|---|---|
| `opencue_nuke_launcher.py` | Nuke 內，任何版本 | 只用 `nuke` 收集 script 路徑、啟用中的 Write 節點（包括 Group 內的）、frame 範圍、Nuke 版本 |
| `opencue_nuke_submit.py` | `C:\opencue\venv` | CueSubmit 投遞介面，選 Write 節點、frame 範圍、chunk |
| `menu.py` | Nuke 內 | 在選單列加上 OpenCue > Submit to OpenCue |

送出的指令：

```
ocrun nuke <版本> Nuke<主.次版本> -F #FRAMESPEC# [-X Write1,Write2] -x <script.nk>
```

- **不用 CueSubmit 內建的 Nuke 類型**：它在沒選 Write 節點時送出 `-X [All]`、選多個時送出 `-X a, b`，
  而且固定用 `-F #IFRAME#`，chunk 大於 1 時每個 task 只算第一格。改為借用 Shell 類型、自己組指令（與 Houdini 相同）
- Write 節點預設全選，全選時不帶 `-X`，Nuke 會算所有啟用中的 Write 節點
- **chunk 可以大於 1**：`#FRAMESPEC#` 會換成這個 task 的所有 frame（例如 `1-5x2`），Nuke 在一次啟動內算完，省下重複開啟 script 的時間
- **service** 以版本 tag `nuke_<版本>` 反查（例如 17.0v1 → `nuke17`）
- 不像 repo 的外掛，**啟動後不等待**，Nuke 可以繼續操作
- Nuke 算圖失敗時會正確回傳非 0（實測 Write 名稱不存在、輸出目錄不存在都是 exit 1），不需要 `ocrun` 另外檢查輸出

### 安裝

**算圖節點**：`dcc.toml` 裡要有該 Nuke 版本，見 [`02` 第五節](02-算圖節點.md#五呼叫-dccocrun)。

**伺服器**：每個 Nuke 版本要有對應的 service，tags 包含 `nuke_<版本>`（`OPENCUE_INIT_SERVICES`）。

**pipeline 工具區**：把 [`client/nuke/`](client/nuke/) 的三個檔案放到 `P:\pipeline\opencue\client\nuke\`。
Nuke 的 job 算圖時只讀 `.nk` 與 `ocrun`，不讀這裡的檔案，所以可以直接覆蓋更新（與 Maya 相同）。

**工作站**：把這個目錄加進 `NUKE_PATH`（環境變數，或工作室 `init.py` 裡的 `nuke.pluginAddPath()`）。
Nuke 啟動時會執行其中的 `menu.py`，選單列出現 **OpenCue > Submit to OpenCue**。

### 驗證狀態

- Nuke 的 terminal 模式下啟動器收集正確（兩個 Write，含 Group 內的 `Comp.WriteB`）
- 農場實測：`-F 1-5x2`（chunk 3）只算第 1、3、5 格；`-F 1-2`、`-F 3-4`（chunk 2）各算兩格；`-X` 以逗號指定多個 Write 可用
- 以程式操作投遞視窗送出「全部 Write」與「只選 WriteA」兩種，各 5 格全部成功
- **尚未在 Nuke 介面中人工操作**（選單、存檔詢問）；本機只有 Nuke 17.0v1

依據：[`notes/sandbox/31`](../sandbox/31-Nuke內投遞.md)。

## 九、投遞 job 時要注意的事

給寫投遞腳本或 pipeline 工具的 TD：

| 項目 | 做法 | 依據 |
|---|---|---|
| 指定 DCC 版本 | 用 **service**（例如 `houdini2204`），不要手寫 tag | [`sandbox/21`](../sandbox/21-Service與資源模型.md) |
| 指令 | 以**串列**傳入，不要傳字串，否則 Windows 路徑的反斜線會被吃掉 | [`sandbox/17` 場景 6](../sandbox/17-故障排查與常見疏失速查.md#場景-6dcc-算圖報找不到檔案反斜線路徑被吃掉) |
| 含空白的路徑 | 串列**不保護空白**，場景檔、輸出路徑等要**自己在前後加雙引號** | [`sandbox/17` 場景 24](../sandbox/17-故障排查與常見疏失速查.md#場景-24路徑含空白時-frame-失敗) |
| 呼叫 DCC | 一律透過 `ocrun <產品> <版本> <程式>`，不寫安裝路徑 | [`02` 第五節](02-算圖節點.md#五呼叫-dccocrun) |
| 作業系統 | 指定 `os="Windows"`，同時決定派工對象與 log 位置 | [`sandbox/17` 場景 21](../sandbox/17-故障排查與常見疏失速查.md#場景-21混合作業系統農場中job-成功但-log-找不到) |
| layer 名稱 | 至少 3 個字元 | [`sandbox/21`](../sandbox/21-Service與資源模型.md) |
| 場景檔 | 算圖時讀的是**場景檔當下的內容**，不是送出時的快照。排隊或算圖期間覆寫同一個檔案，之後的 frame 會算到新內容。要保留舊版就另存新檔再送 | 設計決定（見下方） |

範例腳本在 [`notes/sandbox/lab/submit_dcc.py`](../sandbox/lab/submit_dcc.py)、[`submit_houdini_twostage.py`](../sandbox/lab/submit_houdini_twostage.py)。

### 場景檔不做快照（設計決定）

投遞工具直接使用送出當下的場景檔，不複製一份給 job。這能應付大部分的情況，第一版維持如此。
日後若需要「送出時複製場景檔」，會做成**預設關閉**的選項。

### CueWeb 投遞的限制

CueWeb 可以投遞 job，但有三個限制：沒有 tag 欄位、沒有 OS 欄位、記憶體預設 256 MB。
正式投遞建議用桌面工具或腳本。依據：[`notes/sandbox/13`](../sandbox/13-CueWeb與RESTGateway.md)。
