# 01 — OpenCue 伺服器

Linux + Docker 主機，跑 Cuebot、PostgreSQL、REST Gateway、CueWeb。**不參與算圖。**

---

## 一、事前請 IT 準備

這些都在 Docker 之外，Portainer 做不到。

### 1. 對外開放的 port

| 來源 | 目的 | Port | 用途 | 必要性 |
|---|---|---|---|---|
| 算圖節點、artist 工作站 | 本機 | **8443** | RQD 註冊回報、CueGUI / CueSubmit 連線 | **必要** |
| 本機 | 算圖節點、artist 工作站 | **8444** | Cuebot 回連節點派發 frame | **必要**（節點端要開入站） |
| 瀏覽器 | 本機 | 3000 | CueWeb | 使用 CueWeb 時 |
| — | — | 5432、8448 | DB、REST Gateway | **不要開放**，只走容器內部網路 |

**8443 與 3000 都沒有身分驗證**：連得到 8443 就能用 `cueadmin` 操控整座農場，
連得到 3000 就能在 CueWeb 上 kill / retry job。兩者都**只能開放給內網**。

依據：[`notes/sandbox/11` 第 3 點](../sandbox/11-正式部署風險與待辦.md#3-網路通訊矩陣與防火牆)。

### 2. 共享儲存掛在宿主上

CueWeb 要讀得到 frame log 才能顯示。請 IT 把存放 frame log 的共享
（與節點寫入的是同一個）掛在宿主上，例如 `/mnt/opencue/logs`。

- 需要網頁縮圖預覽的話，算圖輸出也要掛，例如 `/mnt/projects/render`
- 不需要在 CueWeb 看 log 的話，這一項可以省略

依據：[`notes/sandbox/13`](../sandbox/13-CueWeb與RESTGateway.md)、[`16`](../sandbox/16-Portainer與SSH的分工.md)（也有不需宿主掛載的 CIFS volume 做法，但宿主仍要裝 `cifs-utils`）

### 3. DNS

Cuebot 會用節點的**短名稱**（例如 `RENDER01`）回連節點。
宿主本身能解析節點短名稱的話，容器會沿用宿主的設定，不需要額外處理。

請 IT 確認：

```bash
getent hosts RENDER01        # 在宿主上執行，要解析得到
```

依據：[`notes/sandbox/11` 第 1 點](../sandbox/11-正式部署風險與待辦.md#1-多節點的-dns-解析別用-extra_hosts)、[`22` 第六節](../sandbox/22-兩種部署路線.md#六主檔改了什麼讓它只填環境變數就能部署)。

### 4. Docker 的容器 log 輪替

Docker 預設的容器 log **沒有大小上限**。請 IT 在 `/etc/docker/daemon.json` 設定：

```json
{
  "log-driver": "json-file",
  "log-opts": { "max-size": "50m", "max-file": "5" }
}
```

依據：[`notes/sandbox/15` 第 6 點](../sandbox/15-空間規劃.md#6-docker-宿主容器-log-容易被忽略)。

### 5. 宿主要能連到 ghcr.io

使用 GHCR 上的現成 image 時才需要。公司防火牆或 proxy 可能會擋。
連不出去的話改用自建 registry（見第六節）。

## 三、路線 A：Portainer

### 1. 準備環境變數

複製 [`server/env.example`](server/env.example)，填入以下【必填】項：

| 變數 | 說明 |
|---|---|
| `POSTGRES_PASSWORD` | 資料庫密碼 |
| `JWT_SECRET` | CueWeb 呼叫 REST Gateway 用，隨機長字串 |
| `CUEWEB_NEXTAUTH_SECRET` | 隨機長字串 |
| `CUE_FRAME_LOG_DIR` | frame log 的共享位置，**必須是 UNC 正斜線**，例如 `//fileserver/opencue/logs` |
| 五個 `OPENCUE_*_IMAGE` | 預設已填好 GHCR 的 image，通常不用改 |

隨機字串可以這樣產生：

```bash
openssl rand -base64 32
```

其他常改的項目：

| 變數 | 說明 |
|---|---|
| `CUEWEB_PUBLIC_URL` | 使用者在瀏覽器輸入的網址 |
| `FRAME_LOG_MOUNT_SOURCE` | 宿主上 frame log 共享的掛載點（第一節第 2 項） |
| `FRAME_LOG_MOUNT_TARGET`、`CUEWEB_LOG_ROOTS` | **兩者都等於 `CUE_FRAME_LOG_DIR` 去掉開頭的一個斜線**，例如 `/fileserver/opencue/logs`。不一致時 CueWeb 顯示「Log file not found」 |
| `OPENCUE_INIT_SHOWS` / `OPENCUE_INIT_SERVICES` | 部署後自動建立的 show 與 service（見第四節） |

**`CUE_FRAME_LOG_DIR` 為什麼一定要 UNC 正斜線**：這個路徑由 Windows 節點寫入，
再由 Linux 容器裡的 CueWeb 讀取。磁碟機代號（`L:/...`）在 Linux 容器內不成立，
CueWeb 會回 400。`//server/share/...` 是兩邊都成立的唯一寫法。
依據：[`notes/sandbox/13`](../sandbox/13-CueWeb與RESTGateway.md)、[`11` 第 2 點](../sandbox/11-正式部署風險與待辦.md#2-網路磁碟機代號可用但有一個例外)。

### 2. 建立 stack

1. Portainer → **Stacks** → **Add stack**
2. Name：`opencue`（不能與現有的 stack 同名；重建時先刪除舊的 stack）
3. Build method 選 **Repository**（建議）：

   | 欄位 | 值 |
   |---|---|
   | Repository URL | `https://github.com/chordee/OpenCue` |
   | Repository reference | `refs/heads/studio/release`（**不是** `studio/main`，見下方說明） |
   | Compose path | `notes/deploy/server/opencue.portainer.yml`（從 repo 根目錄算起，照這個值輸入） |
   | Authentication | 關閉（公開 repo） |

   宿主連不到 GitHub 時，改選 **Web editor**，貼上 [`server/opencue.portainer.yml`](server/opencue.portainer.yml) 的內容。
4. Environment variables：**Load variables from .env file** 上傳填好的檔案，或逐項填入
5. Repository 模式下，**GitOps updates** 開啟，Mechanism 選 **Polling**，間隔 5～15 分鐘
6. **Deploy the stack**

Repository 模式的好處是 yml 有修改時會自動同步，不需要重新貼上。

**為什麼追蹤 `studio/release` 而不是 `studio/main`**：
`studio/main` 是日常工作的分支，筆記、測試腳本都會 push 到這裡。
若正式環境直接追蹤它，**任何一次 push 都會在幾分鐘內上線**，
包括不小心寫錯的 yml。`studio/release` 只在確認要更新正式環境時才推進，
更新的意圖明確，出問題時也能把它退回上一個 commit。操作方式見 [`04` 第一節](04-維運.md#一升級與回滾)。

依據：[`notes/sandbox/23`](../sandbox/23-Portainer的Git模式.md)。

【必填】項沒填的話，部署會直接失敗並指出缺哪一個：

```
required variable POSTGRES_PASSWORD is missing a value: 必須設定
```

### 3. Repository 模式的更新行為

| 情況 | 結果 |
|---|---|
| push 到 `studio/main` | **不會觸發部署** |
| 推進 `studio/release`，只改了文件 | 會觸發部署，但**只重跑 flyway 與 init**，服務不中斷 |
| 推進 `studio/release`，修改了 yml | **只重建設定有變動的服務**（實測只改 Cuebot 參數時，只有 Cuebot 重啟） |
| 在 Portainer 修改環境變數 | 不會自動套用，要按 **Pull and redeploy**，**所有容器重建** |
| 升級 image | **不會自動發生**。image 的 tag 在環境變數裡，要人工修改（見 [`04`](04-維運.md)） |
| 按下 **Pull and redeploy** | **所有容器強制重建**，會短暫中斷，不要隨手按 |

webhook 模式的網址**不需要認證**就能觸發，UUID 不要貼在公開的地方。

### 4. 第一次部署會比較久

五個 image 合計約 6 GB。本機實測從 GHCR 下載花了約 **34 分鐘**（視網路而定）。
Portainer 會一直等到下載完才回應，頁面會轉很久，這是正常的。

- 可以請 IT 事先在宿主上 `docker pull` 這五個 image
- 若 Portainer 前面有反向代理，可能會先逾時，但部署仍會在背景完成

依據：[`notes/sandbox/22` 第八節](../sandbox/22-兩種部署路線.md#八把-image-放到-ghcr取代自建-registry)。

## 四、初始化：show、subscription、service

stack 裡的 `init` 容器會在 Cuebot 啟動後自動執行，建立環境變數指定的項目。

```
OPENCUE_INIT_SHOWS=projA,projB
OPENCUE_INIT_SERVICES=[{"name":"houdini2204","tags":["houdini_22_0_429"],"min_memory_gb":4}]
```

- **可重複執行**：每次更新 stack 都會再跑，已存在的項目不會被修改
- **要修改既有的 service，請到 CueGUI / CueWeb 上改**，改環境變數沒有效果
- service 的 `tags` 要對應節點 `rqd.conf` 裡的 `RQD_TAGS`，而且**不要同時放 `general`**，
  否則版本綁定會失效（tag 比對是「或」）

### 【重要】新 show 必須訂閱節點所在的 allocation

show 沒有訂閱某個 allocation 的話，那個 allocation 裡的節點**永遠不會**接到
這個 show 的 job，而且**沒有任何錯誤訊息**。

`init` 預設會訂閱 `local.general`、`local.desktop`、`cloud.general` 三個。
artist 工作站通常在 `local.desktop`，不要漏掉。有自訂 allocation 時要加進
`OPENCUE_INIT_ALLOCS`。

依據：[`notes/sandbox/22` 第五節](../sandbox/22-兩種部署路線.md#五初始化容器-init)、[`17` 場景 22](../sandbox/17-故障排查與常見疏失速查.md#場景-22新建的-show-投遞的-job-永遠停在-waiting)。

### show 建立後就刪不掉

只要投過 job，show 就無法刪除，只能停用。**命名前先想清楚**，不要拿正式環境測試。
依據：[`notes/sandbox/20`](../sandbox/20-相依性與維運操作.md)。

## 五、路線 B：docker compose

需要 SSH 與執行 `docker` 的權限。

```bash
git clone https://github.com/chordee/OpenCue
cd OpenCue/notes/deploy/server
cp env.example .env              # 填寫方式同第三節
```

直接使用 GHCR 的 image：

```bash
docker compose --env-file .env -f opencue.portainer.yml up -d
```

在宿主上從原始碼 build（`.env` 裡的 image 名稱可自訂，例如 `opencue/cuebot:local`）：

```bash
docker compose --env-file .env -f opencue.portainer.yml -f build.yml up -d --build
```

在宿主上 build 的代價：

- build cache 約 **50 GB**，cuebot 編譯約 10 分鐘，期間 CPU 滿載（依據：[`notes/sandbox/15`](../sandbox/15-空間規劃.md)、[`22` 第七節](../sandbox/22-兩種部署路線.md#七路線-b-實測)）
- 要能連到 Maven、npm、PyPI
- 用指令建立的 stack，Portainer 只能有限度地管理

### 站點專屬設定

宿主解析不到節點短名稱時，複製 `site.example.yml` 修改後多疊一層：

```bash
cp site.example.yml site.yml
docker compose --env-file .env -f opencue.portainer.yml -f site.yml up -d
```

路線 A 沒辦法疊加檔案，需要時把 `site.yml` 的內容合併進 Web editor。

## 六、自建 registry（不使用 GHCR 時）

宿主連不到 ghcr.io，或需要自己修改的 image 時使用。

1. 部署 [`server/registry.portainer.yml`](server/registry.portainer.yml)（獨立的 stack）
2. 在開發機 build 並推送：

   ```bash
   cd notes/deploy/server
   docker compose --env-file .env -f opencue.portainer.yml -f build.yml build
   docker compose --env-file .env -f opencue.portainer.yml -f build.yml \
     push flyway cuebot rest-gateway cueweb init
   ```

   `push` 要列出服務名稱，否則連 `postgres:15.1` 也會嘗試推送。

3. `env.example` 的五個 image 改成 registry 上的位置

**正式環境的 registry 需要 TLS 與認證**（尚未實測）。
沒有 TLS 的話，每台要拉 image 的主機都得設定 `insecure-registries`，
那需要修改 daemon.json 並重啟 Docker。

依據：[`notes/sandbox/14`](../sandbox/14-Registry流程.md)。

## 七、部署後驗證

```bash
# 1. 容器狀態：flyway 與 init 是 Exited (0)，其他是 healthy
#    第一次部署時，flyway 的 log 最後有 3 行 duplicate key ... "c_task_lock_pk"，
#    是上游的 seed 與 migration 重複插入同樣的資料，不影響運作
docker ps -a --filter name=opencue-

# 2. init 做了什麼
docker logs opencue-init

# 3. CueWeb
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3000     # 200

# 4. 節點上線後：Cuebot 容器內能解析節點名稱，並連得到 8444
docker exec opencue-cuebot getent hosts RENDER01
docker exec opencue-cuebot bash -c 'timeout 3 bash -c "</dev/tcp/RENDER01/8444" && echo OK || echo FAIL'
```

只有 Portainer 權限時，1、2 在 Portainer 的 Containers 頁面看狀態與 Logs；
4 用容器的 **Console** 執行。

**第 4 項沒通過的症狀是「frame 永遠卡在 RUNNING、沒有 log」**，
而 host 列表看起來完全正常，非常難排查。節點上線後務必檢查。

## 八、監控（選用）

[`server/monitoring.portainer.yml`](server/monitoring.portainer.yml) 是獨立的 stack：Prometheus + Grafana + PostgreSQL exporter。
設定檔寫在 yml 內（inline configs），Portainer 可直接部署，不需要掛載檔案。

1. opencue stack 先部署完成（監控 stack 會加入它的 `opencue` network）
2. 新增 stack，貼上 `monitoring.portainer.yml`，環境變數：

   | 變數 | 說明 |
   |---|---|
   | `POSTGRES_PASSWORD` | 與 opencue stack 相同 |
   | `GRAFANA_ADMIN_PASSWORD` | Grafana 的 admin 密碼 |

3. 瀏覽 `http://<伺服器>:3001`，Dashboards → Import，上傳
   `sandbox/config/grafana/dashboards/PostgreSQL.json`

- 資源用量：三個容器合計約 130 MB 記憶體，image 約 1.5 GB
- Prometheus 刻意不對外開放（沒有認證），只有 Grafana 的 3001 需要開放給內網
- **上游的 `cuebot.json` 儀表板已經過時**（2021 年，9 個指標已不存在），匯入後大部分是空白的。
  要監控 Cuebot 需要自己做儀表板。可用的指標見 [`notes/sandbox/24` 第四節](../sandbox/24-派工行為與監控.md#四監控prometheus--grafana)
- 排程佇列的指標要在 opencue stack 設定 `CUEBOT_METRICS_COLLECTOR=true`（修改後要 Pull and redeploy）

依據：[`notes/sandbox/24`](../sandbox/24-派工行為與監控.md)。

## 九、Docker 以外的長期維運

這些需要宿主權限，或另外容器化的排程方案。項目與做法見 [`04-維運.md`](04-維運.md)：

| 工作 | 沒做的後果 |
|---|---|
| DB 備份（`pg_dump`） | 宿主故障即失去全農場的 job 狀態與歷史 |
| DB 歷史表清理 | DB 無限成長（沒有自動清除機制） |
| frame log 保留期清理 | 共享儲存被塞爆 |
| registry garbage-collect | 自建 registry 才需要 |
