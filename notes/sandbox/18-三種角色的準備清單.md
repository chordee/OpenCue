# 18 — 三種角色的準備清單

> **本篇已由 `notes/deploy/` 取代**，正式部署請以那邊為準。
> 保留本篇作為整理當時的紀錄。

前面的筆記是**依測試時序**寫的，同一台機器要準備什麼會散在好幾份裡。
這一份改用**機器角色**的維度重新展開，當作實際部署時的檢查清單。

## 先釐清有幾種機器

| 角色 | 作業系統 | 說明 |
|---|---|---|
| **OpenCue Server** | Linux + Docker | 跑 Cuebot / DB / CueWeb。**不參與算圖** |
| **Artist Workstation** | Windows | artist 日常工作的機器。**下班後兼任 render node** |
| **Render Host** | Windows | 專職算圖機，無人使用 |

**注意第二種是雙重身分** —— 它同時要裝「用戶端工具」與「算圖節點」兩套東西，
是三者中準備工作最多的。

---

# 一、OpenCue Server（Linux + Docker）

OpenCue Server 主要由 Docker 容器封裝應用層，架構相對單純，但**宿主作業系統層仍有幾項基礎設施必須配置**。

## 1. 基礎軟體

```
Docker Engine + Docker Compose
Portainer（若採用）
```

## 2. 對外開放的 port

| Port | 方向 | 用途 | 必要性 |
|---|---|---|---|
| **8443** | 入站 | Windows 節點的 RQD 註冊與回報、artist 用戶端連線 | **必要** |
| 3000 | 入站 | CueWeb 網頁介面 | 若啟用 |
| 5432 | — | **不要開放**，DB 只走容器內部網路 | — |
| 8448 | — | **不要開放**，REST Gateway 只給 CueWeb 用 | — |

## 3. 【關鍵】容器內要解析得到 render node 的短名稱

Cuebot 會把節點回報的名稱**截成第一段短名稱**，再用它回連節點的 8444。
所以那個短名稱必須在 **Cuebot 容器內**解析得到 ——
容器不一定繼承宿主的 DNS search domain。

部署後務必驗證：

```bash
docker exec opencue-cuebot getent hosts RENDER01
docker exec opencue-cuebot bash -c 'timeout 3 bash -c "</dev/tcp/RENDER01/8444" && echo 通 || echo 不通'
```

解不到的話，用 [`notes/deploy/server/site.example.yml`](../deploy/server/site.example.yml) 加上 `dns` / `dns_search` 指向公司 DNS
（見 [`11` 第 1 點](11-正式部署風險與待辦.md#1-多節點的-dns-解析別用-extra_hosts)、[`22` 第六節](22-兩種部署路線.md#六主檔改了什麼讓它只填環境變數就能部署)）。**不要用 extra_hosts 逐台硬寫，那無法規模化。**

這一項沒做好的症狀是「frame 永遠卡在 RUNNING、沒有 log」，
而 host 列表看起來完全正常，**極難排查**。

## 4. 共享儲存（只有 CueWeb 需要）

CueWeb 要讀 frame log 才顯示得出來，所以要把共享儲存掛給它。
兩種做法：

- 宿主上 mount，再 bind mount 進容器
- 用 Docker 的 local volume driver + `type: cifs`（不需宿主 mount，
  但**宿主核心仍須支援 CIFS**，見 [`16`](16-Portainer與SSH的分工.md)）

**若不打算用 CueWeb 的 log 檢視，這一項可以不做。**

## 5. 維運排程（不可省略）

這些 Portainer 做不到，需要宿主權限或容器化的排程方案（見 [`16`](16-Portainer與SSH的分工.md)）：

| 工作 | 沒做的後果 |
|---|---|
| PostgreSQL 歷史表清理 | **DB 無限成長**（歷史表沒有自動清除機制） |
| `pg_dump` 備份 | 宿主故障即全農場狀態盡失 |
| frame log 保留期清理 | 共享儲存被塞爆 |
| registry garbage-collect | registry 磁碟被塞爆 |

## 6. 其他

- `daemon.json`：設定 container log 輪替（預設**無上限**）
- systemd：Docker 開機自啟
- registry：**必須有 TLS 憑證**，否則要設 `insecure-registries`
  而那需要改 daemon.json 並重啟 daemon

**詳見**：[`07`](07-Portainer部署實錄.md)（Portainer 部署）、[`11`](11-正式部署風險與待辦.md)（風險與待辦）、[`14`](14-Registry流程.md)（Registry）、
[`15`](15-空間規劃.md)（空間）、[`16`](16-Portainer與SSH的分工.md)（權限分工）

# 二、Artist Workstation（Windows）

**雙重身分**：白天是 artist 的工作機，下班後是 render node。
所以下面的準備工作是「用戶端」＋「算圖節點」兩套。

## 1. Python 環境

本次實測使用 **Python 3.11.9**（Windows 原生，**不是 WSL**）。

```
python -m venv C:\opencue\venv
```

## 2. 套件安裝

```bash
# 用戶端工具
pip install ./proto ./pycue ./pyoutline ./cueadmin ./cuegui ./cuesubmit ./cuenimby

# 算圖節點（兼任 render node 才需要）
pip install ./rqd
pip install wmi pywin32          # 【必要】rqd 沒有宣告這兩個 Windows 相依
cd rqd/winps && pip install .    # 【必要】否則不回報記憶體用量，需要 MSVC
```

裝完會有（實測）：

```
opencue_cuegui / cuenimby / cuesubmit / proto / pycue / pyoutline / rqd
PySide6 6.5.3 + pywin32 + WMI + winps
```

**兩個容易漏掉的**：

- `wmi` / `pywin32` —— 不裝的話 RQD **啟動即崩潰**
- `winps` —— 不裝的話 RQD 能跑，但**記憶體用量永遠回報 0**，而且沒有警告。
  它是 C++ 擴充，需要 MSVC 編譯器

## 3. 【陷阱】三個元件的設定檔在三個不同位置

這是 Windows 上特別容易漏的地方：

| 元件 | 設定檔位置 |
|---|---|
| pycue / cuegui / cuesubmit / cueadmin | `%APPDATA%\opencue\opencue.yaml` |
| CueNIMBY | `%USERPROFILE%\.config\opencue\cuenimby.json` |
| RQD | `%LOCALAPPDATA%\OpenCue\rqd.conf`（或用 `RQD_CONFIG_FILE` 指定） |

CueNIMBY 用的是 Linux 慣例的 `~/.config`，**沒有做平台判斷**。
而且全新的 Windows 機器上 `~/.config` 不存在，
CueNIMBY 會因為 `mkdir` 沒帶 `parents=True` 而**啟動失敗**（見 [`05` 第 10 項](05-可回饋上游的問題.md#10-cuenimby-在全新的-windows-機器上會因建立設定目錄失敗而無法啟動)）——
部署腳本要先把那個目錄建好。

範本：[`notes/deploy/client/opencue-client.yaml`](../deploy/client/opencue-client.yaml)、[`notes/deploy/node/cuenimby-workstation.json`](../deploy/node/cuenimby-workstation.json)、
[`notes/deploy/node/rqd-windows.conf`](../deploy/node/rqd-windows.conf)

## 4. 目錄結構

```
C:\opencue\
    venv\            Python 環境
    bin\             DCC 包裝腳本（每個版本一個 .bat）
    scripts\         算圖腳本
    tmp\             RQD 的 TEMP/TMP、Nuke disk cache
    logs\            （若 frame log 寫本機；正式環境應寫共享儲存）
```

## 5. DCC 軟體與包裝腳本

每個要用的 DCC 版本，在 `C:\opencue\bin\` 放一支包裝腳本：

```
hython-22.0.429.bat
maya-render-2027.bat
nuke-17.0v1.bat
```

**所有節點的檔名必須一致，內容各自指向本機的安裝位置。**
這樣 job 指令就不需要知道每台機器把 DCC 裝在哪。

**三個硬性要求：**

1. **必須是純 ASCII** —— cmd.exe 用 OEM 代碼頁解析 .bat，
   UTF-8 中文註解會變亂碼並破壞語法（見 [`09` 坑 #13](09-NIMBY與混合機隊.md#坑-13bat-檔必須是純-ascii)）
2. **授權伺服器要寫進去** —— RQD 不繼承使用者環境
   （`ADSKFLEX_LICENSE_FILE` / `foundry_LICENSE` / `solidangle_LICENSE`）
3. **找不到執行檔要明確回傳錯誤碼**，不要靜默失敗

## 6. RQD 設定（`rqd.conf`）

```ini
[Override]
OVERRIDE_CUEBOT      = <Linux 主機名稱或 IP>
OVERRIDE_HOSTNAME    = <本機的單段主機名稱>
RQD_BECOME_JOB_USER  = False
RQD_USE_IP_AS_HOSTNAME = 0
OVERRIDE_IS_DESKTOP  = True
OVERRIDE_NIMBY       = False          # 改用 CueNIMBY 排程，見下
RQD_TMPDIR           = C:\opencue\tmp
RQD_TAGS             = general houdini22 houdini_22_0_429 maya2027 nuke17
```

**`RQD_TAGS` 要列出本機實際裝了哪些 DCC 版本** ——
Cuebot 靠它決定能不能把工作派過來。

**`OVERRIDE_HOSTNAME` 必須是單段名稱**（不要 FQDN），
因為 Cuebot 會截成第一段，而那個名稱要在 Cuebot 容器內解析得到。

## 7. 啟動方式：**必須是登入時觸發，不能用 Windows 服務**

NIMBY 與 CueNIMBY 都需要跑在**使用者 session**。
Windows 服務跑在 session 0，看不到使用者的鍵鼠活動，NIMBY 會完全失效。

啟動腳本 `C:\opencue\bin\rqd-start.bat` 要做三件事：

1. **固定工作目錄** —— 否則 Linux 風格路徑會被解析到不同磁碟機
2. **重設 PATH 與 TEMP/TMP** —— 不要繼承啟動者的環境
3. **先起 RQD，等它註冊完成，再起 CueNIMBY** ——
   順序顛倒會得到 `failed to lock host`

## 8. CueNIMBY 排程

```json
"schedule": {
  "monday": { "start": "09:00", "end": "18:00", "state": "disabled" },
  ...
}
```

**務必寫成不跨午夜的封鎖時段。** 跨午夜（如 `18:00-09:00 available`）
會完全失效且方向相反，見 [`09` 坑 #11](09-NIMBY與混合機隊.md#坑-11跨午夜的排程時段完全失效)。

## 9. 防火牆與網路

| 項目 | 設定 |
|---|---|
| 出站 8443 | 連到 OpenCue Server |
| **入站 8444** | **必要** —— Cuebot 要回連本機派發 frame |
| 網路磁碟機 | 全公司代號一致 |

**入站 8444 最容易漏**，漏掉的症狀就是「frame 卡 RUNNING 無 log」。

## 10. 防毒 / EDR

若啟用 RQD 內建 NIMBY（`OVERRIDE_NIMBY = True`），
它會用 `pynput` 掛**全域鍵鼠 hook**，企業防護軟體常判定為 Keylogger 並攔截。

**採用 CueNIMBY 時段排程並關閉 RQD NIMBY 就不會有這個問題** ——
這是選擇 CueNIMBY 的另一個理由（見 [`11` 第 5 點](11-正式部署風險與待辦.md#5-防毒--edr-可能把-nimby-當成側錄木馬)）。

## 11. DCC 內嵌的投遞外掛（選配）

repo 內有現成的：

```
cuesubmit/plugins/maya/   （CueMayaSubmit.py + userSetup.py）
cuesubmit/plugins/nuke/   （CueNukeSubmit.py + menu.py）
```

**只有 Maya 與 Nuke，沒有 Blender。** 本次未安裝測試。

**詳見**：[`08`](08-Windows節點實錄.md)（RQD 安裝）、[`09`](09-NIMBY與混合機隊.md)（NIMBY）、[`10`](10-Windows用戶端工具.md)（用戶端工具）、[`12`](12-真實DCC算圖.md)（DCC 包裝）

# 三、Render Host（Windows，專職算圖）

大致與工作站相同，但**少裝用戶端、啟動方式相反**。

## 與工作站的差異

| 項目 | 工作站 | 專職算圖機 |
|---|---|---|
| 用戶端工具（cuegui/cuesubmit） | 要裝 | **不需要** |
| CueNIMBY | 要裝 | **不需要** |
| `OVERRIDE_IS_DESKTOP` | `True` | **`False`** |
| `OVERRIDE_NIMBY` | `False`（改用排程） | `False` |
| 啟動方式 | 登入時觸發 | **Windows 服務** |
| Allocation | `local.desktop` | `local.general` |
| `OVERRIDE_CORES` | 可保留幾核給 artist | 全開 |

## 只需要安裝

```bash
pip install ./proto ./rqd
pip install wmi pywin32
cd rqd/winps && pip install .
```

## 【待驗證】服務模式能不能看到網路磁碟機代號

這是部署專職算圖機前**必須先確認**的事，本次因無管理員權限無法實測。

Windows 的磁碟機代號**繫結於登入工作階段**。服務跑在 session 0，
使用者對應的磁碟機在那裡不存在。

**驗證方式**：在該機器上以服務帳號執行一個寫入 `H:\...` 的測試工作。

若不通，對策是：

- 服務啟動時以服務帳號執行 `net use` 建立對應
- 或用 GPO 為該帳號建立持續性對應
- 或該節點的路徑改用 UNC（但專案檔內部的路徑改不了）

## 啟動：Windows 服務

專職機器沒有 NIMBY 的 session 限制，可以正大光明用服務，
**開機自啟的問題自然解決**。

需要管理員權限建立服務。包裝腳本裡的 `NODE_ROLE` 設成 `render`
就不會啟動 CueNIMBY。

**詳見**：[`08`](08-Windows節點實錄.md)、[`09`](09-NIMBY與混合機隊.md)（兩種機器的設定對照表）

# 四、共通的前置作業（三者都需要確認）

| 項目 | 說明 |
|---|---|
| **網路磁碟機代號一致** | 全公司同一代號指向同一共享 |
| **DNS 能解析節點短名稱** | 而且要在 **Cuebot 容器內**解析得到 |
| **共享儲存的容量與保留策略** | frame log 與算圖輸出，見 [`15`](15-空間規劃.md) |
| **`CUE_FRAME_LOG_DIR` 用 UNC 正斜線** | 這是唯一在 Windows 與 Linux 容器兩端都成立的寫法 |
| **時間同步** | 排程、log 時間戳、frame 統計都依賴它 |

# 五、部署順序建議

```
1. OpenCue Server
   └─ Docker + stack 部署 + 確認 8443 可連
        │
2. 一台 Render Host（先做一台驗證）
   ├─ Python + RQD + winps
   ├─ 包裝腳本 + rqd.conf + RQD_TAGS
   ├─ 【驗證】cueadmin -lh 看得到這台
   ├─ 【驗證】Cuebot 容器內能解析並連通本機 8444
   └─ 【驗證】投一個真實算圖 job 並成功
        │
3. 其餘 Render Host
   └─ 複製上一台的設定，只改 OVERRIDE_HOSTNAME 與包裝腳本的路徑
        │
4. Artist Workstation
   ├─ 用戶端工具 + opencue.yaml
   ├─ 【驗證】cuegui 看得到農場
   ├─ 【驗證】從 cuesubmit 投得出 job
   └─ 再加上 RQD + CueNIMBY（兼任 render node）
        │
5. 維運排程
   └─ DB 清理、備份、log 保留期
```

**第 2 步只做一台就好。** 那一台把所有坑踩完、驗證通過，
剩下的才批次部署 —— 否則同一個問題會在二十台機器上重演。
