# 02 — 目標架構（依 IT 描述整理）

## 已確認的條件

1. 目標是**一台 Linux 主機裝 Docker**。
2. 那台主機上**會掛很多其他服務**，希望用 Docker 各自隔離 → OpenCue 只是租戶之一。
3. 那台主機**不參與算圖**。
4. 實際算圖的衛星電腦**多半是 Windows**。
5. 存取方式：應該能 SSH 進去，但**要準備好只有 Portainer 的情況**（IT 不一定放行）。

## 由此推導的架構

```
┌─────────────────────────────────────────┐
│ Linux 主機（Docker，多服務共用）          │
│                                          │
│  OpenCue stack                           │
│   ├── postgres      (internal only)      │
│   ├── flyway        (跑完即退)            │
│   ├── cuebot        (對外 8443/gRPC)     │
│   ├── rest-gateway  (選配)               │
│   └── cueweb        (選配，對外 3000)     │
│                                          │
│  其他服務 stack…                          │
└──────────────┬───────────────────────────┘
               │ gRPC 8443
     ┌─────────┴─────────┬─────────────┐
     │                   │             │
┌────▼─────┐      ┌──────▼────┐  ┌─────▼────┐
│ Windows  │      │ Windows   │  │ Windows  │
│ RQD 8444 │      │ RQD 8444  │  │ RQD 8444 │
│ (+NIMBY) │      │ (+NIMBY)  │  │ (+NIMBY) │
└──────────┘      └───────────┘  └──────────┘
```

**關鍵差異：`rqd` 不放進 Docker stack。** 官方 compose 對 rqd 那段的註解本身就寫了
「In a production environment, this should be disabled from the stack and only run
on render hosts」。我們的情況更明確 —— 宿主不算圖，所以 stack 裡直接不要有 rqd。

這個「Cuebot 在 Docker、RQD 在原生主機」的組合，repo 裡有現成文件可以照著演練：
`sandbox/Running_Hybrid_RQD_setup_using_sandbox.md`（對應
`docs/_docs/developer-guide/hybrid-rqd-setup.md`）。

## OpenCue 元件分工與服務角色速查

OpenCue 的生態系由「用戶端工具」、「排程中樞」、「算圖節點」與「監控介面」四層組成：

| 元件名稱 | 運作位置 | 角色職責與分工 | 通訊埠 / 協定 |
|---|---|---|---|
| **pyoutline** | 用戶端 (Python) | 算圖工作定義框架。把工作拆成 Layer、設定 Frame 範圍、相依性與執行指令，並產出 Session 定義檔。 | 本地 API |
| **CueSubmit** | 藝術家工作站 | 桌面 GUI 提交工具（或 DCC 內嵌外掛）。讓藝術家挑選場景、設定格數、指定 Layer Tag 並投遞給 Cuebot。 | 8443 / gRPC |
| **CueAdmin** | 管理員終端 | 命令列管理工具。管理 Show、Allocation、Subscription、Host 狀態、移轉節點、手動解鎖或終止工作。 | 8443 / gRPC |
| **CueGUI** | 藝術家 / TD 桌面 | 桌面版綜合監控 UI（含 Cuetopia 監控 Job/Frame、CueCommander 監控節點負載）。 | 8443 / gRPC |
| **CueNIMBY** | 藝術家工作站 | 系統列小工具。依**排程**（如上班時段鎖定）或使用者**手動切換**，通知 Cuebot 暫停派工給本機。**不偵測鍵鼠** —— 鍵鼠偵測是 RQD 內建 NIMBY （`rqd/rqd/rqnimby.py`，用 pynput）的職責，兩者獨立，見 `09`。 | 8443 / gRPC |
| **Cuebot** | 伺服器容器 | **農場排程大腦（無狀態）**。管理狀態機、計算優先級與配額、把 Frame 派發給合適的 RQD 節點。 | 8443 (入站) / gRPC |
| **PostgreSQL** | 伺服器容器 | **全農場唯一真實來源（有狀態）**。儲存所有的 Job、Frame、Host、Tag、Allocation 與歷史紀錄。 | 5432 (內部) / TCP |
| **Flyway** | 伺服器容器 | **資料庫遷移工具（One-shot）**。開機時執行 SQL DDL 建立或升級 Schema，完成後立即退出。 | 5432 (內部) / TCP |
| **RQD** | 算圖節點 (Windows/Linux) | **節點執行守護行程**。向 Cuebot 註冊本機硬體規格與 Tag，監聽派工指令，啟動子行程算圖並寫入日誌。 | 8444 (入站) / gRPC |
| **REST Gateway** | 伺服器容器 | **gRPC 轉 HTTP/JSON 橋接器**。負責將 Cuebot 的 gRPC 介面包裝成 REST API，提供 JWT 身分驗證。 | 8448 (內部) / HTTP |
| **CueWeb** | 伺服器容器 | **網頁版管理介面 (Next.js)**。提供瀏覽器端的作業監控、日誌下載、Frame 狀態查詢與簡易管理。 | 3000 (對外) / HTTP |

## 一顆 Frame 的端到端生命週期（淺白流程拆解）

以下描述從藝術家送出算圖，到成品落地的 7 個關鍵步驟：

```
[藝術家 / DCC]
      │ 1. 提交 (CueSubmit / pyoutline)
      ▼
   [Cuebot] ── 2. 寫入狀態 ──> [PostgreSQL] (狀態: PENDING / WAITING)
      │
      │ 3. 排程派工 (Dispatching: 媒合 Tag, Alloc, 記憶體)
      ▼ (主動連線節點 8444)
 [Windows RQD] (狀態: RUNNING)
      │
      ├─ 4. 啟動子行程算圖 (包裝腳本 .bat ➔ hython / Render / Nuke)
      ├─ 5. 寫入 Frame 日誌 (寫入 CUE_FRAME_LOG_DIR //fileserver/.../xxx.rqlog)
      ├─ 6. 輸出影像成品 (寫入專案共享磁碟 H:\... 或 UNC)
      │
      ▼ 7. 回報結果 (ReportStatus: Exit code 0=SUCCEEDED, 非0=DEAD)
   [Cuebot] ── 更新狀態 ──> [PostgreSQL]
      │
      ▼ 8. 狀態更新與呈現 (CueGUI 綠燈 / CueWeb 讀取 Log 與預覽)
```

1. **工作打包與提交 (Submit)**：
   - 藝術家在 Maya / Houdini 或獨立的 `cuesubmit` 介面設定範圍（如 1-100 格）、指定算圖標籤（如 `general`, `houdini22`）。
   - `pyoutline` 將任務結構序列化，透過 gRPC (8443) 送達 **Cuebot**。
2. **登記排隊 (Enqueue)**：
   - Cuebot 接收任務，在 **PostgreSQL** 建立 Job 與 Layer 記錄，每個格數展開為一個 Frame 實體，初始狀態為 `WAITING`。
3. **媒合派工 (Dispatch)**：
   - Cuebot 內部的排程迴圈（Dispatcher）持續掃描待算 Frame 與可用 Host。
   - 檢查三大條件：**主機未被鎖定（Unlocked）**、**記憶體與核心數充裕**、**Host Tags 包含 Layer 所需的全部 Tags**。
   - 媒合成功後，Cuebot 主動對該 Windows 節點的 RQD (8444) 發起 `RunFrame` gRPC 呼叫。
4. **節點執行 (Execution)**：
   - Windows 節點上的 RQD 接收到任務，建立暫存環境變數（`CUE_IFRAME`、`TEMP` 等）。
   - 呼叫預先部署的包裝腳本（如 `hython-22.0.429.bat`），由其定位本機 DCC 執行檔啟動算圖。
5. **日誌與資源監控 (Logging & Profiling)**：
   - RQD 攔截 DCC 的 stdout/stderr，串流寫入 UNC 路徑的 `.rqlog` 檔案。
   - 後台線程透過 `winps` 定期採樣 DCC 行程樹的記憶體使用量（RSS）。
6. **完成回報 (Reporting)**：
   - DCC 算圖結束，子行程回傳 Exit Code。
   - RQD 向 Cuebot 發送 Frame 結束回報。Exit code 0 標記為 `SUCCEEDED`；非 0 標記為 `DEAD` 並依設定重試或停滯。
     （OpenCue 的 frame 狀態名稱是 `DEAD`，**沒有 `FAILED` 這個狀態**，寫 SQL 查詢時要注意。）
7. **監控可視化 (Visualization)**：
   - Cuebot 更新資料庫。藝術家的 **CueGUI** 介面立刻亮綠燈。
   - 主管或藝術家若開啟 **CueWeb** 網頁，Next.js 伺服器端自 REST Gateway 取得狀態，並直接自唯讀掛載的共享儲存讀取 `.rqlog` 呈現在網頁上。

## 必須注意的點

### 1. RQD 的 port 是全域設定，不是每台各自設

引 hybrid 文件原文：

> **CueBot connects to ALL RQD instances using a single configured port (default: 8444).**

意思是所有 render node 都必須在**同一個 port** 上聽。因為我們的 stack 裡不會有
Docker RQD，就沒有 8444 的 port 衝突問題，反而單純。

### 2. Windows RQD 的設定差異

`sandbox/rqd_windows.conf` 是現成範本，幾個關鍵項：

| 設定 | 值 | 原因 |
|---|---|---|
| `RQD_BECOME_JOB_USER` | `False` | Windows 上不做 job user 切換 |
| `RQD_USE_PATH_ENV_VAR` | `1` | 靠 PATH 找算圖程式 |
| `OVERRIDE_IS_DESKTOP` | `True` | 標記為工作站而非專職 render node |
| `OVERRIDE_NIMBY` | `True` | 有人在用電腦時不搶資源 |
| `MINIMUM_IDLE` | `900` | 閒置 15 分鐘才開始算 |
| `RQD_TMPDIR` | `C:\tmp\rqd` | Windows 路徑 |

**NIMBY 對「衛星算圖電腦是 artist 工作站」這個情境是核心功能** —— 有人在操作時
RQD 會自動退讓。另有 `cuenimby` 提供系統列小工具讓使用者自己控制。

### 3. 路徑對齊：這次的情況反而單純

先前擔心的「Linux/Windows 路徑不相容」，在這個架構下要分兩層看：

- **Cuebot 不解讀路徑**，它只是把 frame 的執行指令字串轉交給 RQD。
  所以 Cuebot 在 Linux、RQD 在 Windows，本身不衝突。
- 真正要對齊的是「**投 job 的機器**」與「**執行 frame 的 RQD**」。
  如果 artist 都是從 Windows 投、也都在 Windows 上算，兩邊路徑天然一致
  （磁碟機代號已同步，且實測可用；僅 frame log 需要 UNC，見 `11` 第 2 點），反而比混合環境好處理。

### 4. 待驗證：frame log 目錄

compose 目前設 `CUE_FRAME_LOG_DIR=/tmp/rqd/logs`（Linux 路徑），但實際寫 log 的是
**Windows 上的 RQD**，寫不進 Linux 路徑。

這項**必須實測確認**：這個值是否會被下發給 RQD、Windows RQD 如何解讀、
是否需要改成 UNC 路徑。**先不要假設，實際投一個 job 看 log 落在哪。**（後續已實測，見 `08`）

### 5. 多服務共存的隔離要求

因為宿主上還有別的服務：

| 項目 | 做法 |
|---|---|
| Stack 名稱 | 固定 project name（如 `opencue`），避免容器名撞到其他 stack |
| PostgreSQL 5432 | **不要 publish 到宿主**，宿主很可能已經有別的 postgres 佔用；OpenCue 自己的 db 留在內部網路即可 |
| Cuebot 8443 | 必須 publish，Windows RQD 要連 |
| RQD 8444 | stack 裡沒有 rqd，不需要 |
| CueWeb 3000 | 若啟用，建議掛反向代理而非直接對外 |
| 網路 | 明確命名自己的 network，不要用 default |
| 資源 | 加上 CPU/記憶體限制，避免吃掉其他服務的資源 |
| 重啟 | `restart: unless-stopped`，配合宿主的 Docker 開機自啟 |

## 兩種部署路徑

### A. 有 SSH（理想）

直接 `git clone` + `docker compose up -d`，跟本次測試流程一致。
image 可以現場 build，也可以拉 registry。

### B. 只有 Portainer（要先備好）

限制與對策：

| 限制 | 對策 |
|---|---|
| compose 裡的 `build:` 難處理 | 預先把 cuebot / flyway image 建好推到 registry，compose 只留 `image:` |
| flyway image 內含 migration SQL（build 進去的） | 同上，必須預先建好推 registry |
| `${HOME}` 等 shell 變數不存在 | 全部改成 Portainer stack 的環境變數 |
| 宿主檔案系統不好放檔案 | 需要的 bind mount 改 named volume |

**本機已有 Portainer CE（`portainer-ce:lts`，9443）在跑，這條路可以直接實測，
不要用推測的。**
