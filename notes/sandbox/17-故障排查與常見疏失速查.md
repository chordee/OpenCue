# 17 — 故障排查與常見疏失速查手冊

實作人員在安裝、部署或營運 OpenCue 時，最常面臨的挑戰是：**「畫面卡住了 / 噴出某行錯，我到底該去改哪一個檔案、哪一條設定？」**

本篇以**「眼前看到的現象或報錯關鍵字」**為索引，將本專案在實測中踩過、驗證過的 15 個坑點全面具體化，直接對準可能發生疏失的設定位置與排查指令。

## 各場景詳細排查與處置手冊

### 場景 1：Job 卡在 PENDING、Frame 全卡 WAITING，Host 顯示 UP / OPEN

- **現場畫面**：`cueadmin -lh` 顯示 Windows 節點狀態健康（`UP`、`OPEN`），Job 已經進入佇列，但所有 Frame 動也不動。
- **對準疏失點**：
  1. 檢查 [`notes/deploy/node/rqd-windows.conf`](../deploy/node/rqd-windows.conf) 的 `RQD_TAGS` 是否漏掉了 `general`。
  2. 若主機被移入自訂 Allocation（如 `local.desktop`），主機標籤被重置，預設 pyoutline 派發的任務要求 `general | util` 標籤，兩者對不上。
- **排查驗證**：
  進入 DB 容器查詢兩者的 Tag：
  ```bash
  docker exec -it opencue-db psql -U cuebot -c "
  SELECT str_name, str_tags FROM layer WHERE str_state='PENDING';
  SELECT h.str_name, ht.str_tag FROM host h JOIN host_tag ht ON h.pk_host=ht.pk_host;"
  ```
- **解法**：在 Windows 節點的 `rqd.conf` 加上 `RQD_TAGS = general`，重啟 RQD。

---

### 場景 2：Host 狀態顯示 LOCKED，Job 派不上去

- **現場畫面**：`cueadmin -lh` 顯示節點狀態為 `LOCKED`，即使沒有人在操作電腦也一樣。
- **對準疏失點**：
  1. 檢查當前時間是否落在 `cuenimby.json` 設定的上班封鎖時段（如週一至週五 09:00-18:00）。
  2. 檢查 `cuenimby.json` 是否設定了跨午夜時段（如 `18:00-09:00 available` 或 `22:00-06:00 disabled`）—— 此設定觸發上游邏輯 Bug，會導致整天判定反轉！
- **排查驗證**：
  查看本機 CueNIMBY 日誌：
  ```powershell
  Get-Content C:\opencue\cuenimby.log -Tail 20
  ```
- **解法**：
  1. 測試期間手動解鎖：
     ```bash
     cueadmin -force -unlock -host <節點名稱>
     ```
  2. 正式排程必須改寫為不跨午夜的封鎖時段（如 `09:00-18:00 disabled`）。

---

### 場景 3：Frame 卡在 RUNNING 數十分鐘，無 Log、無子行程

- **現場畫面**：CueGUI 上看見 Frame 變成黃色 `RUNNING`，但看算圖機的工作管理員毫無 DCC 行程，Log 目錄也完全沒有產生 `.rqlog`。
- **對準疏失點**：
  1. **單向通訊中斷**：RQD 能連上 Cuebot（8443），但 Cuebot 要派工回連 RQD（8444）時失敗。
  2. Windows 工作站本機防火牆阻擋了 8444 入站。
  3. Cuebot 把主機名稱截成第一段短名稱，但 Cuebot 容器內的 DNS 解析不到該短名稱。
- **排查驗證**：
  在 Linux 宿主檢視 Cuebot 日誌：
  ```bash
  docker logs opencue-cuebot | grep "RqdClientException"
  ```
  若出現 `failed to obtain status for frame`，在 Cuebot 容器內測試網路：
  ```bash
  docker exec opencue-cuebot getent hosts <Windows節點短名稱>
  docker exec opencue-cuebot bash -c 'timeout 3 bash -c "</dev/tcp/<Windows節點短名稱>/8444" && echo OK || echo FAIL'
  ```
- **解法**：
  1. Windows 防火牆放行 TCP 8444 Inbound。
  2. 在 `opencue.portainer.yml` 加入 `dns` 與 `dns_search`，或配置 `extra_hosts`。

### 場景 4：Frame 啟動瞬間崩潰，回報 Exit Status 299

- **現場畫面**：Job 剛被派發就立刻轉為紅色，退出碼顯示 `299`。
- **先理解 299 的意義**：`299` 定義在
  `cuebot/src/main/java/com/imageworks/spcue/dispatcher/Dispatcher.java:68`，
  名稱是 `EXIT_STATUS_FRAME_CLEARED` —— 意思是「**這個 frame 被 Cuebot 清掉了**」，
  **它是一個通用代碼，本身不指向任何特定原因**。
  真正的原因一定要去 Cuebot 的 log 裡找，不能只看 299 就下結論。
- **對準疏失點**：Linux 容器版 RQD 特有問題。投遞者的 Linux UID（通常為第一個桌面使用者的 1000）與 RQD 容器內既有的 `rqd` 系統帳號 UID 1000 衝突，RQD 內部無條件執行 `useradd` 失敗。
- **排查驗證**：
  檢視 Cuebot 日誌：
  ```bash
  docker logs opencue-cuebot | grep ABORTED
  # 輸出：ABORTED: Not launching, user xxx(1000:0) could not be created.
  ```
- **解法**：在 `docker-compose.override.yml` 或 RQD entrypoint 先行用不衝突的 UID（如 2000）建立同名使用者：
  ```yaml
  entrypoint:
    - /bin/sh
    - -c
    - 'id -u <使用者名> >/dev/null 2>&1 || useradd --uid 2000 --gid 1000 -M <使用者名>; exec /app/openrqd'
  ```

### 場景 5：Windows RQD 啟動時直接崩潰 ModuleNotFoundError: 'wmi'

- **現場畫面**：在 Windows 執行 `rqd.exe` 時立刻跳出錯誤終止：
  `ModuleNotFoundError: No module named 'wmi'`。
- **對準疏失點**：OpenCue 上游 `rqd/pyproject.toml` 遺漏宣告 Windows 專用的條件相依套件。
- **解法**：手動在 Windows venv 補齊套件：
  ```cmd
  <venv>\Scripts\pip.exe install wmi pywin32
  ```

### 場景 6：DCC 算圖報找不到檔案，反斜線路徑被吃掉

- **現場畫面**：Houdini 或 Maya 報錯找不到場景檔，Frame Log 印出的指令把 `\\server\share\file.ma` 顯示為 `serversharefile.ma`。
- **對準疏失點**：投遞 Job 的 Python 腳本（`submit.py`）傳遞了「字串」格式的指令，觸發了 pyoutline 底層的 POSIX `shlex.split()` 解析，將反斜線當成跳脫字元刪除。
- **解法**：投遞腳本的 `Shell(command=...)` 參數，**一律嚴格傳入串列（List）**，例如：
  ```python
  # 正確
  command = ["ocrun", "maya", "2027", "Render", "-rd", outdir, r"\\server\share\file.ma"]
  # 錯誤
  command = f"ocrun maya 2027 Render -rd {outdir} \\\\server\\share\\file.ma"
  ```
- **注意**：串列只保護反斜線，**不保護空白**。路徑含空白時還要自己加引號，見[場景 24](#場景-24路徑含空白時-frame-失敗)。

### 場景 7：Nuke 算圖全面失敗，報 Unable to create disk cache

- **現場畫面**：Nuke 在本機手動執行包裝腳本正常，但經由 OpenCue 農場派發時每個 Frame 都以 Exit 1 失敗，Log 顯示：
  `ERROR: Unable to create disk cache at C:/temp/nuke`。
- **對準疏失點**：RQD 傳給子行程的環境變數裡有 `TMP` 但**漏傳了 `TEMP`**。Nuke 在 Windows 找不到 `TEMP` 時，會自動退回嘗試存取寫死的 `C:/temp`，而節點上根本沒有該目錄。
- **解法**：透過 `ocrun` 執行 Nuke。`ocrun` 會以 `TMP` 補上 `TEMP`，並把 `NUKE_DISK_CACHE`
  設為 `TEMP` 底下的 `nuke`（不存在就建立），見 [`26`](26-ocrun取代wrapper.md)。
  自己寫的腳本若不透過 `ocrun`，要自行設定這兩個變數。

### 場景 8：Windows 包裝腳本報 'tlocal' is not recognized 或語法錯誤

- **現場畫面**：啟動 RQD 或執行算圖包裝腳本時，控制台噴出：
  `'tlocal' is not recognized as an internal or external command`，或 `if (...)` 括號配對錯誤。
- **對準疏失點**：包裝腳本（`.bat`）存成了 UTF-8 編碼且含有中文註解。Windows `cmd.exe` 預設使用繁體中文 OEM 代碼頁（CP950）解析，將 UTF-8 中文字節誤判為控制字元，破壞了語法。
- **解法**：所有部署在 Windows 節點上的 `.bat` 檔案必須是 **純 ASCII 編碼**。所有中文說明請寫在外部 Markdown 筆記中。

### 場景 9：CueWeb 檢視 Frame Log 報 HTTP 400: Query parameter 'path' is required

- **現場畫面**：在 CueWeb 點擊檢視某個 Frame 的 Log，瀏覽器跳出 HTTP 400 錯誤。
- **對準疏失點**：Cuebot 的 `CUE_FRAME_LOG_DIR` 被設定成了 Windows 磁碟機代號路徑（例如 `C:/opencue/logs` 或 `L:/logs`）。CueWeb 執行於 Linux 容器中，其後端 API 呼叫 `path.isAbsolute()`，判斷非 `/` 開頭的路徑為無效路徑並直接拒絕。
- **解法**：將 `CUE_FRAME_LOG_DIR` 統一設定為 **UNC 正斜線格式**：
  ```
  CUE_FRAME_LOG_DIR=//fileserver/opencue/logs
  ```
  `//` 開頭在 Linux 為合法絕對路徑（自根目錄解析），在 Windows 亦為合法 UNC 路徑，可達成跨平台路徑無損互通。

### 場景 10：CueWeb 讀取 Log 報 HTTP 403: Path is outside the allowed log roots

- **現場畫面**：CueWeb 點擊 Log 報錯 HTTP 403 Forbidden。
- **對準疏失點**：
  1. 白名單環境變數混淆：Log 讀取路由受 `CUEWEB_LOG_ROOTS` 控制，而非 `CUEWEB_PREVIEW_ROOTS`（後者是圖片縮圖白名單）。
  2. 容器內未正確掛載共享 Log 目錄。
- **解法**：
  在 `opencue.portainer.yml` 的 `cueweb` 服務確認配置：
  ```yaml
  environment:
    CUEWEB_LOG_ROOTS: /mnt/logs
    CUEWEB_PREVIEW_ROOTS: /mnt/render
  volumes:
    - ${FRAME_LOG_MOUNT_SOURCE}:/mnt/logs:ro
    - ${RENDER_OUT_MOUNT_SOURCE}:/mnt/render:ro
  ```

### 場景 11：CueNIMBY 啟動報 RqdClientException: failed to lock host

- **現場畫面**：開機登入或執行啟動腳本時，CueNIMBY 崩潰並丟出 `failed to lock host` 錯誤。
- **對準疏失點**：啟動順序錯誤。「鎖定主機」操作本質上是 Cuebot 接收請求後**回呼該節點的 RQD 8444**。若腳本先啟動 CueNIMBY、或在 RQD 尚未啟動完成前呼叫鎖定，回呼必定連線失敗。
- **解法**：啟動腳本中必須**先啟動 RQD**，並插入等待延遲（使用不畏重導向的 `ping -n 21 127.0.0.1 > nul`），確保 RQD 註冊完成後才啟動 CueNIMBY。

### 場景 12：資料庫手動清理時，活躍或進行中的任務歷史遭誤刪

- **現場畫面**：執行 SQL 清理超過 90 天的歷史紀錄後，發現當天正在執行中的 Job 也消失了，相關外鍵連動資料全被 CASCADE 抹除。
- **對準疏失點**：`job_history` 表中，尚未結束的 Job 其結束時間戳 `int_ts_stopped` 的**預設值為 0**。若 SQL 僅寫 `WHERE int_ts_stopped < (90天前)`，因為 `0 < 過去的任意時間戳` 恆成立，所有活躍中工作將全數遭到誤刪。
- **解法**：清理 SQL 必須嚴格加入防護條件：
  ```sql
  DELETE FROM job_history 
  WHERE int_ts_stopped > 0 
    AND int_ts_stopped < EXTRACT(EPOCH FROM NOW() - INTERVAL '90 days');
  ```

### 場景 13：算圖指令行為怪異，Windows 內建指令被別的程式取代

- **現場畫面**：Frame Log 裡出現明明是 Windows 指令、卻回報 Linux 風格錯誤的情形。例如：

  ```
  D:\dev\OpenCue>cmd /c timeout /t 3 /nobreak
  timeout: invalid time interval '/t'
  ```

  Windows 內建的 `timeout.exe` 不會說「invalid time interval」，
  那是 **GNU coreutils 版本的 `timeout`** 才有的訊息。

- **為什麼會這樣**：RQD 會把自己行程的 `PATH` 原封不動傳給每一個 frame。
  如果 RQD 是從某個開發者的 shell 啟動的（例如 Git Bash），
  那個 shell 的 `PATH` 前面會插入 `C:\Program Files\Git\usr\bin`，
  裡面有一整套 Unix 工具，**同名的會蓋掉 Windows 內建指令**。

  於是 frame 執行 `timeout` 時，找到的是 Git 帶來的 Unix 版，參數格式完全不同。

- **為什麼容易被誤判**：檢查「系統的環境變數設定」會顯示一切正常，
  因為污染不在系統設定裡，而在**啟動 RQD 的那個行程**裡。
  本專案就踩過這個陷阱 —— 先前確認「持久 PATH 是乾淨的」而誤以為問題已解決，
  實際上執行中的 RQD 仍帶著污染。

- **正確的檢查方式**：不要看系統設定，去看 frame log 裡實際的 `env PATH=` 那一行。

  ```bash
  grep "^env  *PATH=" <某個 frame 的 .rqlog>
  ```

  正常應該只有 Windows 的系統路徑：

  ```
  PATH=C:\WINDOWS\system32;C:\WINDOWS;C:\WINDOWS\System32\Wbem;...
  ```

- **解法**：不要繼承，在啟動腳本裡直接指定（[`notes/deploy/node/rqd-start.bat`](../deploy/node/rqd-start.bat) 已包含）：

  ```bat
  set PATH=%SystemRoot%\system32;%SystemRoot%;%SystemRoot%\System32\Wbem
  set PATH=%PATH%;%SystemRoot%\System32\WindowsPowerShell\v1.0
  ```

  正式環境用排程工作或服務啟動 RQD 時，環境本來就是乾淨的，
  但**加上這兩行可以保證每台節點行為一致**，不受啟動方式影響。

### 場景 14：Frame Log 檔案憑空消失，或跑到別的磁碟機

- **現場畫面**：Job 跑完了、狀態也正常，但去 `CUE_FRAME_LOG_DIR` 指定的位置找，
  卻是空的。CueWeb 點開 log 也顯示不出來。

- **為什麼會這樣**：如果 `CUE_FRAME_LOG_DIR` 沿用 sandbox 的預設值
  `/tmp/rqd/logs`（Linux 風格路徑），Windows 上的 Python 會把它解讀成
  **「相對於當前磁碟機的絕對路徑」**。

  也就是說，RQD 從哪個磁碟機啟動，log 就寫到那個磁碟機：

  | RQD 的工作目錄 | log 實際落點 |
  |---|---|
  | `D:\dev\OpenCue` | `D:\tmp\rqd\logs\...` |
  | `C:\opencue` | `C:\tmp\rqd\logs\...` |

  **整個過程不會有任何錯誤訊息**，檔案確實寫出去了，只是落在意料之外的位置。

- **怎麼確認**：全碟搜尋一次就知道：

  ```bash
  # Git Bash
  find /c /d -name "*.rqlog" -newermt "-1 hour" 2>/dev/null
  ```

- **解法**：`CUE_FRAME_LOG_DIR` 不要留 Linux 預設值，
  填成 render node 平台看得懂的路徑。多台節點時用 UNC 正斜線：

  ```
  CUE_FRAME_LOG_DIR=//fileserver/opencue/logs
  ```

  為什麼是 UNC 正斜線而不是磁碟機代號，見 [`13`](13-CueWeb與RESTGateway.md) ——
  簡單說是因為 CueWeb 跑在 Linux 容器裡，也要讀這個路徑。

### 場景 15：部署時 docker pull 失敗，說 repository 不存在或要登入

- **現場畫面**：

  ```
  docker pull opencue/cueweb:latest
  Error response from daemon: pull access denied for opencue/cueweb,
  repository does not exist or may require 'docker login'
  ```

- **最容易誤判的地方**：這個訊息看起來像「帳號沒權限」或「要先 docker login」，
  很多人會去研究帳號設定。**但真正的原因是那個 image 根本不存在。**

- **事實**：OpenCue 官方只發布了兩個 image：

  | Image | Docker Hub |
  |---|---|
  | `opencue/cuebot` | 有（但最新 tag 只到 `1.19.1`，遠落後於原始碼的 `1.34.4`） |
  | `opencue/rqd` | 有 |
  | `opencue/cueweb` | **沒有** |
  | `opencue/rest-gateway` | **沒有** |

  而官方 `docker-compose.yml` 裡卻寫著 `image: opencue/cueweb:latest`，
  所以照著文件做一定會失敗。

- **怎麼快速確認某個 image 到底存不存在**：

  ```bash
  curl -s -o /dev/null -w "%{http_code}\n" \
    https://hub.docker.com/v2/repositories/opencue/cueweb/
  # 404 = 不存在   200 = 存在
  ```

- **解法**：自行建置並推到內部 registry，流程見 [`14`](14-Registry流程.md)。
  這不是「比較好的做法」，而是**唯一的做法**。

### 場景 16：Portainer 部署後，容器裡的掛載目錄是空的

- **現場畫面**：stack 部署成功、容器也 healthy，
  但進去看掛載點卻是空目錄：

  ```bash
  docker exec opencue-cueweb ls /mnt/logs
  # (什麼都沒有)
  ```

  於是 CueWeb 讀不到 log。

- **為什麼會這樣（僅限 Docker Desktop 測試環境）**：
  從 WSL 執行 `docker compose` 時，Docker Desktop 會**自動轉換路徑**，
  把 `/mnt/c/...` 翻譯成 Windows 的實際位置。

  但 **Portainer 是直接對 daemon 下指令，沒有這層轉換**。
  寫成 `/mnt/c/opencue/logs` 時，daemon 就真的去找它自己檔案系統裡的
  `/mnt/c/opencue/logs` —— 那個路徑不存在，於是 Docker 建一個空目錄掛上去。

- **解法**：用 daemon 看得到的路徑。Docker Desktop 把 Windows 磁碟掛在：

  ```
  /run/desktop/mnt/host/c/opencue/logs
  ```

- **正式環境不會遇到這個問題**：真正的 Linux 宿主沒有這層轉換，
  直接填實際掛載點即可，例如 `/mnt/opencue/logs`。

  記在這裡是因為**測試階段一定會踩到**，而且症狀（空目錄、不報錯）
  很容易被誤認為是權限或掛載失敗。

### 場景 17：CueWeb 的縮圖預覽打不開 EXR（這不是故障）

- **現場畫面**：Houdini / Karma 算出來的 `.exr` 在 CueWeb 上點預覽沒有反應，
  但 Maya / Nuke 的 `.png` 就正常顯示。

- **原因**：CueWeb 的預覽功能只服務**瀏覽器原生看得懂的格式**：
  `png`、`jpeg`、`webp`、`bmp`、`avif`。

  （`svg` 刻意被排除，因為同源提供 SVG 等於允許執行腳本，是安全考量。）

  **EXR 不在清單內**，瀏覽器本來就不支援，這是設計如此，不是壞掉。

- **實務上怎麼辦**：如果希望在網頁上看到算圖預覽，
  需要在算圖流程裡**額外產生一張代理圖（proxy / thumbnail）**，
  例如算完 EXR 後順手轉一張小尺寸 PNG 放在同目錄。

  這會增加儲存用量，規劃時要算進去（見 [`15`](15-空間規劃.md)）。

### 場景 18：Frame 的記憶體用量顯示 0（這不是故障）

- **現場畫面**：CueGUI 的 `MaxRss` 欄位、或資料庫的 `int_mem_max_used`
  顯示為 `0`，但那個 frame 明明跑了算圖軟體，不可能不吃記憶體。

- **原因**：RQD 是**每 10 秒採樣一次**正在執行的 frame
  （`rqd/rqd/rqconstants.py:55`，`RSS_UPDATE_INTERVAL = 10`）。

  一個 frame 有沒有數據，取決於**它的執行區間有沒有跨過採樣時點**，
  而不是單純的「跑得久不久」。跑 7 秒的 frame 可能剛好落在兩次採樣之間，
  什麼都沒被記錄到。

- **實測對照**（前兩列是**同一支腳本、同樣用 hython、執行時間相近**）：

  | Frame | 執行情況 | 記憶體 |
  |---|---|---|
  | `drivetest`（失敗那次） | 失敗後重試，實際跑兩輪，跨過採樣點 | **461,956 KB** |
  | `drivetest`（成功那次） | 只跑一輪約 7 秒 | **0** |
  | `nuke_render` | 每格約 2 秒 | **0** |
  | `maya_render` | 每格約 18 秒 | 530,644 KB |
  | `houdini_render` | 每格約 6 秒但連續 4 格 | 1,145,644 KB |

- **兩個常見的誤判**：

  1. **以為 winps 沒裝好**（Windows 節點需要這個 C++ 擴充才會回報記憶體，
     見 [`08`](08-Windows節點實錄.md)）。要驗證它是否生效，請用**確定會跨過採樣點**的 frame ——
     跑超過 10 秒，或連續算多格。

  2. **拿這些統計做容量規劃**。短 frame 的數據不可信，
     若要用歷史數據決定 job 的記憶體需求，
     **必須排除回報 0 的 frame**，否則會嚴重低估。

- **不需要修**：這是採樣機制的先天特性，不是設定錯誤。
  只要知道怎麼解讀就好。

### 場景 19：Job 被派到沒有該 DCC 版本的節點

- **現場畫面**：明明在 layer tags 指定了 `houdini_22_0_429`，
  job 卻跑到只裝了 Houdini 21 的節點上，然後包裝腳本回報
  `hython not found`（exit 127）。

- **根因**：**Cuebot 的 tag 比對是正規表示式，而且是「或」不是「且」。**

  `cuebot/src/main/java/com/imageworks/spcue/dao/postgres/DispatchQuery.java:296`

  ```sql
  AND host.str_tags ~* ('(?x)' || layer.str_tags || '\y')
  ```

  layer 的多個 tag 會以 ` | ` 串接後**直接當成 regex pattern**，
  而 `|` 在 regex 裡就是「或」。

  所以 `tags=["general", "houdini_22_0_429"]` 的實際意思是
  **「有 general 或 有 houdini_22_0_429 都可以」** ——
  任何在派工池裡的節點都符合，版本綁定形同虛設。

- **解法**：**要綁版本就只放版本 tag。**

  ```python
  tags=["houdini_22_0_429"]              # 正確
  tags=["general", "houdini_22_0_429"]   # 錯誤，等於沒綁
  ```

  反過來說，若要**允許多個版本擇一**，正好可以利用這個特性：

  ```python
  tags=["houdini_22_0_429", "houdini_22_0_368"]   # 兩個版本都可以
  ```

- **命名上的注意事項**：
  - tag 會被當成 regex，**不要用 `.` `*` `+` `(` 等字元**，只用英數與底線
  - 部分查詢沒有加單字邊界 `\y`，理論上可能**子字串誤配**
    （`houdini2` 配到 `houdini22`）。避免讓某個 tag 成為另一個的前綴

### 場景 20：新節點加入後永遠收不到工作

- **現場畫面**：新節點已經註冊，`cueadmin -lh` 顯示 `UP` / `OPEN`，
  tag 也確認無誤，但 frame 就是停在 `WAITING`，**沒有任何錯誤訊息**。

- **這個症狀與「tag 不匹配」完全相同**，所以很容易只查 tag 而漏掉真正的原因。

- **根因**：**job 綁定 facility，跨 facility 不會派工。**

  兩種 RQD 的預設 facility **都是 `cloud`**：

  | 實作 | 位置 |
  |---|---|
  | Rust RQD | `rust/crates/rqd/src/config/mod.rs:162` |
  | Python RQD | `rqd/rqd/rqconstants.py:44` |

  而用戶端投出來的 job 預設是 `local`
  （pycue 的 `cuebot.facility_default`）。

  **所以新節點預設落在 `cloud.general`，永遠收不到 `local` 的 job。**

- **診斷**：同時看 host 與 job 兩邊的 facility

  ```bash
  cueadmin -lh              # Alloc 欄的前綴就是 facility
  cueadmin -lji <job名稱>    # 或看 CueGUI 的 Attributes -> facility
  ```

  ```
  LAPTOP-ULJICLO8  ...  local.desktop     <- facility local
  render02         ...  cloud.general     <- facility cloud  ← 對不上
  ```

- **解法**：把節點移到 job 所在 facility 的 allocation

  ```bash
  cueadmin -force -move local.general -host render02
  ```

  **移動後先前卡住的 job 會自動被撿走，不需要重投。**

  或在節點設定檔明確指定 facility：

  ```yaml
  machine:
    facility: local
  ```

- **部署建議**：**統一規劃 facility 並在每個節點明確指定**，
  不要依賴預設值。否則每加一台新機器都會踩一次。

- **後續實測（Windows RQD，三台測試節點）**：

  | `DEFAULT_FACILITY` | `RQD_TAGS` 開頭 | 註冊結果 |
  |---|---|---|
  | `local` | `general` | `local.general` |
  | （沒設） | `general` | `cloud.general` |
  | `local` | `desktop` | `local.desktop` |

  - Python RQD 的 `[Override]` 裡寫 `DEFAULT_FACILITY = local` **確實生效**
  - allocation 由節點回報的**第一個**能對上 allocation 的 tag 決定
    （`HostManagerService.java:189-209`），而且**只在第一次註冊時決定**
  - `OVERRIDE_IS_DESKTOP = True` 加上的 `desktop` tag 排在 `RQD_TAGS` 之後，
    所以 `RQD_TAGS` 以 `general` 開頭的工作站會進 `local.general`，不是 `local.desktop`。
    本機 LAPTOP 在 `local.desktop`，是早期 `RQD_TAGS` 還沒有 `general` 時註冊的結果

  測試節點停止後無法 lock（lock 要由 Cuebot 回連 RQD，同[場景 11](#場景-11cuenimby-啟動報-rqdclientexception-failed-to-lock-host) 的機制），
  約 5 分鐘後被標成 DOWN，之後用 `opencue.api.findHost(name).delete()` 刪除。

### 場景 21：混合作業系統農場中，job 成功但 log 找不到

- **現場畫面**：job 回報 SUCCEEDED，但去 log 目錄找卻沒有檔案。
  **完全沒有錯誤訊息。**

- **前提**：只有在農場裡**同時存在不同作業系統的節點**時才會發生。
  若節點全是 Windows（或全是 Linux），不會遇到。

- **根因**：`CUE_FRAME_LOG_DIR` 是設在 **Cuebot** 上的，**全農場共用一個值**。
  Windows 路徑交給 Linux 節點會被當成**相對路徑**。

  實測：Cuebot 設 `C:/opencue/logs`，Linux 容器節點的 log 落在

  ```
  /app/C:/opencue/logs/testing/testshot/logs/.../xxx.rqlog
       ↑ 在工作目錄底下建了一個字面上叫 "C:" 的資料夾
  ```

- **診斷**：直接去節點上找檔案

  ```bash
  # Linux 節點
  docker exec <節點> find / -name "*.rqlog" 2>/dev/null | head

  # 或看 DB 記錄的路徑與實際位置是否一致
  ```

- **解法**：用 OpenCue 內建的 per-OS log 根目錄
  （`JobLogUtil.java:59-66`）。在 Cuebot 的啟動參數加上：

  ```
  --log.frame-log-root.Windows=C:/opencue/logs
  --log.frame-log-root.debian=/tmp/rqd/logs
  ```

  **屬性名稱的 OS 部分要對應 job 的 `str_os`**，
  也就是 RQD 回報的平台名稱（`Windows` / `debian` / …）。

- **【重要前提】job 必須有指定 `os`**：

  ```python
  outline.cuerun.launch(ol, os="Windows")
  ```

  因為查找的 key 是 **job 的 `str_os`**，不是執行節點的 OS。
  job 沒指定 OS 時，查找會失敗並退回 `default_os`，等於沒有分平台。

  這與控制派工的是**同一個參數** —— 指定 OS 既決定派到哪種節點，
  也決定 log 寫到哪裡。

- **範圍限制**：這個機制**只管 frame log**。
  場景檔、貼圖、算圖輸出的路徑完全不經過它，那是投 job 端的責任。

### 場景 22：新建的 show 投遞的 job 永遠停在 WAITING

- **現場畫面**：投到 `testing` 的 job 正常執行，換成新建的 show 就一直 `WAITING`，
  **沒有任何錯誤訊息**。host、tag、facility、OS、資源全部都對。

- **這個症狀和[場景 1](#場景-1job-卡在-pendingframe-全卡-waitinghost-顯示-up--open)（tag）、[場景 20](#場景-20新節點加入後永遠收不到工作)（facility）一模一樣**，三者要一起排查。

- **根因**：Cuebot 找工作的順序是
  「**這台 host 屬於哪個 allocation → 哪些 show 訂閱了這個 allocation → 那些 show 的 job**」
  （`DispatchQuery.java` 的 `FIND_SHOWS`）。
  show 沒有訂閱節點所在的 allocation，Cuebot 根本不會看到這個 show 的 job。

  `testing` 是 flyway 的種子資料，已經訂閱了 `local.general`、`local.desktop`、`cloud.general`。
  **用 API 或介面新建的 show 預設沒有任何 subscription。**

- **最容易漏的是 `local.desktop`**：Windows 工作站在本機測試中被放在這個 allocation
  （`RQD_TAGS` 以 `desktop` 開頭的節點會進這裡，見[場景 20](#場景-20新節點加入後永遠收不到工作) 的後續實測），
  只訂閱 `local.general` 的話，工作站永遠拿不到這個 show 的 job。

- **診斷**：

  ```sql
  -- 節點在哪個 allocation
  SELECT h.str_name, a.str_name AS alloc
  FROM host h JOIN alloc a ON a.pk_alloc = h.pk_alloc;

  -- show 訂閱了哪些 allocation
  SELECT sh.str_name AS show, a.str_name AS alloc, s.int_burst
  FROM subscription s
  JOIN show sh ON sh.pk_show = s.pk_show
  JOIN alloc a ON a.pk_alloc = s.pk_alloc
  ORDER BY 1, 2;
  ```

  節點的 allocation 不在該 show 的清單裡，就是這個問題。
  另外 `int_burst` 必須大於 0，而且要比已用的核心數多至少 1 核。

- **解法**：補上 subscription。用 `opencue-init` 容器的話，把 allocation 加進
  `OPENCUE_INIT_ALLOCS` 後重新部署即可（已存在的不會重複建立）：

  ```
  建立 subscription local.desktop.inita（1000 核）
  ```

  實測補上後 **10 秒內**就 SUCCEEDED。詳見 [`22`](22-兩種部署路線.md)。

### 場景 23：RQD 一啟動就崩潰，報 UnicodeDecodeError

- **現場畫面**：

  ```
  UnicodeDecodeError: 'cp950' codec can't decode byte 0x.. in position ..: illegal multibyte sequence
  ```

  同一份 `rqd.conf` 在某些機器可以用，換一台就不行。

- **根因**：RQD 讀 `rqd.conf` 時**沒有指定編碼**，使用系統的 ANSI 代碼頁。
  繁體中文 Windows 是 cp950，設定檔裡只要有 UTF-8 的中文（**包括註解**）就會解碼失敗。

  能用的那台機器，通常是開啟了 Windows 的
  「Beta：使用 Unicode UTF-8 提供全球語言支援」，ANSI 代碼頁變成 65001。

  檢查方式（PowerShell）：

  ```powershell
  (Get-ItemProperty HKLM:\SYSTEM\CurrentControlSet\Control\Nls\CodePage).ACP
  # 950 = cp950，65001 = UTF-8
  ```

- **解法**：`rqd.conf` **只用純 ASCII**，註解也用英文。
  [`notes/deploy/node/rqd-windows.conf`](../deploy/node/rqd-windows.conf) 已經改成純 ASCII 版本。

- **相關**：`.bat` 放中文也會出問題（[場景 8](#場景-8windows-包裝腳本報-tlocal-is-not-recognized-或語法錯誤)），原因類似但來源不同（cmd.exe 的 OEM 代碼頁）。
  節點端所有檔案都用純 ASCII 最保險。詳見 [`notes/deploy/02` 第二節](../deploy/02-算圖節點.md#二重要設定檔與腳本一律使用純-ascii)、[`05` 第 18 項](05-可回饋上游的問題.md#18-python-rqd-讀取-rqdconf-時沒有指定編碼)。

### 場景 24：路徑含空白時 frame 失敗

- **現場畫面**：frame 一開始就 DEAD，log 裡的指令在空白處被切斷：

  ```
  C:\opencue>D:/programs/Side Effects Software/Houdini 22.0.429/bin/hython.exe -c print(123)
  'D:/programs/Side' is not recognized as an internal or external command,
  ```

  ```
  C:\opencue>cmd /c dir /b C:\Program Files\Common Files
  The system cannot find the file specified.
  ```

- **根因**：pyoutline 把串列形式的指令**直接用空白接成一個字串**，不加引號
  （`pyoutline/outline/backend/cue.py:325`：`" ".join(cmd)`）。
  Cuebot 只用一個字串欄位存指令，Windows RQD 也是以字串執行，元素的邊界就不見了。

  所以[場景 6](#場景-6dcc-算圖報找不到檔案反斜線路徑被吃掉) 的「用串列傳入」**只能保護反斜線，不能保護空白**。

- **實測**（Windows 節點，每種各一個 frame）：

  | 串列中的元素 | 結果 |
  |---|---|
  | `C:\Program Files\Common Files`（參數） | DEAD |
  | `"C:\Program Files\Common Files"`（自己加引號） | SUCCEEDED |
  | `D:\programs\Side Effects Software\...\hython.exe`（執行檔） | DEAD |
  | 同上，自己加引號 | SUCCEEDED |
  | `D:/programs/Side Effects Software/...`（正斜線） | DEAD |
  | 同上，自己加引號 | SUCCEEDED |

- **解法**：
  1. 執行檔一律透過 `ocrun`（[`26`](26-ocrun取代wrapper.md)），指令裡沒有安裝路徑；
     `ocrun` 以串列呼叫 DCC，安裝路徑含空白也沒問題（Houdini 裝在
     `Side Effects Software` 底下，已實際算圖成功）
  2. 參數中可能含空白的路徑（場景檔、輸出路徑），在投遞腳本裡**自己加上雙引號**：

     ```python
     def q(path):
         return '"' + path + '"'

     command = ["ocrun", "maya", "2027", "Render", "-r", "sw",
                "-s", "#IFRAME#", "-e", "#IFRAME#", "-rd", q(outdir), q(scene)]
     ```

     `ocrun` 收到的參數已經去掉外層引號，再原樣轉給 DCC（實測 `"C:/opencue/tmp/a b/t.py"`、`"x y"` 完整傳到 hython）。

- **CueSubmit 與 DCC 外掛**：它們用 `command.split()` 以空白切開指令字串，
  **加引號也無效**。路徑含空白時無法使用，只能確保指令與路徑沒有空白。

- 詳見 [`05` 第 21 項](05-可回饋上游的問題.md#21-pyoutline-把串列指令用空白接起來不加引號)。

### 場景 25：算圖節點的桌面跳出 Autodesk 錯誤回報視窗

- **現場畫面**：節點（或兼任節點的工作站）桌面上出現 Autodesk 的錯誤回報視窗。
  有兩種情況：
  1. **每個 Maya frame 都跳，但 frame 全部成功**，圖也都有輸出
  2. 偶爾跳，同時有 frame 失敗

- **情況 1 的根因**：frame 缺少 `ALLUSERSPROFILE`。Maya 裡的 Autodesk 授權模組（CLIC）
  在算完、結束時丟出例外，由授權模組自帶的回報程式跳出視窗；每格也因此多花約 15 秒。
  確認方式：`%LOCALAPPDATA%\Autodesk\CER\` 底下的 `cer.log` 出現 `UPI_PRODUCT, value CLIC`，
  例外碼 `0xE06D7363`。**`MAYA_DISABLE_CER` 關不掉這個視窗**，它只管 Maya 本體的回報。

- **情況 2 的根因**：算圖用的 `mayabatch.exe` 真的當掉。確認方式是 Windows 事件檢視器 → 應用程式，
  找 `mayabatch.exe` 的錯誤。先前實測的原因是記憶體耗盡（工作站開著 Maya，同時跑好幾個算圖 frame）。

- **解法**：
  - 情況 1：`rqd.conf` 加上 `[UseHostEnvVar]` 區段並列入 `ALLUSERSPROFILE`，重啟 RQD
    （範本 [`node/rqd-windows.conf`](../deploy/node/rqd-windows.conf) 已加入）
  - 情況 2：找出 Maya 當掉的原因，常見的是記憶體不足。看 frame log 的 `maxrss` 與 Windows 事件紀錄

- 詳見 [`28`](28-Maya結束時跳出錯誤回報.md)、[`25` 第五節](25-Maya內投遞.md#五人工測試中發現的問題)。

### 場景 26：用 API 砍 job，沒有錯誤但 job 繼續跑

- **現場畫面**：腳本呼叫 `job.kill()`，沒有任何例外，但 job 仍是 PENDING，frame 繼續 RUNNING。
  RQD 的 log 沒有收到 kill 請求。

- **根因**：Cuebot 對手動砍 job 要求附上理由（`JobManagerSupport.java:100`）。
  理由是空的就只在自己的 log 記一行 `**Invalid Job Kill Request**`，
  gRPC 仍回傳成功，呼叫端完全不知道沒有生效。

- **解法**：一律附上理由：

  ```python
  job.kill(reason="cancel by pipeline")
  ```

  只砍單一 frame 的 `proc.kill()` 不需要理由，不受影響。

- 詳見 [`26`](26-ocrun取代wrapper.md)。

### 場景 27：frame 產生的檔名日期或 log 時間差了 15 小時

- **現場畫面**：算圖腳本以日期命名的資料夾是前一天；DCC 寫進 frame log 的時間與主機時間對不上。

- **根因**：RQD 把每個 frame 的 `TZ` 寫死為 `PST8PDT`（`rqd/rqd/rqmachine.py` 的 `getTimezone()`），
  frame 裡的本地時間是美西時間。

- **解法**：`rqd.conf` 的 `[UseHostEnvVar]` 區段列入 `TZ`，重啟 RQD
  （範本 [`node/rqd-windows.conf`](../deploy/node/rqd-windows.conf) 已加入）。
  Windows 主機通常沒有 `TZ`，frame 拿到空值，改用 Windows 的時區設定。
  Linux 節點不能照搬：空的 `TZ` 在 Linux 代表 UTC。

- 詳見 [`29`](29-frame的時區.md)。

### 場景 28：frame 顯示成功，但沒有輸出圖

- **現場畫面**：Maya（Arnold）的 frame 全部 SUCCEEDED、exit 0，輸出目錄卻是空的。
  frame log 裡有 `license checkout error` 與 `aborting render because ... abort_on_license_fail`。

- **根因**：
  1. frame 拿不到 Arnold 授權：授權伺服器的位置（`solidangle_LICENSE`）只在使用者環境裡，RQD 不會傳給 frame
  2. Arnold 中止時，`Render.exe` 仍然回傳 0

- **解法**：
  - `dcc.toml` 的 `[env]` 寫入 `solidangle_LICENSE`
  - 一律透過 `ocrun` 執行 Maya：`ocrun` 檢查到這類錯誤會讓 frame 以 exit 1 結束，不會再出現假成功
    （log 最後有 `[ocrun] failing the frame`）

- 詳見 [`30`](30-Arnold授權與假成功.md)。

### 場景 29：新節點永遠註冊不上，RQD 沒有任何錯誤

- **現場畫面**：RQD 已啟動（log 停在 `RQD Started`），`cueadmin -lh` 卻看不到這台。

- **排查驗證**：

  ```bash
  docker logs opencue-cuebot 2>&1 | grep "value too long"
  # ERROR: value too long for type character varying(128)（在 recalculate_tags 裡）
  ```

- **根因**：節點所有 tag 以空白串起來超過 128 個字元（上游 `host.str_tags` 的上限）。
  DCC 版本 tag 越多越容易超過；工作站的 `desktop` 本身就會出現三次。

- **解法**：使用工作室 build 的 flyway image（含 `R__Studio_widen_host_tags.sql`，上限改為 4000），
  重新執行 flyway 後，節點在下一次回報時自動註冊。見 [`32`](32-節點tag長度上限.md)。
