# 17 — 故障排查與常見疏失速查手冊

實作人員在安裝、部署或營運 OpenCue 時，最常面臨的挑戰是：**「畫面卡住了 / 噴出某行錯，我到底該去改哪一個檔案、哪一條設定？」**

本篇以**「眼前看到的現象或報錯關鍵字」**為索引，將本專案在實測中踩過、驗證過的 15 個坑點全面具體化，直接對準可能發生疏失的設定位置與排查指令。

## 各場景詳細排查與處置手冊

### 場景 1：Job 卡在 PENDING、Frame 全卡 WAITING，Host 顯示 UP / OPEN

- **現場畫面**：`cueadmin -lh` 顯示 Windows 節點狀態健康（`UP`、`OPEN`），Job 已經進入佇列，但所有 Frame 動也不動。
- **對準疏失點**：
  1. 檢查 `notes/sandbox/stack/rqd-windows.conf` 的 `RQD_TAGS` 是否漏掉了 `general`。
  2. 若主機被移入自訂 Allocation（如 `local.desktop`），主機標籤被重置，預設 pyoutline 派發的任務要求 `general | util` 標籤，兩者對不上。
- **排查驗證**：
  進入 DB 容器查詢兩者的 Tag：
  ```bash
  docker exec -it opencue-db psql -U cuebot -c "
  SELECT str_name, str_tags FROM layer WHERE str_state='PENDING';
  SELECT h.str_name, ht.str_tag FROM host h JOIN host_tag ht ON h.pk_host=ht.pk_host;"
  ```
- **解法**：在 Windows 節點的 `rqd.conf` 加上 `RQD_TAGS = general`，重啟 RQD。

### 場景 2：Host 狀態顯示 LOCKED，Job 派不上去

- **現場畫面**：`cueadmin -lh` 顯示節點狀態為 `LOCKED`，即使沒有人在操作電腦也一樣。
- **對準疏失點**：
  1. 檢查當前時間是否落在 `cuenimby.json` 設定的上班封鎖時段（如週一至週五 09:00-18:00）。
  2. 檢查 `cuenimby.json` 是否設定了跨午夜時段（如 `18:00-09:00 available` 或 `22:00-06:00 disabled`）—— 此設定觸發上游邏輯 Bug，會導致整天判定反轉！
- **排查驗證**：
  查看本機 CueNIMBY 日誌：
  ```powershell
  Get-Content C:\opencue\cuenimby.log -Tail 20
  ```
- **解法**：
  1. 測試期間手動解鎖：
     ```bash
     cueadmin -force -unlock -host <節點名稱>
     ```
  2. 正式排程必須改寫為不跨午夜的封鎖時段（如 `09:00-18:00 disabled`）。

---

### 場景 3：Frame 卡在 RUNNING 數十分鐘，無 Log、無子行程

- **現場畫面**：CueGUI 上看見 Frame 變成黃色 `RUNNING`，但看算圖機的工作管理員毫無 DCC 行程，Log 目錄也完全沒有產生 `.rqlog`。
- **對準疏失點**：
  1. **單向通訊中斷**：RQD 能連上 Cuebot（8443），但 Cuebot 要派工回連 RQD（8444）時失敗。
  2. Windows 工作站本機防火牆阻擋了 8444 入站。
  3. Cuebot 把主機名稱截成第一段短名稱，但 Cuebot 容器內的 DNS 解析不到該短名稱。
- **排查驗證**：
  在 Linux 宿主檢視 Cuebot 日誌：
  ```bash
  docker logs opencue-cuebot | grep "RqdClientException"
  ```
  若出現 `failed to obtain status for frame`，在 Cuebot 容器內測試網路：
  ```bash
  docker exec opencue-cuebot getent hosts <Windows節點短名稱>
  docker exec opencue-cuebot bash -c 'timeout 3 bash -c "</dev/tcp/<Windows節點短名稱>/8444" && echo OK || echo FAIL'
  ```
- **解法**：
  1. Windows 防火牆放行 TCP 8444 Inbound。
  2. 在 `opencue.portainer.yml` 加入 `dns` 與 `dns_search`，或配置 `extra_hosts`。

### 場景 4：Frame 啟動瞬間崩潰，回報 Exit Status 299

- **現場畫面**：Job 剛被派發就立刻轉為紅色 Failed，退出碼顯示 `299`（`EXIT_STATUS_FRAME_CLEARED`）。
- **對準疏失點**：Linux 容器版 RQD 特有問題。投遞者的 Linux UID（通常為第一個桌面使用者的 1000）與 RQD 容器內既有的 `rqd` 系統帳號 UID 1000 衝突，RQD 內部無條件執行 `useradd` 失敗。
- **排查驗證**：
  檢視 Cuebot 日誌：
  ```bash
  docker logs opencue-cuebot | grep ABORTED
  # 輸出：ABORTED: Not launching, user xxx(1000:0) could not be created.
  ```
- **解法**：在 `docker-compose.override.yml` 或 RQD entrypoint 先行用不衝突的 UID（如 2000）建立同名使用者：
  ```yaml
  entrypoint:
    - /bin/sh
    - -c
    - 'id -u <使用者名> >/dev/null 2>&1 || useradd --uid 2000 --gid 1000 -M <使用者名>; exec /app/openrqd'
  ```

### 場景 5：Windows RQD 啟動時直接崩潰 ModuleNotFoundError: 'wmi'

- **現場畫面**：在 Windows 執行 `rqd.exe` 時立刻跳出錯誤終止：
  `ModuleNotFoundError: No module named 'wmi'`。
- **對準疏失點**：OpenCue 上游 `rqd/pyproject.toml` 遺漏宣告 Windows 專用的條件相依套件。
- **解法**：手動在 Windows venv 補齊套件：
  ```cmd
  <venv>\Scripts\pip.exe install wmi pywin32
  ```

### 場景 6：DCC 算圖報找不到檔案，反斜線路徑被吃掉

- **現場畫面**：Houdini 或 Maya 報錯找不到場景檔，Frame Log 印出的指令把 `\\server\share\file.ma` 顯示為 `serversharefile.ma`。
- **對準疏失點**：投遞 Job 的 Python 腳本（`submit.py`）傳遞了「字串」格式的指令，觸發了 pyoutline 底層的 POSIX `shlex.split()` 解析，將反斜線當成跳脫字元刪除。
- **解法**：投遞腳本的 `Shell(command=...)` 參數，**一律嚴格傳入串列（List）**，例如：
  ```python
  # 正確
  command = ["C:/opencue/bin/maya-render-2027.bat", r"\\server\share\file.ma", outdir]
  # 錯誤
  command = f"C:/opencue/bin/maya-render-2027.bat \\\\server\\share\\file.ma {outdir}"
  ```

### 場景 7：Nuke 算圖全面失敗，報 Unable to create disk cache

- **現場畫面**：Nuke 在本機手動執行包裝腳本正常，但經由 OpenCue 農場派發時每個 Frame 都以 Exit 1 失敗，Log 顯示：
  `ERROR: Unable to create disk cache at C:/temp/nuke`。
- **對準疏失點**：RQD 傳給子行程的環境變數裡有 `TMP` 但**漏傳了 `TEMP`**。Nuke 在 Windows 找不到 `TEMP` 時，會自動退回嘗試存取寫死的 `C:/temp`，而節點上根本沒有該目錄。
- **解法**：在包裝腳本 `nuke-17.0v1.bat` 顯式定義快取與暫存環境：
  ```bat
  if "%NUKE_DISK_CACHE%"=="" set NUKE_DISK_CACHE=C:\opencue\tmp\nuke
  if not exist "%NUKE_DISK_CACHE%" mkdir "%NUKE_DISK_CACHE%"
  set TEMP=C:\opencue\tmp
  set TMP=C:\opencue\tmp
  ```

### 場景 8：Windows 包裝腳本報 'tlocal' is not recognized 或語法錯誤

- **現場畫面**：啟動 RQD 或執行算圖包裝腳本時，控制台噴出：
  `'tlocal' is not recognized as an internal or external command`，或 `if (...)` 括號配對錯誤。
- **對準疏失點**：包裝腳本（`.bat`）存成了 UTF-8 編碼且含有中文註解。Windows `cmd.exe` 預設使用繁體中文 OEM 代碼頁（CP950）解析，將 UTF-8 中文字節誤判為控制字元，破壞了語法。
- **解法**：所有部署在 Windows 節點上的 `.bat` 檔案必須是 **純 ASCII 編碼**。所有中文說明請寫在外部 Markdown 筆記中。

### 場景 9：CueWeb 檢視 Frame Log 報 HTTP 400: Query parameter 'path' is required

- **現場畫面**：在 CueWeb 點擊檢視某個 Frame 的 Log，瀏覽器跳出 HTTP 400 錯誤。
- **對準疏失點**：Cuebot 的 `CUE_FRAME_LOG_DIR` 被設定成了 Windows 磁碟機代號路徑（例如 `C:/opencue/logs` 或 `L:/logs`）。CueWeb 執行於 Linux 容器中，其後端 API 呼叫 `path.isAbsolute()`，判斷非 `/` 開頭的路徑為無效路徑並直接拒絕。
- **解法**：將 `CUE_FRAME_LOG_DIR` 統一設定為 **UNC 正斜線格式**：
  ```
  CUE_FRAME_LOG_DIR=//fileserver/opencue/logs
  ```
  `//` 開頭在 Linux 為合法絕對路徑（自根目錄解析），在 Windows 亦為合法 UNC 路徑，可達成跨平台路徑無損互通。

### 場景 10：CueWeb 讀取 Log 報 HTTP 403: Path is outside the allowed log roots

- **現場畫面**：CueWeb 點擊 Log 報錯 HTTP 403 Forbidden。
- **對準疏失點**：
  1. 白名單環境變數混淆：Log 讀取路由受 `CUEWEB_LOG_ROOTS` 控制，而非 `CUEWEB_PREVIEW_ROOTS`（後者是圖片縮圖白名單）。
  2. 容器內未正確掛載共享 Log 目錄。
- **解法**：
  在 `opencue.portainer.yml` 的 `cueweb` 服務確認配置：
  ```yaml
  environment:
    CUEWEB_LOG_ROOTS: /mnt/logs
    CUEWEB_PREVIEW_ROOTS: /mnt/render
  volumes:
    - ${FRAME_LOG_MOUNT_SOURCE}:/mnt/logs:ro
    - ${RENDER_OUT_MOUNT_SOURCE}:/mnt/render:ro
  ```

### 場景 11：CueNIMBY 啟動報 RqdClientException: failed to lock host

- **現場畫面**：開機登入或執行啟動腳本時，CueNIMBY 崩潰並丟出 `failed to lock host` 錯誤。
- **對準疏失點**：啟動順序錯誤。「鎖定主機」操作本質上是 Cuebot 接收請求後**回呼該節點的 RQD 8444**。若腳本先啟動 CueNIMBY、或在 RQD 尚未啟動完成前呼叫鎖定，回呼必定連線失敗。
- **解法**：啟動腳本中必須**先啟動 RQD**，並插入等待延遲（使用不畏重導向的 `ping -n 21 127.0.0.1 > nul`），確保 RQD 註冊完成後才啟動 CueNIMBY。

### 場景 12：資料庫手動清理時，活躍或進行中的任務歷史遭誤刪

- **現場畫面**：執行 SQL 清理超過 90 天的歷史紀錄後，發現當天正在執行中的 Job 也消失了，相關外鍵連動資料全被 CASCADE 抹除。
- **對準疏失點**：`job_history` 表中，尚未結束的 Job 其結束時間戳 `int_ts_stopped` 的**預設值為 0**。若 SQL 僅寫 `WHERE int_ts_stopped < (90天前)`，因為 `0 < 過去的任意時間戳` 恆成立，所有活躍中工作將全數遭到誤刪。
- **解法**：清理 SQL 必須嚴格加入防護條件：
  ```sql
  DELETE FROM job_history 
  WHERE int_ts_stopped > 0 
    AND int_ts_stopped < EXTRACT(EPOCH FROM NOW() - INTERVAL '90 days');
  ```
