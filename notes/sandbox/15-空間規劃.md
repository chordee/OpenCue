# 15 — 空間規劃

先前的空間相關內容散在各處且多為定性描述。這一份集中整理，
**數字皆為本機實測**，並標明哪些可以外推、哪些不行。

## 實測基準

以下取自本次測試環境（11 個 job / 34 個 frame，含 Houdini、Maya、Nuke 真實算圖）。

| 項目 | 實測值 | 說明 |
|---|---|---|
| frame log（`.rqlog`） | 19 檔，平均 **6.6 KB**（3.9–10 KB） | **不可直接外推**，見下 |
| 算圖輸出 | 16 檔，平均 **239 KB** | 320×240 的測試圖，**不可外推** |
| PostgreSQL | **13 MB** | 含空 schema 的基礎開銷 |
| Docker images | 59.4 GB（可回收 10.9 GB） | 含本機其他專案的 image |
| Docker build cache | **50.0 GB**（可回收 16.0 GB） | 見下方「建置機器」 |
| Docker volumes | 6.7 GB（可回收 2.7 GB） | |
| Docker containers | 579 MB（可回收 561 MB） | 多為已停止容器 |
| Windows 節點暫存 | 56 KB | `C:\opencue\tmp` |

## 各項目的成長特性

### 1. 建置機器：build cache 是最大的隱形消耗

**50 GB，而且這只是一個專案、幾次建置之後的量。**

Docker 的 buildx cache 預設不會自動清理。CueWeb（Next.js）與 cuebot（Gradle）
每次改動重建都會留下新的 cache 層。

```bash
docker system df                    # 看總量
docker builder prune                # 清掉未使用的 cache
docker builder prune --keep-storage 20GB   # 保留上限
docker builder prune -a             # 全清（下次 build 會很慢）
```

**建議**：建置機器設定 cache 上限，或在 CI 流程中定期清理。
`--keep-storage` 比全清好，保留常用層可大幅縮短重建時間。

也要注意**磁碟與記憶體是兩回事** —— CueWeb 的 build 另外需要數 GB 記憶體
（本次第一輪 build 就因記憶體不足被系統中止，見 `13`）。

### 2. Registry：每個版本約 6 GB

| Image | 大小 |
|---|---|
| cueweb | 2.52 GB |
| flyway | 2.15 GB |
| cuebot | 1.06 GB |
| rest-gateway | 184 MB |

保留 10 個版本 ≈ 60 GB。詳見 `14`，含 garbage-collect 的操作方式
（刪除 manifest 之後必須另外執行 GC 才會真的回收）。

`flyway` 的 2.15 GB 對一個「跑完即退」的 one-shot 容器偏大
（基底是 almalinux:9 加 JDK），若在意空間可以考慮瘦身。

### 3. PostgreSQL：會無限成長，但速度不快

實測 13 MB（34 個 frame 之後），其中大部分是空 schema 的基礎開銷。

**關鍵問題不是速度而是「永遠不會縮」**：
Cuebot 在 job 完成 72 小時後把它搬進歷史表，
但**歷史表沒有任何自動清除機制**（見 `11` 第 6 點）。

清理 SQL 與必要的防護條件見 `11`，重點是一定要加 `int_ts_stopped > 0`，
否則會誤刪未結束的 job。

**建議**：
- 訂定歷史保留期（例如 90 天），以排程執行清理
- 納入 `pg_dump` 備份（指令見 `11`）
- 定期 `VACUUM FULL` 或 `pg_repack` 才會真的把空間還給檔案系統

### 4. Frame log：數量大但單檔小，**本次數字不可外推**

實測平均 6.6 KB，但那是**測試用的簡單工作**：

- `/bin/sleep` 的 log 只有 header 與環境變數
- Houdini/Maya/Nuke 的測試場景也極簡單

**真實算圖的 log 可能大上兩三個數量級** —— 算圖器的 verbose 輸出、
警告、統計資訊，單檔數 MB 並不罕見。

真正可外推的是**數量**：每個 frame 一個檔案。

```
50,000 frames/天 × 每檔 1 MB  ≈ 50 GB/天
```

**這通常是共享儲存上成長最快的東西。**

**建議**：
- 訂定 log 保留期（例如 30 天）並以排程刪除
- 注意刪除 log 不會影響 Cuebot 的 job 歷史，只是之後點開會找不到檔案
- CueWeb 的 log 讀取會回 404，不會壞掉

### 5. 算圖輸出：實際上最大的消耗者，但不在 OpenCue 管轄內

實測 239 KB/frame，但那是 320×240 的測試圖，**完全不能外推**。

正式環境的 2K/4K EXR 動輒數十到數百 MB。這部分的容量規劃屬於
專案與儲存團隊的範疇，OpenCue 只是把路徑寫進 job 而已。

值得注意的是 `13` 提到的一點：**CueWeb 的縮圖預覽不支援 EXR**
（只服務 png/jpeg/webp/bmp/avif）。若要在網頁上看預覽，
需要另外產生代理圖，那又是額外的空間。

### 6. Docker 宿主：容器 log 容易被忽略

`docker system df` 顯示 containers 佔 579 MB，其中 96% 可回收 ——
多為已停止的容器。

**更需要注意的是 container 的 stdout/stderr log**，預設的 json-file driver
**沒有大小上限**。Cuebot 長期執行會持續累積。

建議在 compose 中對常駐服務加上輪替設定：

```yaml
logging:
  driver: json-file
  options:
    max-size: "50m"
    max-file: "5"
```

（本次的 stack 尚未加入這項，正式部署前應補上。）

宿主定期清理：

```bash
docker system df                     # 先看
docker container prune               # 已停止的容器
docker image prune                   # 沒被引用的 image
docker volume prune                  # 沒被引用的 volume（小心）
```

**`docker system prune -a` 要謹慎** —— 它會刪掉所有未被容器使用的 image，
包含你剛從 registry 拉下來但當下沒在跑的版本。

### 7. Windows render node 本機

目前只用到 56 KB，但會成長的有：

| 路徑 | 內容 |
|---|---|
| `C:\opencue\tmp` | RQD 的 TEMP/TMP（見 `12` 坑 #14） |
| `C:\opencue\tmp\nuke` | Nuke 的 disk cache |
| DCC 各自的暫存 | Houdini、Maya 的 cache 目錄 |

**Nuke 的 disk cache 尤其需要注意** —— 它預設會持續累積直到達到設定上限。

**建議**：節點上設排程清理 `C:\opencue\tmp`，或在 `rqd-start.bat` 啟動時
清空（但要注意不能刪到正在執行的 frame 的暫存）。

## 需要 IT 確認的容量問題

| 項目 | 問題 |
|---|---|
| 共享儲存 | frame log 與算圖輸出的配額、保留策略由誰管 |
| Registry 主機 | 磁碟大小、保留幾個版本 |
| 建置機器 | 磁碟大小（build cache 會吃掉數十 GB）、記憶體 |
| Linux 宿主 | Docker 根目錄所在磁碟的大小，以及是否與其他服務共用 |
| 備份 | DB 與 registry volume 的備份空間與週期 |

## 尚未量測

| 項目 | 原因 |
|---|---|
| 真實負載下的 log 大小 | 測試場景太簡單 |
| DB 的長期成長曲線 | 測試時間太短 |
| 共享儲存的實際用量 | 本機沒有檔案伺服器 |
| container log 的累積速度 | Cuebot 才跑幾小時 |
