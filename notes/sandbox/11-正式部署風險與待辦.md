# 11 — 正式部署的風險與待辦

本次測試是「單一節點、同一台機器、實驗室網路」。規模化到真實環境時，
以下幾項在測試中不會浮現，但一定會遇到。

## 1. 多節點的 DNS 解析：別用 extra_hosts

`08` 的坑 #6 記錄到：Cuebot 會把 render node 的主機名稱截成第一段短名稱，
並用它回連 8444，所以該短名稱**必須在 Cuebot 容器內解析得到**。

測試時的解法是在 compose 硬寫：

```yaml
extra_hosts:
  - "${RENDER_NODE_NAME}:${RENDER_NODE_ADDR}"
```

**這個做法無法規模化。** 10 台、30 台 Windows 節點時，不可能逐一維護。

### 正確做法：讓容器使用公司 DNS 與網域搜尋後綴

```yaml
cuebot:
  dns:
    - 192.168.1.1        # 公司內部 DNS
  dns_search:
    - studio.local       # 網域名稱後綴
```

容器要解析短名稱 `RENDER01` 時，會自動查詢 `RENDER01.studio.local`，
完全不需要維護 `extra_hosts`。

**部署時要驗證的一行**：

```bash
docker exec opencue-cuebot getent hosts RENDER01
docker exec opencue-cuebot bash -c 'timeout 3 bash -c "</dev/tcp/RENDER01/8444" && echo OK || echo FAIL'
```

`notes/deploy/server/opencue.portainer.yml` 本身**不寫** DNS：容器預設沿用宿主的 search 網域，
宿主能解析節點短名稱時不需要任何設定。解析不到才疊上 `notes/deploy/server/site.example.yml`。
（空的 `dns_search` 會清掉繼承來的網域，所以不能放進主檔當變數，見 `22` 第六節。）

## 2. 網路磁碟機代號：可用，但有一個例外

**本節初版寫「嚴禁使用磁碟機代號」，範圍下得太寬，已修正。**

### 目標環境的前提（已確認）

- workstation 與 render node **全部都是 Windows**
- 所有機器的**網路磁碟機代號已同步**（同一個代號指向同一個共享）
- **專案檔案內部就是用磁碟機代號指定路徑**

在這個前提下，要求全面改用 UNC 等於要重寫所有場景檔，不切實際。
而且實測證明沒有必要。

### 實測：RQD 在使用者 session 下三種路徑都可用

從農場派一個 frame 到 Windows 節點，分別嘗試寫入三種形式：

```
host   : LAPTOP-ULJICLO8
使用者 : chordee

磁碟機代號   H:\opencue-drivetest                        -> 寫入成功 (34 bytes)
UNC 反斜線   \\192.168.0.107\chordee\opencue-drivetest    -> 寫入成功 (34 bytes)
UNC 正斜線   //192.168.0.107/chordee/opencue-drivetest    -> 寫入成功 (34 bytes)

結果: 全部成功
```

**結論：場景檔、算圖輸出、暫存路徑都可以沿用既有的磁碟機代號慣例。**

### 例外一：RQD 以 Windows 服務執行時（待驗證）

磁碟機代號是**綁定於登入工作階段**的。`09` 的結論是：

| 機器類型 | RQD 啟動方式 | 磁碟機代號 |
|---|---|---|
| artist 工作站 | 登入時觸發，跑在使用者 session | **可用**（已實測） |
| 專職算圖機 | Windows 服務，跑在 session 0 | **待驗證** |

系統服務在 session 0，看不到使用者對應的磁碟機。常見對策是在服務啟動時
以服務帳號執行 `net use`，或用 GPO 為該帳號建立持續性對應。

**本機無管理員權限，無法實測服務情境。** 這是部署專職算圖機前必須確認的項目：

1. 那些機器的 RQD 要以服務還是登入 session 執行？
2. 若是服務，服務帳號是否看得到那些磁碟機代號？

若不確定，最簡單的驗證是在該機器上以服務帳號執行一個寫入 `H:\...` 的測試工作。

### 例外二：CUE_FRAME_LOG_DIR 必須用 UNC 正斜線

這一項**與上面無關，是另一個獨立的技術限制**。

`CUE_FRAME_LOG_DIR` 的值除了 render node 會用，**CueWeb 也會拿它去讀檔**，
而 CueWeb 跑在 Linux 容器裡。

| 寫法 | Windows RQD | Linux 的 CueWeb 容器 |
|---|---|---|
| `L:/opencue/logs` | 可寫入 | **無法解析**，`path.isAbsolute()` 回 false → HTTP 400 |
| `//fileserver/opencue/logs` | 可寫入（UNC） | **可解析**，`//` 在 Linux 上是合法絕對路徑 |

實測見 `13`。所以：

> **frame log 的根目錄用 UNC 正斜線形式，其餘路徑沿用磁碟機代號即可。**

若不打算使用 CueWeb 的 log 檢視功能，這個限制就不存在，
`CUE_FRAME_LOG_DIR` 也可以用磁碟機代號。

### 小結

| 用途 | 建議 | 理由 |
|---|---|---|
| 場景檔、貼圖、算圖輸出 | **磁碟機代號**（沿用既有慣例） | 已實測可用，且專案檔內部本來就這樣寫 |
| frame 指令中的路徑 | 磁碟機代號，**反斜線** | 避免 DCC 命令列把正斜線當成選項開關 |
| `CUE_FRAME_LOG_DIR` | **UNC 正斜線** | 需要同時被 Linux 容器內的 CueWeb 解析 |
| 專職算圖機（服務執行） | **先驗證** | 服務帳號是否看得到磁碟機代號 |

## 3. 網路通訊矩陣與防火牆

目前只記了 port 號，沒有整理成可交給 IT 的矩陣。

| 來源 | 目的 | Port | 協定 | 用途 |
|---|---|---|---|---|
| Windows 節點 | Linux 宿主 | **8443** | TCP | RQD 向 Cuebot 註冊、回報狀態與 frame 結果 |
| Linux 宿主 | Windows 節點 | **8444** | TCP | Cuebot 派發 frame、查詢 frame 狀態、kill frame |
| Artist 工作站 | Linux 宿主 | **8443** | TCP | cueadmin / cuegui / cuesubmit / cuenimby |
| 瀏覽器 | Linux 宿主 | 3000 | TCP | CueWeb（若啟用） |
| 節點 / 工作站 | 檔案伺服器 | 445 | TCP | SMB 共享儲存 |

**最容易漏掉的是 8444 的 Inbound**：Windows 工作站的本機防火牆預設會擋，
沒開的話症狀就是 `04` 坑 #3 那種「host 看起來正常、frame 永遠卡住」。

### 資安曝險：gRPC 沒有身分驗證

本次測試觀察到的事實：`cueadmin` 只要指向 `localhost:8443` 就能列出所有
host、job，並執行 kill、delete-host 等操作，**過程中沒有任何帳號密碼或憑證**。

意味著：

- 任何能連到 8443 的人，拿到 `cueadmin` 就能操控整座農場
- job 的指令由投 job 端決定，等同可在所有 render node 上執行任意命令
- 通訊為明文

**因為那台 Linux 宿主還會掛其他服務**，8443 必須嚴格限制在內網網段／VLAN，
絕不可對外暴露。CueWeb 若啟用也應掛在反向代理後面加認證。

## 4. 全新環境的初始化（Administrative Bootstrap）

目前所有測試都依賴 `seed_data.sql` 產生的 demo 資料：show `testing`、
shot `testshot`、allocation `local.general` / `local.desktop`。

**正式環境部署完乾淨的 Cuebot 後，這些都不存在**，需要手動建立。

```bash
# 1. 建立正式的 show
cueadmin -create-show <show_name>

# 2. 建立 allocation（facility / 名稱 / tag）
cueadmin -create-alloc local render general
cueadmin -create-alloc local workstation desktop

# 3. 讓 show 訂閱 allocation（size = 保證核心數，burst = 尖峰上限）
cueadmin -create-sub <show_name> local.render 100 200
cueadmin -create-sub <show_name> local.workstation 50 100

# 4. 把上線的節點移進對應的 allocation
cueadmin -force -move local.render -host RENDER01 RENDER02
cueadmin -force -move local.workstation -host ARTIST01

# 5. 確認
cueadmin -la          # 列出 allocation
cueadmin -lb <show>   # 列出該 show 的訂閱
cueadmin -lh          # 列出 host 與其 allocation
```

**別忘了 tag**：見 `09` 的坑 #10 —— host 移進非 general 的 allocation 後，
若沒有在 RQD 設定 `RQD_TAGS = general`，就收不到 pyoutline 預設的
`general | util` job，而且完全沒有錯誤提示。

## 5. 防毒 / EDR 可能把 NIMBY 當成側錄木馬

`09` 記錄到 RQD NIMBY 用 `pynput` 偵測鍵鼠活動。

**風險**：`pynput` 的作法是掛全域鍵盤滑鼠 hook。企業級的端點防護
（Windows Defender ASR、CrowdStrike、SentinelOne 等）普遍會把
「掛全域輸入 hook 的 Python 行程」判定為 Keylogger 並攔截或直接終止。

**後果**：RQD 可能無法啟動、或 NIMBY 靜默失效（artist 工作時照樣被派工）。

**待辦**：部署前先與 IT 確認，必要時為
`C:\opencue\...\python.exe` / `rqd.exe` 申請白名單。

註：若採用 `09` 的結論 —— 用 CueNIMBY 時段排程、關閉 RQD 內建 NIMBY
（`OVERRIDE_NIMBY = False`）—— 就不會掛輸入 hook，可以完全迴避這個風險。
**這是選擇 CueNIMBY 排程的另一個理由。**

## 6. PostgreSQL 的資料保留與備份

`06` 只寫了「需要定期清理策略」，以下是查證後的實際機制。

### Cuebot 的歷史資料處理

`cuebot/src/main/resources/opencue.properties:419`：

```properties
# Jobs will be archived to the history tables after being completed for this long.
history.archive_jobs_cutoff_hours=72
```

`HistoricalManagerService.transferJob()` 會把完成超過 72 小時的 job
搬到歷史表：`job_history`、`layer_history`、`frame_history`。

**關鍵：那是「搬移」，不是「刪除」。**

搜尋過 cuebot 原始碼，**沒有任何針對歷史表的自動清除機制**
（只有 migration 裡針對未完成 frame 的觸發器會刪 `frame_history` 的列）。

**結論**：熱資料表不會因歷史資料而變慢，但 **PostgreSQL 的體積會無限成長**。
需要自行規劃歷史表的保留期與清理作業。

### 清理 SQL（含一個必要的防護條件）

外鍵連動已驗證確實成立：

```
frame_history | c_frame_history_pk_job | CASCADE | job_history
layer_history | c_layer_history_pk_job | CASCADE | job_history
```

所以只要刪 `job_history`，`layer_history` 與 `frame_history` 會一併清掉。

**但直覺的寫法會誤刪資料**：

```sql
-- 【錯誤】不要這樣寫
DELETE FROM job_history
WHERE int_ts_stopped < EXTRACT(EPOCH FROM NOW() - INTERVAL '90 days');
```

`job_history.int_ts_stopped` 的**預設值是 0**，尚未結束的 job 其值就是 0，
而 `0 < 任何過去的 epoch` 恆為真 —— 這些列會被一併刪除，
並 CASCADE 清掉它們的 layer / frame 歷史。

本機實測（測試環境共 8 筆 job_history）：

| 寫法 | 會刪除的筆數 |
|---|---|
| 未加防護 | **2**（皆為 `int_ts_stopped = 0`，且仍存在於 `job` 表中的活躍 job） |
| 加上 `int_ts_stopped > 0` | 0（正確，因為測試資料都很新） |

**正確寫法**：

```sql
DELETE FROM job_history
WHERE int_ts_stopped > 0
  AND int_ts_stopped < EXTRACT(EPOCH FROM NOW() - INTERVAL '90 days');
```

執行前務必先以 `SELECT count(*)` 用同一組條件確認影響範圍。

另有 `b_archived` 布林欄位，語意上應可作為額外條件，
但本次測試的 job 都未滿 72 小時、尚未歸檔，無法驗證其行為，故不納入建議。

### 備份

named volume `opencue-db-data` 若損壞，整座農場的狀態就沒了。
至少要有定期的邏輯備份：

```bash
# 備份
docker exec opencue-db pg_dump -U cuebot -d cuebot -Fc -f /tmp/cuebot.dump
docker cp opencue-db:/tmp/cuebot.dump ./cuebot-$(date +%Y%m%d).dump

# 還原（到乾淨的資料庫）
docker cp ./cuebot-YYYYMMDD.dump opencue-db:/tmp/restore.dump
docker exec opencue-db pg_restore -U cuebot -d cuebot --clean /tmp/restore.dump
```

`-Fc` 是 custom format，支援平行還原與選擇性還原，比純 SQL 好用。

**後續實測（還原）**：以臨時的 postgres:15.1 容器還原本機備份（283 KB）：

| 指令 | 情境 | 結果 |
|---|---|---|
| `--clean` | 空的 DB | **exit 1、474 個錯誤**（全是 DROP 不存在的物件），但資料完整 |
| `--clean --if-exists` | 已有資料、先刪掉 2 個 service | exit 0、0 個錯誤，service 13 → 11 → 還原後 13 |
| `--clean --if-exists` | 空的 DB | exit 0、0 個錯誤 |

還原後 host / service / show / job_history 的數量（2 / 13 / 3 / 41）、
表數量（68）、flyway 版本（49）都與正式 DB 一致。
**上面的還原指令應加上 `--if-exists`**，正式步驟已更新在 `notes/deploy/04`。

**備份頻率的考量**：DB 裡的是 job 狀態與歷史，不是算圖成果。
遺失一天的資料代表「不知道昨天哪些 job 跑過」，而不是要重算。
對多數團隊每日一次即可。

## 8. 自建 image 與 registry 不是選項，是必要步驟

原本以為「正式環境可以直接拉官方預建 image」，實測後確認**行不通**。

### CueWeb 與 REST Gateway 根本沒有發布

```
opencue/cuebot        -> HTTP 200
opencue/rqd           -> HTTP 200
opencue/cueweb        -> HTTP 404
opencue/rest-gateway  -> HTTP 404
```

compose 裡寫的 `image: opencue/cueweb:latest` 是無效的。
要用網頁 UI，**必須自行 build**。

### 就算是有發布的 cuebot，版本也落後很多

Docker Hub 上 `opencue/cuebot` 的 tag 只到 `1.19.1`，
而從 master 建出來的是 `1.34.4`。

### 因此正式部署的流程是

```
開發/建置機器                      內部 registry              Linux 宿主
  git clone
  docker compose build   ──push──>  registry.example.com  ──pull──>  Portainer
    cuebot                            /opencue/cuebot:1.34.4          stack
    flyway                            /opencue/flyway:1.34.4
    rest-gateway                      /opencue/rest-gateway:1.34.4
    cueweb                            /opencue/cueweb:1.34.4
```

**需要準備的**：

| 項目 | 說明 |
|---|---|
| 建置機器 | 需要足夠記憶體。CueWeb 是 Next.js，build 時 Node 會吃數 GB |
| 內部 registry | 或使用雲端 registry。Portainer 需要能拉取 |
| Tag 策略 | **不要用 `latest`**。用明確版本，才能回滾與追溯 |
| 認證設定 | CueWeb 的 `NEXT_PUBLIC_AUTH_PROVIDER` 是 **build arg**，要啟用登入認證就必須在 build 時決定 |

### 自行 build 的其他好處

| 好處 | 說明 |
|---|---|
| 版本一致 | Cuebot / RQD / client 全部來自同一個 commit，不會有協定落差 |
| 客製化 | log 編輯器連結、預覽程式、CueProgBar 指令等都是 build arg |
| 供應鏈控管 | base image 的安全更新、內部政策 |
