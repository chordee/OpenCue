## 五、建議的下一步

### 若能找到任何一台實體 Windows 機器（即使是閒置筆電）

**不需要裝 DCC**，光裝 Python + RQD 就能一次驗證四個最容易出事的項目：

1. 第二台的短主機名稱能否被 Cuebot 容器解析
2. Windows 防火牆的入站 8444
3. 磁碟機代號在兩台之間是否真的一致
4. 包裝腳本在「路徑不同的機器」上是否有效（放一個假的包裝腳本即可）

**這四項的投報率遠高於本機任何其他測試。**

### 本機還能做、且值得做的

| 優先 | 項目 | 理由 |
|---|---|---|
| 中 | RQD NIMBY 即時偵測 | 若最終決定用它而非 CueNIMBY 排程，行為必須先確認 |
| 中 | 雙角色並存的派工行為 | 工作站與專職算圖機同時在線時的分配 |
| 中 | DCC 內嵌投遞外掛 | artist 實際會用的投遞方式（Maya / Nuke） |
| 低 | Portainer UI 操作 | 若 IT 只給 UI 才需要 |
| 低 | monitoring profile | 對「先跑起來」沒有幫助，且吃資源 |

**若考慮啟用 Loki，優先序要提高** —— 啟用後 frame log 改走 Loki 而非檔案系統，
我們花很多力氣驗證的 UNC 路徑、per-OS 對應、CueWeb 讀取限制**全部不適用**，
那些結論要重測。

### 不建議在本機做

| 項目 | 理由 |
|---|---|
| Windows 虛擬機 | 記憶體吃緊、要裝整套 DCC、授權可能有問題，投報率低 |
| 規模測試 | 單機模擬數十節點的結果不具參考價值 |
