## 二、部分驗證 —— 有重要條件未涵蓋

## 五、建議的下一步

### 若能找到任何一台實體 Windows 機器（即使是閒置筆電）

**不需要裝 DCC**，光裝 Python + RQD 就能一次驗證四個最容易出事的項目：

1. 第二台的短主機名稱能否被 Cuebot 容器解析
2. Windows 防火牆的入站 8444
3. 磁碟機代號在兩台之間是否真的一致
4. `ocrun` 在「路徑不同的機器」上是否有效（`dcc.toml` 指向任一個程式即可）

**這四項的投報率遠高於本機任何其他測試。**

### 本機還能做的（都需要人工操作）

本機可以自動完成的項目已全部做完（[`22`](22-兩種部署路線.md)、[`23`](23-Portainer的Git模式.md)、[`24`](24-派工行為與監控.md)）。剩下的都需要有人操作介面或 DCC：

| 項目 | 需要的操作 |
|---|---|
| 桌面版 CueSubmit | 開啟視窗、投遞一個 job |
| RQD 內建 NIMBY 即時偵測 | 算圖時移動滑鼠或鍵盤（只有決定改用它、不用 CueNIMBY 排程時才需要） |
| DCC 內嵌投遞外掛 | 在 Maya / Nuke 裡操作 |
| Portainer UI 操作 | 照 [`notes/deploy/01`](../deploy/01-伺服器.md) 在介面上建一次 stack，確認文件寫得夠清楚 |

Loki 已評估並決定不採用（[`24` 第五節](24-派工行為與監控.md#五loki-日誌後端只評估未實測)），前面關於檔案系統 log 的結論維持有效。

### 不建議在本機做

| 項目 | 理由 |
|---|---|
| Windows 虛擬機 | 記憶體吃緊、要裝整套 DCC、授權可能有問題，投報率低 |
| 規模測試 | 單機模擬數十節點的結果不具參考價值 |
