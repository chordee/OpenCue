# 05 — 可回饋上游的問題

本次建置過程中發現的、屬於 OpenCue 專案本身而非我們環境的問題。
每一項都附了重現方式與定位到的程式碼位置。

## 1. `.gitattributes` 不完整，Windows 上 clone 後 cuebot 無法 build

**嚴重度**：中（擋住所有 Windows 開發者）

**現況**：repo 的 `.gitattributes` 只有一行：

```
*.sh text eol=lf
```

**問題**：Windows 使用者的 git 通常是 `core.autocrlf=true`，clone 後 Java 原始碼
變成 CRLF。cuebot 的 Gradle build 含 `spotless` 格式檢查，要求 LF，直接失敗：

```
Execution failed for task ':spotlessJavaCheck'.
> The following files had format violations:
      src/main/java/com/imageworks/common/spring/remoting/CueServerInterceptor.java
          -package com.imageworks.common.spring.remoting;\r\n
```

**誤導性**：失敗前會先噴一大串 `repo.spring.io` 的 HTTP 401，很容易被誤判成
網路或 repository 問題，但那些是雜訊。

**建議修法**：補上涵蓋原始碼的 `.gitattributes`，例如

```
* text=auto eol=lf
*.bat text eol=crlf
*.png binary
```

## 2. Sandbox 的 RQD 回報 IPv6 位址，導致 Cuebot 無法派發 frame

**嚴重度**：高（開箱即壞，sandbox 的預設設定無法完成任何 frame）

**重現**：照 `sandbox/README.md` 在 Linux（本例為 WSL2 Ubuntu 24.04）上
`docker compose up -d`，投任何 job。

**現象**：
- `cueadmin -lh` 看起來正常，host 狀態 UP
- 但 host 名稱是 IPv6 位址，例如 `fdc2:c6c:d60f:9::4`
- frame 永遠卡在 RUNNING，無 log、無子行程
- Cuebot log：`failed to obtain status for frame ...`

**根因**：`docker-compose.yml` 的 rqd 服務設定

```yaml
- OPENRQD__MACHINE__USE_IP_AS_HOSTNAME=true
```

RQD 挑到 IPv6 位址回報，但 openrqd 的 gRPC server 只聽 IPv4。
「RQD → Cuebot」通、「Cuebot → RQD」不通。

實測（從 cuebot 容器內）：

```
rqd:8444             → OK
fdc2:c6c:d60f:9::4:8444 → Connection refused
```

**建議修法**：sandbox 的預設值改為 `false`（Rust RQD 的原始碼預設本來就是
false，見 `rust/config/rqd.yaml` 的註解）。若要保留 IP 模式，需確保選出的是
gRPC server 實際綁定的位址家族。

## 3. RQD 無條件建立使用者，uid 衝突時整個 frame 失敗

**嚴重度**：高（任何投 job 者的 uid 撞到容器內既有 uid 就全掛）

**現象**：frame 回報 exit status 299（`EXIT_STATUS_FRAME_CLEARED`），
Cuebot log：

```
ABORTED: Not launching, user chordee(1000:0) could not be created.
× Failed to create user chordee: useradd: UID 1000 is not unique
```

**根因**：`rust/crates/rqd/src/frame/manager.rs:84-96`

只要 `run_frame.uid_optional` 有值，就無條件呼叫 `create_user_if_unexisting`，
**完全不看 `runner.run_as_user` 設定**（該設定預設為 false）。

而 `create_user_if_unexisting`（`rust/crates/rqd/src/system/linux.rs:921`）
只用**名稱**判斷存在與否，名稱不存在就 `useradd --uid <uid>`，
撞到既有 uid 就失敗。

sandbox 的 rqd 容器內 uid 1000 已被 `rqd` 使用者佔用，
而 Linux 桌面環境第一個使用者的 uid 慣例就是 1000 —— 衝突機率極高。

**建議修法**（擇一或併行）：
- 只在 `runner.run_as_user == true` 時才建立使用者
- uid 已被佔用時，退回使用 `default_uid` 並記一筆 warning，而不是 abort 整個 frame
- 至少讓錯誤訊息指出可以用 `run_as_user` 或 `default_uid` 解決

## 4. compose 檔裡的 macOS 專用路徑

**嚴重度**：低（不影響功能，但會在 Linux 宿主根目錄留下空目錄）

`docker-compose.yml` 的 rqd volumes 有：

```yaml
- /var/folders:/var/folders:ro
```

`/var/folders` 是 macOS 的暫存路徑。Linux 宿主上 Docker 會自動建一個
root-owned 空目錄掛進去。

**建議修法**：改成平台條件式，或至少加註解說明用途。
