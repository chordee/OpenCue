# 05 — 可回饋上游的問題

本次建置過程中發現的、屬於 OpenCue 專案本身而非我們環境的問題。
每一項都附了重現方式與定位到的程式碼位置。

## 1. `.gitattributes` 不完整，Windows 上 clone 後 cuebot 無法 build

**嚴重度**：中（擋住所有 Windows 開發者）

**現況**：repo 的 `.gitattributes` 只有一行：

```
*.sh text eol=lf
```

**問題**：Windows 使用者的 git 通常是 `core.autocrlf=true`，clone 後 Java 原始碼
變成 CRLF。cuebot 的 Gradle build 含 `spotless` 格式檢查，要求 LF，直接失敗：

```
Execution failed for task ':spotlessJavaCheck'.
> The following files had format violations:
      src/main/java/com/imageworks/common/spring/remoting/CueServerInterceptor.java
          -package com.imageworks.common.spring.remoting;\r\n
```

**誤導性**：失敗前會先噴一大串 `repo.spring.io` 的 HTTP 401，很容易被誤判成
網路或 repository 問題，但那些是雜訊。

**建議修法**：補上涵蓋原始碼的 `.gitattributes`，例如

```
* text=auto eol=lf
*.bat text eol=crlf
*.png binary
```

## 2. Sandbox 的 RQD 回報 IPv6 位址，導致 Cuebot 無法派發 frame

**嚴重度**：高（開箱即壞，sandbox 的預設設定無法完成任何 frame）

**重現**：照 `sandbox/README.md` 在 Linux（本例為 WSL2 Ubuntu 24.04）上
`docker compose up -d`，投任何 job。

**現象**：
- `cueadmin -lh` 看起來正常，host 狀態 UP
- 但 host 名稱是 IPv6 位址，例如 `fdc2:c6c:d60f:9::4`
- frame 永遠卡在 RUNNING，無 log、無子行程
- Cuebot log：`failed to obtain status for frame ...`

**根因**：`docker-compose.yml` 的 rqd 服務設定

```yaml
- OPENRQD__MACHINE__USE_IP_AS_HOSTNAME=true
```

RQD 挑到 IPv6 位址回報，但 openrqd 的 gRPC server 只聽 IPv4。
「RQD → Cuebot」通、「Cuebot → RQD」不通。

實測（從 cuebot 容器內）：

```
rqd:8444             → OK
fdc2:c6c:d60f:9::4:8444 → Connection refused
```

**建議修法**：sandbox 的預設值改為 `false`（Rust RQD 的原始碼預設本來就是
false，見 `rust/config/rqd.yaml` 的註解）。若要保留 IP 模式，需確保選出的是
gRPC server 實際綁定的位址家族。

## 3. RQD 無條件建立使用者，uid 衝突時整個 frame 失敗

**嚴重度**：高（任何投 job 者的 uid 撞到容器內既有 uid 就全掛）

**現象**：frame 回報 exit status 299（`EXIT_STATUS_FRAME_CLEARED`），
Cuebot log：

```
ABORTED: Not launching, user chordee(1000:0) could not be created.
× Failed to create user chordee: useradd: UID 1000 is not unique
```

**根因**：`rust/crates/rqd/src/frame/manager.rs:84-96`

只要 `run_frame.uid_optional` 有值，就無條件呼叫 `create_user_if_unexisting`，
**完全不看 `runner.run_as_user` 設定**（該設定預設為 false）。

而 `create_user_if_unexisting`（`rust/crates/rqd/src/system/linux.rs:921`）
只用**名稱**判斷存在與否，名稱不存在就 `useradd --uid <uid>`，
撞到既有 uid 就失敗。

sandbox 的 rqd 容器內 uid 1000 已被 `rqd` 使用者佔用，
而 Linux 桌面環境第一個使用者的 uid 慣例就是 1000 —— 衝突機率極高。

**建議修法**（擇一或併行）：
- 只在 `runner.run_as_user == true` 時才建立使用者
- uid 已被佔用時，退回使用 `default_uid` 並記一筆 warning，而不是 abort 整個 frame
- 至少讓錯誤訊息指出可以用 `run_as_user` 或 `default_uid` 解決

## 4. compose 檔裡的 macOS 專用路徑

**嚴重度**：低（不影響功能，但會在 Linux 宿主根目錄留下空目錄）

`docker-compose.yml` 的 rqd volumes 有：

```yaml
- /var/folders:/var/folders:ro
```

`/var/folders` 是 macOS 的暫存路徑。Linux 宿主上 Docker 會自動建一個
root-owned 空目錄掛進去。

**建議修法**：改成平台條件式，或至少加註解說明用途。

## 5. Windows 上的 RQD 相依套件沒有宣告

**嚴重度**：中（Windows 節點無法啟動，但錯誤訊息明確、容易自行解決）

**重現**：在 Windows 上 `pip install ./rqd` 後直接執行 `rqd`。

**現象**：

```
File "rqd/rqmachine.py", line 762, in __updateProcsMappingsFromWindows
    import wmi
ModuleNotFoundError: No module named 'wmi'
```

**根因**：`rqd/pyproject.toml` 的 `dependencies` 為

```toml
dependencies = [
    "opencue_proto",
    "psutil==5.9.8",
    "pynput==1.7.6",
    "future==1.0.0"
]
```

沒有任何 Windows 專用相依，但 `rqd/rqd/rqmachine.py:762` 在 Windows 路徑上
會 `import wmi`。

**建議修法**：加上環境標記條件式相依

```toml
dependencies = [
    "opencue_proto",
    "psutil==5.9.8",
    "pynput==1.7.6",
    "future==1.0.0",
    "wmi; sys_platform == 'win32'",
    "pywin32; sys_platform == 'win32'",
]
```

## 6. 文件缺少「Cuebot 需解析 render node 短名稱」的說明

**嚴重度**：低（文件問題，但會造成難以診斷的故障）

Cuebot 會把 RQD 回報的主機名稱截成第一個 label，並用該短名稱回連節點的 8444。
當 Cuebot 跑在容器內時，容器不一定繼承宿主的 DNS search domain，
短名稱可能解析不到。

症狀是 frame 卡在 RUNNING、無 log，而 `cueadmin -lh` 顯示一切正常 ——
非常難判斷。

**建議**：在部署文件補上驗證步驟

```bash
docker exec <cuebot容器> getent hosts <render節點短名稱>
docker exec <cuebot容器> bash -c 'timeout 3 bash -c "</dev/tcp/<節點>/8444" && echo OK'
```

## 7. `CUE_FRAME_LOG_DIR` 的預設值對 Windows 節點無效且不會報錯

**嚴重度**：中（安靜失效，log 寫到非預期位置）

sandbox 預設 `CUE_FRAME_LOG_DIR=/tmp/rqd/logs`。Windows 上的 RQD 收到這個路徑，
Python 會解析成「相對於當前磁碟機」的絕對路徑，例如從 `D:\` 啟動就寫到
`D:\tmp\rqd\logs`。

**不會報錯**，但 Cuebot 與 CueWeb 記錄的路徑仍是 `/tmp/rqd/logs/...`，兩邊對不上。

frame log 內甚至出現混合分隔符：

```
logDestination  /tmp/rqd/logs/.../<job>--<id>\<job>.<frame>.rqlog
```

**建議**：跨平台農場的部署文件應明確要求把這個值設為所有節點一致的共享路徑，
或在 RQD 端偵測到非本平台路徑時給出警告。

## 8. Windows 節點若未編譯 winps，完全不回報 frame 記憶體用量

**嚴重度**：中（安靜失效；依記憶體判斷的機制在 Windows 節點上形同無效）

**根因**：`rqd/rqd/rqmachine.py:315-322`

```python
def rssUpdate(self, frames):
    if platform.system() == 'Windows' and winpsIsAvailable:
        self.rssUpdateWindows(frames)
        return
    if platform.system() != 'Linux':
        return
```

`winps` 是 `rqd/winps/` 下的 C++ 擴充，**不在 `pip install ./rqd` 的安裝範圍內**，
需要自行編譯並具備 MSVC。沒有它時 `int_mem_max_used` 恆為 0，
而且沒有任何警告。

**建議修法**（擇一）：
- 把 winps 納入 Windows 的建置/安裝流程，或提供預編譯 wheel
- 啟動時偵測到 Windows 且 `winpsIsAvailable == False` 就記一筆明確的 warning
- 在 Windows 部署文件中明確說明這一步

補充：`rqd/winps/setup.py` 使用 `from distutils.core import setup`，
而 `distutils` 已於 Python 3.12 自標準庫移除（目前靠 setuptools 的相容層運作）。
長期而言建議改用 setuptools。

## 9. Windows 上 frame 的工作目錄沒有生效

**嚴重度**：中（依相對路徑的算圖工作會失敗；多 frame 可能共用目錄互相覆寫）

**現象**：frame log 的 JobSpec 宣告

```
cwd  C:\Users\<user>\AppData\Local\Temp/<job>/<frame>
```

但 frame 行程內 `os.getcwd()` 得到的是 **RQD 行程自己的工作目錄**。

**重現**：以不同工作目錄啟動 RQD，frame 的 cwd 完全跟著變：

| RQD 的工作目錄 | frame 實際 cwd |
|---|---|
| `D:\dev\OpenCue` | `D:\dev\OpenCue` |
| `C:\opencue` | `C:\opencue` |

**根因（已定位到確切程式碼）**：`rqd/rqd/rqcore.py` 的三個平台分支，
只有 Windows 那支漏傳 `cwd` 參數給 `subprocess.Popen`。

| 方法 | 行號 | `cwd` 參數 |
|---|---|---|
| `runLinux` | 1038 | `cwd=self.rqCore.machine.getTempPath()` |
| `runDarwin` | 1428 | `cwd=self.rqCore.machine.getTempPath()` |
| `runWindows` | 1364 | **沒有這個參數** |

```python
# runWindows (L1364)
frameInfo.forkedCommand = subprocess.Popen(tempCommand,
                                           env=self.frameEnv,
                                           stdin=subprocess.PIPE,
                                           stdout=subprocess.PIPE,
                                           stderr=subprocess.STDOUT)
```

依 Python `subprocess` 規格，未指定 `cwd` 即為 `None`，子行程直接繼承
父行程（RQD 本身）的工作目錄 —— 與實測完全吻合。

**建議修法**：在 `runWindows` 的 `Popen` 補上
`cwd=self.rqCore.machine.getTempPath()`，與另外兩個平台一致。

**影響**：使用相對路徑的場景檔、暫存輸出會落在非預期位置；
同時執行的多個 frame 共用同一目錄有覆寫風險。

## 10. CueNIMBY 在全新的 Windows 機器上會因建立設定目錄失敗而無法啟動

**嚴重度**：中（每一台全新的 Windows 工作站都會遇到）

**根因**：`cuenimby/cuenimby/config.py:59-61`

```python
config_dir = Path.home() / ".config/opencue"
config_dir.mkdir(exist_ok=True)
```

`mkdir()` 沒有帶 `parents=True`。Linux/macOS 上 `~/.config` 通常已存在，
但 Windows 沒有這個慣例，全新機器上不會有。

**實測**（Windows，Python 3.11.9）：

```python
target = pathlib.Path(tempfile.mkdtemp()) / '.config/opencue'
target.mkdir(exist_ok=True)
# → FileNotFoundError: [WinError 3] The system cannot find the path specified
```

本次測試機器剛好已有 `~/.config`（其他工具建立的），所以沒觸發。

**建議修法**：

```python
config_dir.mkdir(parents=True, exist_ok=True)
```

## 11. 文件未說明「host 需帶 general 標籤才收得到預設 job」

**嚴重度**：中（失敗時完全無提示，極難排查）

把 host 移進 `local.desktop` allocation 後，它不再帶 `general` 標籤；
而 pyoutline 送出的 job，其 layer 預設 tags 是 `general | util`。
兩者對不上 → 該 host 永遠不會被派工。

**症狀**：`cueadmin -lh` 顯示 host `UP` / `OPEN`，job 顯示 `PENDING`，
frame 停在 `WAITING`，**沒有任何錯誤訊息**。

**排查方式**（值得寫進文件）：

```sql
SELECT str_name, str_tags FROM layer;
SELECT ht.str_tag, ht.str_tag_type FROM host h JOIN host_tag ht ON h.pk_host=ht.pk_host;
```

**解法**：RQD 設定加 `RQD_TAGS = general`，或投 job 時指定對應標籤。

**建議**：在 allocation / tag 的文件中明確說明這個匹配關係，
並在「把 host 移到其他 allocation」的說明旁加註警告。

## 12. CueNIMBY 的排程無法處理跨午夜時段，且失效方向可能與意圖相反

**嚴重度**：高（靜默失效，且可能在「明確要求不要借用」的時段反而開放機器）

**根因**：`cuenimby/cuenimby/scheduler.py:78-87`

```python
current_time = datetime.now().time()
start_time = self._parse_time(day_schedule["start"])
end_time = self._parse_time(day_schedule["end"])
desired_state = day_schedule["state"]

if start_time <= current_time <= end_time:
    return desired_state

# Outside scheduled period - return opposite state
return "available" if desired_state == "disabled" else "disabled"
```

當時段跨越午夜時 `start > end`，`start <= now <= end` **永遠不成立**，
於是無論何時都走到最後一行回傳相反狀態 —— 該時段設定形同完全反向。

**實測**（以 mock 注入時間，直接呼叫真實的 `_check_schedule()`）：

情境 A — 不跨午夜（`09:00-18:00 disabled`）：全部正確

| 時間 | 預期 | 實際 |
|---|---|---|
| 10:00 | disabled | disabled |
| 20:00 | available | available |

情境 B — 跨午夜，以開放時段表達（`18:00-09:00 available`）：

| 時間 | 預期 | 實際 |
|---|---|---|
| 20:00 | available | **disabled** |
| 02:00 | available | **disabled** |
| 23:00 | available | **disabled** |
| 12:00 | disabled | disabled |

→ 結果是機器**永遠不會被借用**，農場靜默地少了一批算力。

情境 C — 跨午夜，以封鎖時段表達（`22:00-06:00 disabled`）：

| 時間 | 預期 | 實際 |
|---|---|---|
| 23:00 | disabled | **available** |
| 03:00 | disabled | **available** |
| 14:00 | available | available |

→ 結果是在**明確要求不要借用的時段反而開放機器**。這個方向更危險。

**建議修法**：

```python
if start_time <= end_time:
    in_window = start_time <= current_time <= end_time
else:  # 跨午夜
    in_window = current_time >= start_time or current_time <= end_time

if in_window:
    return desired_state
return "available" if desired_state == "disabled" else "disabled"
```

**附帶問題**：即使修好時間比較，仍有「日期歸屬」的問題。
`_get_current_schedule()` 用 `datetime.now().strftime("%A")` 取**當天**的設定，
但跨午夜的時段（例如星期五 18:00 到星期六 09:00）在凌晨時會被當成星期六來查。
若星期六沒有設定，就直接回傳 None 不做動作。
完整修正需要一併處理跨日的歸屬。

**迴避方式**：用不跨午夜的「封鎖時段」來表達需求。
例如「下班後才借用」寫成 `09:00-18:00 disabled` 而非 `18:00-09:00 available`，
利用「時段外自動取相反狀態」的特性達到相同效果。

## 13. compose 宣告的 CueWeb / REST Gateway image 並未發布

**嚴重度**：中（`cueweb` profile 無法在不自行 build 的情況下使用）

`docker-compose.yml` 對這兩個服務同時宣告了 `image:` 與 `build:`：

```yaml
rest-gateway:
  image: opencue/rest-gateway:latest
  build:
    context: ./
    dockerfile: rest_gateway/Dockerfile

cueweb:
  image: opencue/cueweb:latest
  build:
    context: ./cueweb
```

但這兩個 repository **在 Docker Hub 上不存在**：

```
opencue/cuebot        -> HTTP 200
opencue/rqd           -> HTTP 200
opencue/cueweb        -> HTTP 404
opencue/rest-gateway  -> HTTP 404
```

```
docker pull opencue/cueweb:latest
Error response from daemon: pull access denied for opencue/cueweb,
repository does not exist or may require 'docker login'
```

也查過 `opencuebuild/`、`academysoftwarefoundation/`、`aswf/` 等組織，皆無。

**影響**：任何想用 `--profile cueweb` 的人，若環境無法 build（例如只有
Portainer 而沒有 build context），會直接失敗，且錯誤訊息指向「權限不足或需要
docker login」，容易誤判成自己的帳號問題。

**建議**：要嘛把 image 發布到 Docker Hub，要嘛移除 `image:` 那行只保留
`build:`，讓意圖明確。

## 15. Rust RQD 的清單型設定無法用環境變數指定

**嚴重度**：中（容器化部署時，tag 這類設定被迫改用設定檔）

**重現**：

```bash
docker run -e "OPENRQD__MACHINE__CUSTOM_TAGS=general,houdini21" opencue-rqd
```

```
thread 'main' panicked at crates/rqd/src/config/mod.rs:33:52:
invalid type: string "general,houdini21", expected a sequence
```

**根因**：`rust/crates/rqd/src/config/mod.rs:636-639`

```rust
Environment::with_prefix("OPENRQD")
    .separator("__")
    .list_separator(","),
```

有設 `list_separator`，但**沒有用 `with_list_parse_key` 指定哪些 key
要當清單解析**，所以 `Vec<String>` 型別的欄位無法從環境變數讀入。

受影響的欄位至少有 `machine.custom_tags`（`config/mod.rs:126`）。

**影響**：容器化部署時，環境變數是最自然的設定方式，
但 tag 這種每台機器都不同的設定被迫改用掛載設定檔，增加部署複雜度。

**建議修法**：對清單型欄位加上 `with_list_parse_key`，例如

```rust
Environment::with_prefix("OPENRQD")
    .separator("__")
    .list_separator(",")
    .with_list_parse_key("machine.custom_tags")
    .try_parsing(true),
```

**迴避方式**：用設定檔並以 `OPENCUE_RQD_CONFIG` 指向它
（`config/mod.rs:622`）。

## 16. 文件未說明 tag 比對是 regex 的「或」

**嚴重度**：中（會讓版本綁定形同虛設，且不易察覺）

`DispatchQuery.java:296`：

```sql
AND host.str_tags ~* ('(?x)' || layer.str_tags || '\y')
```

layer 的多個 tag 以 ` | ` 串接後**直接當成 PostgreSQL 的 regex pattern**，
而 `|` 是 regex 的「或」。因此 layer 指定多個 tag 的語意是
**「任一符合即可」**，不是直覺上的「全部符合」。

實測：一個 tag 為 `general | houdini_22_0_429` 的 job，
會被派到只有 `general` 而沒有 Houdini 22 的節點上。

**影響**：想用 tag 綁定 DCC 版本的人，很自然會寫成
`tags=["general", "houdini_22_0_429"]`（表示「在派工池裡、而且有這個版本」），
結果版本條件完全失效，job 被派到跑不動的機器上。

**另外兩個衍生問題**：

1. tag 內容會被當成 regex，含 `.` `*` `+` 等字元會有非預期比對
2. `DispatchQuery.java:296` 沒有附加單字邊界 `\y`，
   而同檔案的 363、555、642 行有。可能造成子字串誤配

**建議**：在 tag 與 allocation 的文件中明確說明比對語意，
並提醒 tag 命名避開 regex 特殊字元。

## 17. 兩種 RQD 的預設 facility 都是 cloud，與用戶端預設不一致

**嚴重度**：中（新節點預設收不到任何工作，且無錯誤訊息）

| 元件 | 預設 facility | 位置 |
|---|---|---|
| Rust RQD | `cloud` | `rust/crates/rqd/src/config/mod.rs:162` |
| Python RQD | `cloud` | `rqd/rqd/rqconstants.py:44` |
| pycue（投 job 端） | **`local`** | `pycue/opencue/default.yaml` 的 `cuebot.facility_default` |

**結果**：一台全新的 render node 註冊後會落在 `cloud.general`，
而用戶端投出來的 job 是 `local` facility ——
**兩邊對不上，該節點永遠收不到工作**。

**症狀難以診斷**：host 顯示 `UP` / `OPEN`，job 顯示 `PENDING`，
frame 停在 `WAITING`，沒有任何錯誤訊息，且與「tag 不匹配」的症狀完全相同。

**建議**：
- 讓 RQD 與 pycue 的預設值一致，或
- 在 sandbox 文件中明確說明這個落差與 `cueadmin -force -move` 的用法，或
- Cuebot 在偵測到「有 job 待派、且存在 tag 相符但 facility 不同的閒置節點」時
  記錄一筆 warning

## 18. Python RQD 讀取 rqd.conf 時沒有指定編碼

**嚴重度**：中（設定檔含非 ASCII 字元時，在非 UTF-8 系統上 RQD 啟動即崩潰）

`rqd/rqd/rqconstants.py` 以 `config.read(CONFIG_FILE)` 讀檔，沒有傳 `encoding`，
Python 會使用系統的 ANSI 代碼頁。

- 繁體中文 Windows 的 ANSI 代碼頁是 cp950
- 設定檔只要有一個 UTF-8 的中文字（即使只在註解裡），解碼就會失敗：

  ```
  UnicodeDecodeError: 'cp950' codec can't decode byte 0xae in position 18: illegal multibyte sequence
  ```

對照同一個 repo 的其他元件，**都有明確指定 UTF-8**：

| 元件 | 讀檔方式 |
|---|---|
| pycue | `open(..., encoding="utf-8")`（`pycue/opencue/config.py:73, 93`） |
| CueNIMBY | `open(..., encoding='utf-8')`（`cuenimby/cuenimby/config.py:31, 70`） |
| **RQD** | `config.read(CONFIG_FILE)`，**未指定** |

本機 sandbox 沒有踩到，是因為這台 Windows 剛好啟用了
「使用 Unicode UTF-8 提供全球語言支援」（ACP = 65001）。
以 cp950 解碼同一份檔案的實測結果如上。

**建議修法**：

```python
config.read(CONFIG_FILE, encoding="utf-8")
```

## 20. RQD 的 Loki 相依只列在測試相依中

**嚴重度**：中（啟用 Loki 後，一般安裝的 RQD 無法正常記錄 frame log）

`rqd/pyproject.toml` 把 `loki-urllib3-client` 放在 `[project.optional-dependencies]` 的 `test` 裡。
一般 `pip install ./rqd` 不會安裝。

`rqd/rqlogging.py:124-130` 的 `LokiLogger.__init__` 遇到 ImportError 時**直接 return**，
沒有記錄錯誤，物件處於未初始化的狀態，之後使用 `self.client` 會出錯。

**建議**：新增一個 `loki` 選用相依群組（`pip install ./rqd[loki]`），
並在 ImportError 時明確記錄錯誤或丟出例外。

## 21. pyoutline 把串列指令用空白接起來，不加引號

**嚴重度**：中（Windows 上路徑含空白是常態，例如 `C:\Program Files`）

`pyoutline/outline/backend/cue.py:325`：

```python
sub_element(spec_layer, "cmd", " ".join(cmd))
```

串列中含空白的元素會失去邊界。實測 `D:/programs/Side Effects Software/.../hython.exe`
在 Windows 節點上執行時被切成 `D:/programs/Side`，frame 立即 DEAD（見 `17` 場景 24）。

CueSubmit 的問題更直接：`cuesubmit/Submission.py` 先組成字串再 `command.split()`，
連使用者自己加的引號都救不了。

**建議修法**：Windows 目標用 `subprocess.list2cmdline(cmd)`，POSIX 目標用 `shlex.join(cmd)`；
CueSubmit 直接組成串列，不要先組字串再切開。

## 22. CueSubmit 的 Maya 相機選擇會送出錯誤的 `-cam`

**嚴重度**：高（沒選相機就送出時，所有 frame 失敗）

`cuesubmit/ui/SettingsWidgets.py` 的 `InMayaSettings.getCommandData()` 回傳
`self.cameraSelector.text()`，也就是選單按鈕上的文字：

| 選擇 | 按鈕文字 | 送出的指令 |
|---|---|---|
| 沒選 | `[None]` | `-cam [None]` → Maya：`Camera [None] does not exist`，exit 210 |
| 選兩台 | `a, b` | `-cam a, b` → 被 `split()` 切開，無法解析 |

`Submission.buildMayaCmd()` 只檢查 `if camera:`，`[None]` 是非空字串，所以一定會帶上 `-cam`。

**建議修法**：改用 `getChecked()`；沒選時不帶 `-cam`；相機選單改為單選，
或在多選時為每台相機各建一個 layer。
