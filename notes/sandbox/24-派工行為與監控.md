## 一、工作站與專職機同時在線

### 1. 同一個 job 會分到兩種節點

指令用 `hostname`（兩種平台都有），不指定 OS。

**40 個 frame**：全部跑在 render02，LAPTOP 一個都沒拿到。整個 job 只跑了 36 秒。

**500 個 frame**：

| 節點 | frame 數 | 每個 frame 平均耗時 |
|---|---|---|
| render02 | 393 | 5.96 秒 |
| LAPTOP | 107 | 約 1.4 秒 |

LAPTOP 接工作的時間分布：

```
06:35:13  投遞
06:36:59  LAPTOP 第一次接到工作（投遞後約 1 分 45 秒）
06:36:59～06:37:10  連續跑了 83 個
06:37:30  8 個
06:37:49  14 個
06:39:20  2 個
```

觀察：

- render02 投遞後立刻開始；LAPTOP 延遲約 1 分 45 秒才第一次接工作
- 之後是**一陣一陣**的：一次接一批，然後停一段時間
- frame 完成時，Cuebot 會直接把下一個 frame 派給同一台節點；
  其他節點要等下一次定期回報才有機會接工作。40 個 frame 的 job 在 LAPTOP 輪到之前就結束了

**限制**：`hostname` 每個 frame 只跑 1～6 秒，和真實算圖（數分鐘到數小時）差距很大。
這個結果只能說明「兩種節點都會接到同一個 job 的工作」，**不能推論真實算圖的分配比例**。
frame 很長時，每台節點跑完一個就接下一個，分配應該會接近核心數的比例。

同樣的 `hostname`，Windows 原生 RQD 約 1.4 秒、Linux 容器的 Rust RQD 約 6 秒，
後者每個 frame 的固定開銷較大（原因未量測；Rust RQD 每個 frame 都會執行建立使用者的步驟，
見 [`04` 坑 #4](04-部署過程.md#坑-4rqd-建立使用者失敗uid-衝突)，可能是原因之一）。

### 2. 工作站在算圖中途被鎖住（早上上班的情境）

CueNIMBY 上鎖呼叫的是 `host.lock()`（`cuenimby/monitor.py:271`），
與手動鎖定相同。以 `host.lock()` 模擬：

```
06:45:31  frame 開始（ping -n 121，約 2 分鐘）
06:45:35  鎖定 LAPTOP → LOCKED
          另外投遞一個新的 Windows frame
06:47:33  第一個 frame 跑完，SUCCEEDED、exit 0
          新的 frame 一直是 WAITING
06:47:44  解鎖
06:48:03  新的 frame 被接走並完成（解鎖後 19 秒）
```

**鎖定不會中斷正在跑的 frame**，只是不再派新的工作過來。
早上 CueNIMBY 上鎖時，若工作站上有一個要跑好幾小時的 frame，會一直跑到結束。

### 3. 鎖定＋砍掉正在跑的 frame

```python
host = opencue.api.findHost("LAPTOP-ULJICLO8")
host.lock()
for proc in opencue.api.getProcs(host=["LAPTOP-ULJICLO8"]):
    proc.kill()
```

結果：

- Windows 上的程序確實被終止（`ping.exe` 數量 0）
- frame **回到 WAITING**，exit status 記為 1，**重試次數沒有增加**（不算失敗）
- 會由下一台可用的節點**從頭**重跑，已經跑的進度作廢

### 決定

**上班時的鎖定不自動砍 frame。** 需要時由人手動取消工作站上正在跑的 frame
（第 3 節的做法，或在 CueGUI 對該 frame 執行 kill）。
正式做法整理在 [`notes/deploy/03-工作站.md`](../deploy/03-工作站.md)。

## 二、大量 frame

500 個 frame，每個 1 核：

| 項目 | 結果 |
|---|---|
| 總耗時 | 約 4.5 分鐘（06:35:13 → 06:39:41） |
| 結果 | 500 個全部 SUCCEEDED，**0 個 DEAD** |
| Cuebot 記憶體 | 683 MiB（先前實測峰值 555 MiB） |
| DB 記憶體 | 127 MiB |
| 投遞耗時 | 約 1 秒 |

本機兩個節點合計 16 核，吞吐量約每秒 1.85 個 frame。
正式環境的瓶頸會是算圖本身，而不是 Cuebot 的派工速度。

## 三、Portainer Git 模式：修改 yml 只重建該服務

補完 [`23`](23-Portainer的Git模式.md) 最後一項未測的行為。commit `20338f8e` 只修改了 Cuebot 的啟動參數
（新增 `--metrics.prometheus.collector=${CUEBOT_METRICS_COLLECTOR:-false}`），
推進 `studio/release` 後：

| 容器 | 之前 | 之後 |
|---|---|---|
| db | 05:40:49 | 05:40:49 |
| cuebot | 05:41:03 | **07:00:30** |
| rest-gateway | 05:41:14 | 05:41:14 |
| cueweb | 05:41:20 | 05:41:20 |
| init | 06:14:31 | 07:00:45 |

**只有 Cuebot 被重建**（init 是一次性容器，每次都會跑）。
rest-gateway 設定了 `depends_on: cuebot`，但沒有被連帶重建。

### 修改環境變數要手動重新部署

Git 模式下，環境變數存在 Portainer，不在 git。
把 `CUEBOT_METRICS_COLLECTOR` 設為 `true` 後，要按 **Pull and redeploy** 才會套用，
而手動重新部署會**重建所有容器**（實測 58 秒，db、cuebot、rest-gateway、cueweb 全部重啟）。

另一個 stack 透過 external network 接在 `opencue` 上（第四節的監控 stack），
opencue stack 全部重建後**連線不受影響**，network 沒有被重建。

## 四、監控：Prometheus + Grafana

### Cuebot 的指標

`/metrics`（port 8080，只在容器網路內）**預設就有**：

```
cue_frames_completed_total      cue_jobs_completed_total
cue_host_reports_received_total cue_job_core_seconds
cue_layer_max_memory_bytes      cue_layer_max_runtime_seconds
cue_booking_durations_*         cue_find_jobs_by_show_count_total
```

`metrics.prometheus.collector=true` 之後才多出排程佇列的健康指標
（booking / dispatch / manage / report 四個佇列的等待數、執行緒數、被拒絕數），
以及 `cue_cores_idle`、`cue_cores_total` 等。

注意 label 名稱不一致：基本指標用 `cuebot_host`，佇列指標用 `cuebot_hosts`（複數）。

### 部署方式：inline configs

上游 `docker-compose.yml` 的 monitoring profile 用 bind mount 掛 repo 裡的設定檔，
**Portainer 的 Web editor 沒辦法用**。改用 compose 的 inline `configs`：

```yaml
configs:
  prometheus_config:
    content: |
      scrape_configs:
        - job_name: cuebot
          static_configs: [{targets: ['cuebot:8080']}]
```

以 Portainer API 部署（`POST /api/stacks/create/standalone/string`）**成功**，
Prometheus 與 Grafana 都正確讀到設定。結果整理為 [`notes/deploy/server/monitoring.portainer.yml`](../deploy/server/monitoring.portainer.yml)。

### 資源用量

| 容器 | 記憶體 | CPU |
|---|---|---|
| prometheus | 26 MiB | ~0% |
| grafana | 94 MiB | 0.4% |
| db-exporter | 8 MiB | ~0% |

image 合計約 1.5 GB（grafana 995 MB、prometheus 503 MB、exporter 36 MB）。

### 上游的 Grafana 儀表板

| 儀表板 | 結果 |
|---|---|
| `PostgreSQL.json` | **可直接使用** |
| `cuebot.json` | **大部分無法使用** |

`cuebot.json` 最後一次修改是 2021 年（`d84a10ff`）。它引用 27 個指標：

- **9 個在目前的 Cuebot 原始碼中已經不存在**：
  `cue_booked_procs`、`cue_booking_errors`、`cue_booking_retries`、`cue_cleared_procs`、
  `cue_host_balance_failed`、`cue_host_balance_success`、`cue_killed_offender_procs`、
  `cue_killed_oom_procs`、`cue_req_errors`
- 其餘 18 個存在，但都是 **gauge**，儀表板卻套用 `rate()`（給 counter 用的），數值沒有意義

collector 關閉時 29 個查詢全部沒有資料；開啟後也只有 4 個有資料。
要監控 Cuebot，需要自己做儀表板。見 [`05` 第 19 項](05-可回饋上游的問題.md#19-上游的-cuebot-grafana-儀表板已經過時)。
