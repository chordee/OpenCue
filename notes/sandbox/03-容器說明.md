# 03 — Stack 各容器說明

以 repo 根目錄的 `docker-compose.yml` 為準。共 16 個 service，用 profile 分組，
預設只起 4 個。

## Profile 分組

| Profile | 包含的 service | 起法 |
|---|---|---|
| （預設） | `db` `flyway` `cuebot` `rqd` | `docker compose up -d` |
| `cueweb` | `rest-gateway` `cueweb` | `docker compose --profile cueweb up -d` |
| `monitoring` | `db-exporter` `prometheus` `grafana` `loki` | `--profile monitoring` |
| `monitoring-full` | `zookeeper` `kafka` `kafka-ui` `elasticsearch` `kibana` `monitoring-indexer` | `--profile monitoring-full` |
| `all` | 全部 | `--profile all` |

---

## 核心四件（預設啟動）

### `db` — PostgreSQL 資料庫

| 項目 | 值 |
|---|---|
| Image | `postgres:15.1`（官方 image，不需 build） |
| Port | `5432:5432` |
| Volume | `db-data`（named volume） |
| 帳密 | `cuebot` / `cuebot_password`（寫死在 compose） |

**角色**：OpenCue 的唯一真實來源。show、job、layer、frame、host、allocation、
subscription、filter 全部狀態都在這裡。Cuebot 本身是無狀態的，重啟不掉資料；
這個 DB 掉了才是真的掉。

**正式環境**：
- 不要 publish 5432（宿主可能已有別的 postgres 佔 port，而且沒必要對外）
- 密碼移到 `.env` 或 secrets（注意密碼在 compose 裡出現兩次：`db` 的環境變數、
  以及 `cuebot` 的 `command:` 參數，改一處會不同步）
- `db-data` volume 要納入備份

### `flyway` — 資料庫 schema migration

| 項目 | 值 |
|---|---|
| Build | `sandbox/flyway.Dockerfile`（基底 `almalinux:9` + Flyway 9.11.0） |
| Port | 無 |
| 生命週期 | **跑完就結束**（one-shot，不是常駐服務） |

**角色**：把 `cuebot/src/main/resources/conf/ddl/postgres/migrations` 底下的
SQL 依序套到空資料庫，再灌 `seed_data.sql`。`cuebot` 的 `depends_on` 設了
`condition: service_completed_successfully`，也就是**必須等 flyway 成功跑完
Cuebot 才會啟動**。

看到 `flyway` 容器 Exited (0) 是**正常的**，不是故障。

**正式環境**：
- migration SQL 是**build 進 image 的**（`COPY` 進去），所以升級 OpenCue 版本時
  必須重建這個 image，不能只換 Cuebot
- Portainer-only 的情況下，這個 image 一定要預先建好推 registry

### `cuebot` — 排程器（農場大腦）

| 項目 | 值 |
|---|---|
| Build | `cuebot/Dockerfile`（Gradle 編 Java / Spring Boot） |
| 現成 image | `opencue/cuebot`（compose 裡被註解掉） |
| Port | `8443:8443`（gRPC），`8080` 指標端點預設註解掉 |
| 環境 | `CUE_FRAME_LOG_DIR=/tmp/rqd/logs` |
| depends_on | `db` healthy + `flyway` 成功結束 |

**角色**：
- 接受 client（cueadmin / cuesubmit / pyoutline / REST Gateway）的 gRPC 請求
- 維護 job / frame 狀態機
- 決定「哪個 frame 派給哪台 RQD」—— 也就是 dispatch
- 接收 RQD 回報的 frame 完成 / 失敗 / 資源使用量

**這是整個農場唯一不能掛的服務**。它停了，所有 RQD 會閒置、所有 UI 斷線。

**正式環境**：
- 改用 registry 的 `image:` + 明確 tag（不要 `latest`）
- `8443` 必須對外，Windows render node 要連
- `CUE_FRAME_LOG_DIR` 需實測，見 `02-目標架構.md` 的「待驗證」一節
- 考慮開 `8080` 給 Prometheus 抓指標（需同時改 `command:` 加
  `--metrics.prometheus.collector=true`）

### `rqd` — 算圖節點 daemon

| 項目 | 值 |
|---|---|
| Build | `rust/Dockerfile.rqd`（**Rust 版 RQD**，不是 Python 版） |
| Port | `8444:8444` |
| 環境 | `OPENRQD__GRPC__CUEBOT_ENDPOINTS=cuebot:8443`、`OPENRQD__MACHINE__USE_IP_AS_HOSTNAME=true` |
| Volume | `/tmp/rqd/logs`、`/tmp/rqd/shots`、`${HOME}/.opencue/sessions`、`/tmp/opencue`、`/var/folders`(ro) |

**角色**：假裝自己是一台 render node。開機時向 Cuebot 註冊（回報 CPU 數、記憶體），
之後接收派來的 frame、執行指令、把 stdout/stderr 寫成 frame log、回報結果。

**這個容器裡沒有任何算圖軟體** —— 沒有 Blender、Maya、Nuke。所以 sandbox 的 demo job
都是 `/bin/sleep N` 這類假指令，驗證的是排程與狀態流轉，不是真的算圖。

**正式環境：這個 service 要從 stack 刪掉。**
compose 裡的註解自己就寫了「In a production environment, this should be disabled
from the stack and only run on render hosts」。我們的宿主不算圖，render node 是
Windows 機器，各自裝原生 RQD。

## CueWeb profile（網頁 UI）

### `rest-gateway` — gRPC 轉 HTTP

| 項目 | 值 |
|---|---|
| Image | `opencue/rest-gateway:latest`（也有 build 定義） |
| Port | `8448:8448` |
| 環境 | `CUEBOT_ENDPOINT=cuebot:8443`、`JWT_SECRET=${JWT_SECRET:-opencue-dev-jwt-secret-change-in-production}` |

**角色**：Cuebot 只講 gRPC，瀏覽器不會講。這個 gateway 把 gRPC 介面包成 HTTP/JSON，
CueWeb 透過它存取。用 JWT 做認證。

**正式環境**：`JWT_SECRET` 的預設值字面上就寫著 `change-in-production`，必須換掉。

### `cueweb` — 網頁版 UI

| 項目 | 值 |
|---|---|
| Image | `opencue/cueweb:latest` |
| Port | `3000:3000` |
| 技術 | Next.js |

**角色**：瀏覽器版的 job 監控與管理，功能對應桌面版 CueGUI 的一部分。

**正式環境的坑**：Next.js 的 `NEXT_PUBLIC_*` 變數在 **build 時就烘進 image**。
若 image 裡烘的是 `http://localhost:8448`，部署到別台機器就會 `ECONNREFUSED
/api/job/getjobs`。compose 檔頭的註解有寫這個問題與解法（用正確的 build arg 重建）。
**這點在 Portainer 上特別容易踩到**，因為 Portainer 的操作習慣是改環境變數，
但這裡改環境變數沒用。

## monitoring-full profile（事件串流與歷史查詢）

| Service | Image | Port | 角色 |
|---|---|---|---|
| `zookeeper` | `cp-zookeeper:7.7.7` | 2181 | Kafka 的協調服務 |
| `kafka` | `cp-kafka:7.7.7` | 9092 / 29092 | 事件串流。Cuebot 要另外打開 Kafka 設定才會發事件 |
| `kafka-ui` | `provectuslabs/kafka-ui` | 8090→8080 | Kafka 的網頁管理介面 |
| `elasticsearch` | `elasticsearch:9.3.0` | 9200 / 9300 | 事件的長期儲存與搜尋 |
| `kibana` | `kibana:9.3.0` | 5601 | Elasticsearch 的查詢介面 |
| `monitoring-indexer` | build 自 `rust/Dockerfile.monitoring-indexer` | 無 | 從 Kafka 讀事件寫進 Elasticsearch |

**注意**：Cuebot **預設不發 Kafka 事件**。要啟用得改 `cuebot` 的 `command:`
（compose 裡有註解好的替代版本），加上 `--monitoring.kafka.enabled=true`。
只把這個 profile 起來、沒改 Cuebot 設定的話，Kafka 裡不會有東西。

這組很吃資源（Elasticsearch 本身就是記憶體大戶），在「宿主要跑很多服務」的前提下
要謹慎評估。

## 正式環境建議的最小組合

以「Linux 宿主不算圖、Windows 當 render node、宿主還有其他服務」為前提：

```
必要：db, flyway, cuebot
建議：rest-gateway, cueweb   （要有網頁 UI 的話）
不要：rqd                     （宿主不算圖）
後續再評估：monitoring 那組    （吃資源）
```

## 容器進出與修改時機指南（維運與除錯手冊）

實作人員在維運 Docker Stack 時，經常面臨「遇到問題到底要不要進容器？進去該改什麼？」的疑惑。以下整理具體的黃金準則：

### 1. 鐵律：何時「絕對不要」在容器內做修改？

> **容器是「可拋棄的（Stateless）」，容器內的直接變更在重啟或更新時會被全數抹平。**

- **絕對不要進入容器修改設定檔**：例如不要進 `opencue-cuebot` 編輯 Spring properties，不要進 `opencue-cueweb` 改 Next.js 設定。
  - **後果**：只要 Portainer 重新部署、更新 Image Tag 或容器當機重啟，你在容器內修改的檔案會被全新映像檔直接覆蓋。
  - **正確做法**：所有參數調整一律透過 `notes/sandbox/stack/env.example`（Portainer Stack 環境變數）或修訂 `opencue.portainer.yml` 來生效。
- **絕對不要在容器內編譯或安裝相依軟體**：例如不要進 `opencue-cuebot` 跑 Gradle，或進 `opencue-cueweb` 跑 `npm install`。
  - **正確做法**：在獨立的建置機器完成 `docker build` 並推送到 Registry，再由 Portainer 拉取部署（見 `14-Registry流程.md`）。

---

### 2. 時機：何時「必須 / 建議」進容器？（`docker exec` 排查情境）

只有在**「排查現場狀況、提取診斷資訊、或執行單次資料庫管理命令」**時，才需要 `docker exec`：

#### 情境 A：排查網路與 DNS 短名稱反查（進入 `cuebot` 容器）
當 Frame 卡在 `RUNNING` 且無 Log 時，通常是 Cuebot 無法解析 Windows 節點名稱：
```bash
# 1. 檢查容器內是否能解析 Windows 節點短名稱
docker exec opencue-cuebot getent hosts <Windows節點短名稱>

# 2. 測試 Cuebot 能否主動打通節點的 8444 gRPC Port
docker exec opencue-cuebot bash -c 'timeout 3 bash -c "</dev/tcp/<Windows節點短名稱>/8444" && echo 通 || echo 阻擋'
```

#### 情境 B：排查掛載點是否為空目錄（進入 `cueweb` 容器）
當網頁端讀取 Log 或圖片預覽報錯時，確認共享儲存是否真有掛載成功：
```bash
# 檢查容器內的掛載路徑，確認能看到真實的 show/shot/logs 目錄而非空目錄
docker exec opencue-cueweb ls -la /mnt/logs
docker exec opencue-cueweb ls -la /mnt/render
```

#### 情境 C：資料庫底層狀態檢驗與手動維護（進入 `db` 容器）
當排程卡住懷疑 Tag 不匹配，或需要手動備份時：
```bash
# 1. 查詢特定主機的所有硬體與 Allocation 標籤
docker exec -it opencue-db psql -U cuebot -c "
SELECT h.str_name, ht.str_tag, ht.str_tag_type 
FROM host h JOIN host_tag ht ON h.pk_host=ht.pk_host 
WHERE h.str_name='<節點名稱>';"

# 2. 查詢當前等待中 Layer 所要求的標籤
#    注意：layer 表沒有 str_state 欄位，狀態在 job 表，必須 JOIN
docker exec -it opencue-db psql -U cuebot -c "
SELECT l.str_name, l.str_tags
FROM layer l JOIN job j ON l.pk_job = j.pk_job
WHERE j.str_state = 'PENDING';"

# 3. 手動觸發一次邏輯備份
docker exec opencue-db pg_dump -U cuebot -d cuebot -Fc -f /tmp/backup.dump
docker cp opencue-db:/tmp/backup.dump ./cuebot-manual.dump
```

#### 情境 D：排查健康檢查（Healthcheck）失敗原因
當容器狀態卡在 `unhealthy` 時，可進容器直接執行測試指令查看具體 Exit Code 與輸出：
```bash
# 手動觸發 Cuebot 的健康探針指令
docker exec opencue-cuebot curl -sf http://localhost:8080/
echo "Exit Code: $?"  # 22 代表端點未啟用但 Spring 活著（正常），其他代碼代表服務異常
```

### 3. 各容器實用維運指令小抄（Cheat Sheet）

| 容器名稱 | 常用診斷指令 | 預期輸出 / 診斷目的 |
|---|---|---|
| `opencue-db` | `docker exec opencue-db pg_isready -U cuebot` | `accepting connections`（確認 DB 正常服務中） |
| `opencue-flyway` | `docker logs opencue-flyway` | 檢視最後一行是否為 `Successfully applied X migrations` |
| `opencue-cuebot` | `docker logs --tail 100 opencue-cuebot \| grep WARN` | 檢查是否有 `RqdClientException` 或找不到主機的警訊 |
| `opencue-rest-gateway` | `docker logs opencue-rest-gateway` | 查看是否有來自 CueWeb 的 JWT 驗證失敗或連線逾時日誌 |
| `opencue-cueweb` | `docker logs opencue-cueweb` | 查看 Next.js 伺服器端是否有抓取 job 或代理呼叫失敗的錯誤 |
