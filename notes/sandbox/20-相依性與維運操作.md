# 20 — Job 相依性與維運操作

相依性是 OpenCue 的核心排程功能，也是實際 pipeline 一定會用到的
（先算 cache 再算圖、先算圖再合成、多個 AOV 都完成才做合併）。
先前完全沒測過，這一份補上。

測試環境：Windows 節點刻意鎖定，讓所有工作落在 Linux 容器節點 `render02`，
因為 `load_test_jobs.py` 的相依情境用的是 `/bin/sleep`。

---

## 一、相依的狀態機

frame 多了一個狀態 **`DEPEND`**，意思是「被相依關係鎖住，還不能排隊」。

```
DEPEND  ──(相依滿足)──>  WAITING  ──(派工)──>  RUNNING  ──>  SUCCEEDED / DEAD
```

**`DEPEND` 與 `WAITING` 的差別很重要**：

| 狀態 | 意思 | 派工器會看它嗎 |
|---|---|---|
| `WAITING` | 可以跑，在排隊等資源 | **會** |
| `DEPEND` | 被相依鎖住，還輪不到它 | **不會** |

排查時若看到 frame 卡在 `DEPEND`，要找的是**它在等誰**，
而不是去查 tag、facility 或節點資源 —— 那是 `WAITING` 卡住才要查的方向。

## 二、相依的 job 會先暫停送出

`load_test_jobs.py` 的相依情境**一律 paused 送出**，送完才解除暫停。

原因是：若送出後立刻開始派工，第一個 job 可能在後續的相依關係接好之前
就跑完了，導致相依關係建立在一個已結束的 job 上。

送出後的初始狀態（chain 4 層）：

```
 job                  | 暫停 | frame 狀態
----------------------+------+-----------
 chain_00             | t    | WAITING     <- 沒有相依，可以跑
 chain_01             | t    | DEPEND      <- 等 00
 chain_02             | t    | DEPEND      <- 等 01
 chain_03             | t    | DEPEND      <- 等 02
```

**實務上自己寫投遞腳本時也應該這樣做** ——
先全部 paused 送出，接好相依，最後統一 resume。

## 三、實測三種拓樸

### 1. Chain（線性相依）

`load_test_jobs.py chain --chain-length 4`

每個 job 相依於前一個。解除暫停後的取樣：

| 取樣 | chain_00 | chain_01 | chain_02 | chain_03 |
|---|---|---|---|---|
| 1 | WAITING | DEPEND | DEPEND | DEPEND |
| **2** | **SUCCEEDED** | **RUNNING** | **DEPEND** | **DEPEND** |
| 3 | SUCCEEDED | SUCCEEDED | SUCCEEDED | SUCCEEDED |

**取樣 2 是關鍵證據**：00 完成後 01 才開始，而 02、03 仍被鎖著 ——
不是一次全部解開。

### 2. Diamond（A 擋 B 與 C，B+C 再擋 D）

`load_test_jobs.py diamond`

| 取樣 | a | b | c | d |
|---|---|---|---|---|
| 1 | WAITING | DEPEND | DEPEND | DEPEND |
| **2** | **SUCCEEDED** | **RUNNING** | **RUNNING** | **DEPEND** |
| 3 | SUCCEEDED | SUCCEEDED | SUCCEEDED | SUCCEEDED |

**取樣 2 證明兩件事**：

1. `a` 完成後 **b 和 c 同時並行啟動**（不是依序）
2. `d` 仍是 `DEPEND` —— 要等 b 和 c **都**完成

### 3. Fan-in（3 個 blocker 擋 1 個 dependent）

`load_test_jobs.py fan-in --blockers 3`

| 取樣 | blocker_00 | blocker_01 | blocker_02 | dependent |
|---|---|---|---|---|
| 1 | WAITING | WAITING | WAITING | DEPEND |
| **3** | **SUCCEEDED** | **SUCCEEDED** | **RUNNING** | **DEPEND** |
| 4 | SUCCEEDED | SUCCEEDED | SUCCEEDED | **SUCCEEDED** |

**取樣 3 是關鍵**：兩個 blocker 完成了**還不夠**，
`dependent` 一直等到第三個也完成才解開。

### 相依滿足的條件

`opencue.properties:417`：

```properties
depend.satisfy_only_on_frame_success=true
```

**預設只有 frame 成功才算滿足相依。** 也就是說：

- blocker 的 frame 變成 `DEAD` → dependent **永遠不會解開**
- 這是合理的預設（失敗的 cache 不該拿去算圖），
  但**排查時要知道**：dependent 卡在 `DEPEND` 不一定是相依壞了，
  可能是上游有 frame 死掉

## 四、維運操作：`cueadmin -kill` 與 `cueman -term` 不同

清理殘留 job 時發現的：

```bash
cueadmin -force -kill <job>     # job 仍留在清單上
cueman  -force -term <job>      # job 確實消失
```

推測 `-kill` 只砍執行中的 frame，`-term` 才是終止整個 job。
**清理 job 清單要用 `cueman -term`。**

常用的維運指令對照：

| 目的 | 指令 |
|---|---|
| 暫停 / 恢復 job | `cueman -pause <job>` / `cueman -resume <job>` |
| 終止 job（從清單移除） | `cueman -force -term <job>` |
| 重試失敗的 frame | `cueman -force -retry <job>` |
| 放棄（eat）frame，不再重試 | `cueman -force -eat <job>` |
| 砍執行中的 frame | `cueman -force -kill <job>` |
| 列出 frame 與狀態 | `cueman -lf <job>` |
| 鎖定 / 解鎖節點 | `cueadmin -force -lock -host <名稱>` / `-unlock` |
| 移動節點的 allocation | `cueadmin -force -move <alloc> -host <名稱>` |

`cueman` 的操作大多支援 `-layer` 與 `-range` 縮小範圍，例如只重試某幾格：

```bash
cueman -force -retry <job> -range 10-20
```

## 五、對正式 pipeline 的意義

| 情境 | 對應的拓樸 |
|---|---|
| 先產 cache／USD，再算圖 | **chain** |
| 一份場景同時算多個 AOV 或多台相機 | **diamond** 的中段（一個 blocker、多個並行） |
| 多個部分都算完才做合併／轉檔 | **fan-in** |
| 一個前置作業解開大量後續工作 | **fan-out** |

**Houdini 的兩階段派工（產 USD → husk 算圖）就是 chain**，
見 `12` 的說明。

### 排查相依問題的順序

1. frame 是 `DEPEND` 還是 `WAITING`？
   - `DEPEND` → 找它在等誰，檢查上游是否有 `DEAD`
   - `WAITING` → 查 tag、facility、節點資源（見 `17` 場景 1、20）
2. 上游 job 是否有 frame 變成 `DEAD`？
   - 預設 `depend.satisfy_only_on_frame_success=true`，
     上游有死掉的 frame 就永遠不會解開
3. 相依關係是否真的建立了？
   - 送出時若沒有 paused，可能接線前上游就跑完了
