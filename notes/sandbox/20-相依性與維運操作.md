# 20 — Job 相依性與維運操作

相依性是 OpenCue 的核心排程功能，也是實際 pipeline 一定會用到的
（先算 cache 再算圖、先算圖再合成、多個 AOV 都完成才做合併）。
先前完全沒測過，這一份補上。

測試環境：Windows 節點刻意鎖定，讓所有工作落在 Linux 容器節點 `render02`，
因為 `load_test_jobs.py` 的相依情境用的是 `/bin/sleep`。

---

## 一、相依的狀態機

frame 多了一個狀態 **`DEPEND`**，意思是「被相依關係鎖住，還不能排隊」。

```
DEPEND  ──(相依滿足)──>  WAITING  ──(派工)──>  RUNNING  ──>  SUCCEEDED / DEAD
```

**`DEPEND` 與 `WAITING` 的差別很重要**：

| 狀態 | 意思 | 派工器會看它嗎 |
|---|---|---|
| `WAITING` | 可以跑，在排隊等資源 | **會** |
| `DEPEND` | 被相依鎖住，還輪不到它 | **不會** |

排查時若看到 frame 卡在 `DEPEND`，要找的是**它在等誰**，
而不是去查 tag、facility 或節點資源 —— 那是 `WAITING` 卡住才要查的方向。

## 二、相依的 job 會先暫停送出

`load_test_jobs.py` 的相依情境**一律 paused 送出**，送完才解除暫停。

原因是：若送出後立刻開始派工，第一個 job 可能在後續的相依關係接好之前
就跑完了，導致相依關係建立在一個已結束的 job 上。

送出後的初始狀態（chain 4 層）：

```
 job                  | 暫停 | frame 狀態
----------------------+------+-----------
 chain_00             | t    | WAITING     <- 沒有相依，可以跑
 chain_01             | t    | DEPEND      <- 等 00
 chain_02             | t    | DEPEND      <- 等 01
 chain_03             | t    | DEPEND      <- 等 02
```

**實務上自己寫投遞腳本時也應該這樣做** ——
先全部 paused 送出，接好相依，最後統一 resume。

## 三、實測三種拓樸

### 1. Chain（線性相依）

`load_test_jobs.py chain --chain-length 4`

每個 job 相依於前一個。解除暫停後的取樣：

| 取樣 | chain_00 | chain_01 | chain_02 | chain_03 |
|---|---|---|---|---|
| 1 | WAITING | DEPEND | DEPEND | DEPEND |
| **2** | **SUCCEEDED** | **RUNNING** | **DEPEND** | **DEPEND** |
| 3 | SUCCEEDED | SUCCEEDED | SUCCEEDED | SUCCEEDED |

**取樣 2 是關鍵證據**：00 完成後 01 才開始，而 02、03 仍被鎖著 ——
不是一次全部解開。

### 2. Diamond（A 擋 B 與 C，B+C 再擋 D）

`load_test_jobs.py diamond`

| 取樣 | a | b | c | d |
|---|---|---|---|---|
| 1 | WAITING | DEPEND | DEPEND | DEPEND |
| **2** | **SUCCEEDED** | **RUNNING** | **RUNNING** | **DEPEND** |
| 3 | SUCCEEDED | SUCCEEDED | SUCCEEDED | SUCCEEDED |

**取樣 2 證明兩件事**：

1. `a` 完成後 **b 和 c 同時並行啟動**（不是依序）
2. `d` 仍是 `DEPEND` —— 要等 b 和 c **都**完成

### 3. Fan-in（3 個 blocker 擋 1 個 dependent）

`load_test_jobs.py fan-in --blockers 3`

| 取樣 | blocker_00 | blocker_01 | blocker_02 | dependent |
|---|---|---|---|---|
| 1 | WAITING | WAITING | WAITING | DEPEND |
| **3** | **SUCCEEDED** | **SUCCEEDED** | **RUNNING** | **DEPEND** |
| 4 | SUCCEEDED | SUCCEEDED | SUCCEEDED | **SUCCEEDED** |

**取樣 3 是關鍵**：兩個 blocker 完成了**還不夠**，
`dependent` 一直等到第三個也完成才解開。

### 相依滿足的條件

`opencue.properties:417`：

```properties
depend.satisfy_only_on_frame_success=true
```

**預設只有 frame 成功才算滿足相依。** 也就是說：

- blocker 的 frame 變成 `DEAD` → dependent **永遠不會解開**
- 這是合理的預設（失敗的 cache 不該拿去算圖），
  但**排查時要知道**：dependent 卡在 `DEPEND` 不一定是相依壞了，
  可能是上游有 frame 死掉

## 四、維運操作：`cueadmin -kill` 與 `cueman -term` 不同

清理殘留 job 時發現的：

```bash
cueadmin -force -kill <job>     # job 仍留在清單上
cueman  -force -term <job>      # job 確實消失
```

推測 `-kill` 只砍執行中的 frame，`-term` 才是終止整個 job。
**清理 job 清單要用 `cueman -term`。**

常用的維運指令對照：

| 目的 | 指令 |
|---|---|
| 暫停 / 恢復 job | `cueman -pause <job>` / `cueman -resume <job>` |
| 終止 job（從清單移除） | `cueman -force -term <job>` |
| 重試失敗的 frame | `cueman -force -retry <job>` |
| 放棄（eat）frame，不再重試 | `cueman -force -eat <job>` |
| 砍執行中的 frame | `cueman -force -kill <job>` |
| 列出 frame 與狀態 | `cueman -lf <job>` |
| 鎖定 / 解鎖節點 | `cueadmin -force -lock -host <名稱>` / `-unlock` |
| 移動節點的 allocation | `cueadmin -force -move <alloc> -host <名稱>` |

`cueman` 的操作大多支援 `-layer` 與 `-range` 縮小範圍，例如只重試某幾格：

```bash
cueman -force -retry <job> -range 10-20
```

### show 投過 job 之後就刪不掉，只能停用

清理測試用的 show 時發現的（實測）：

```
deleteShow("inita")
→ DataIntegrityViolationException: DELETE FROM folder WHERE pk_show=?
```

job 的歷史紀錄還參照著 show 的 folder，所以**只要投過 job，show 就刪不掉**。
正確做法是停用：

```python
show = opencue.api.findShow("inita")
for sub in show.getSubscriptions():   # 先收回 subscription，避免繼續被派工
    sub.delete()
show.setActive(False)                 # 從 active show 清單中消失
```

另外注意 `opencue.api.deleteShow()` 的參數**是 show 名稱**，文件寫 `show_id`，
但內部是拿它去 `findShow()` 用名稱查詢，傳 id 會回 `EntityNotFoundException`。

因此**建立 show 前先想好命名**，測試用的 show 會一直留在 DB 裡。

## 五、對正式 pipeline 的意義

| 情境 | 對應的拓樸 |
|---|---|
| 先產 cache／USD，再算圖 | **chain** |
| 一份場景同時算多個 AOV 或多台相機 | **diamond** 的中段（一個 blocker、多個並行） |
| 多個部分都算完才做合併／轉檔 | **fan-in** |
| 一個前置作業解開大量後續工作 | **fan-out** |

**Houdini 的兩階段派工（產 USD → husk 算圖）就是 chain**，
見 [`12`](12-真實DCC算圖.md) 的說明。

### 排查相依問題的順序

1. frame 是 `DEPEND` 還是 `WAITING`？
   - `DEPEND` → 找它在等誰，檢查上游是否有 `DEAD`
   - `WAITING` → 查 tag、facility、節點資源（見 [`17` 場景 1](17-故障排查與常見疏失速查.md#場景-1job-卡在-pendingframe-全卡-waitinghost-顯示-up--open)、20）
2. 上游 job 是否有 frame 變成 `DEAD`？
   - 預設 `depend.satisfy_only_on_frame_success=true`，
     上游有死掉的 frame 就永遠不會解開
3. 相依關係是否真的建立了？
   - 送出時若沒有 paused，可能接線前上游就跑完了

# 實戰應用：Houdini 兩階段派工（hython 產 USD → husk 算圖）

這是 chain 相依在真實 pipeline 上的應用，也是 Houdini 大場景的實務做法。

```
階段 1   hython   建立場景並匯出 USD        （1 個 frame）
   │     depend_all（LayerOnLayer）
   ▼
階段 2   husk     直接算那個 USD            （N 個 frame，可平行）
```

**為什麼要拆兩階段**：husk 不需要開啟完整的 Houdini session，
直接讀 USD 算圖，啟動比 hython 快。場景越大、frame 越多，差距越明顯 ——
只需要開一次 Houdini 產出 USD，後面每一格都省下開場景的成本。

## 實作

### 新增的包裝腳本

`notes/deploy/node/husk-22.0.429.bat`，與其他包裝腳本同樣的設計：
固定路徑、指向本機安裝位置、找不到執行檔回傳 127、預留授權環境變數。

```bat
"%HB%\husk.exe" --make-output-path -f %CUE_IFRAME% -n 1 -o "%OUTPUT%" "%SCENE%"
```

`-f %CUE_IFRAME% -n 1` 表示「從這一格開始，算一格」，
frame 編號同樣來自 RQD 注入的環境變數。

### 階段 1 的腳本

`notes/sandbox/lab/stage1_export_usd.py`，用 LOP 建立場景後以 `usd_rop` 匯出。

**關鍵是 `trange=1` 與 `f1` / `f2`** —— 這樣 USD 內才會有整段的動畫取樣。
若用預設值只會輸出當前 frame 的靜態狀態，後面每一格算出來都一樣。

### 投遞腳本

`notes/sandbox/lab/submit_houdini_twostage.py`。相依只有一行：

```python
stage2.depend_all(stage1)      # LayerOnLayer
```

並且**先暫停送出**，確保相依接線完成後才開始派工。

## 實測結果

送出後的結構：

```
 layer       | frame            | 狀態
-------------+------------------+---------
 export_usd  | 0001-export_usd  | WAITING
 husk_render | 0001-husk_render | DEPEND
 husk_render | 0002-husk_render | DEPEND
 husk_render | 0003-husk_render | DEPEND
```

resume 之後的取樣：

| 取樣 | export_usd | husk/0001 | husk/0002 | husk/0003 |
|---|---|---|---|---|
| 2 | **RUNNING** | DEPEND | DEPEND | DEPEND |
| **3** | **SUCCEEDED** | **RUNNING** | **WAITING** | **WAITING** |
| 4 | SUCCEEDED | SUCCEEDED | SUCCEEDED | RUNNING |
| 5 | SUCCEEDED | SUCCEEDED | SUCCEEDED | SUCCEEDED |

**取樣 3 值得注意**：相依滿足後，husk 的 frame 從 `DEPEND` 轉成 `WAITING`
（開始排隊等資源），再依序轉 `RUNNING`。

**它們沒有同時全部啟動** —— 節點有 8 核、每格只要 1 核，理論上可以平行，
但實際是分批派發的。這是 Cuebot 每個排程週期派發數量的正常行為，
不是設定錯誤。規劃時不要假設「相依一解開所有 frame 就同時開跑」。

### 產出驗證

```
twostage.usda       105,498 bytes
twostage.0001.exr   202,525
twostage.0002.exr   434,158     <- 每格大小不同
twostage.0003.exr 1,064,070
```

**檔案大小不同代表動畫確實寫進 USD 了** ——
幾何隨 frame 移動，入鏡的內容不一樣。若三格大小完全相同，
就是 `trange` 沒設定、USD 只有靜態狀態。

frame log 確認包裝腳本正確接到 frame 編號：

```
[wrapper] husk 22.0.429 | frame 2 | scene C:/opencue/render/twostage.usda
exitStatus          0
```

## 延伸：正式環境可以再拆更細

本次階段 1 只有 1 個 frame。真實場景常見的變化：

| 變化 | 做法 |
|---|---|
| 逐格輸出 USD（每格一個檔） | 階段 1 也用多 frame，改 `depend_on(FrameByFrame)` 讓第 N 格對第 N 格 |
| 先跑模擬再產 USD | 三層 chain：模擬 → USD → husk |
| 算完再轉檔／產代理圖 | 第四層，`depend_all` 於 husk 層 |

`depend_on()` 支援的相依型態（`pyoutline/outline/depend.py:44-48`）：

| 型態 | 意義 |
|---|---|
| `LayerOnLayer` | 整層等整層（本次使用） |
| `FrameByFrame` | 第 N 格等第 N 格，可及早開始 |
| `PreviousFrame` | 等前一格，用於有時序相依的模擬 |
| `LayerOnAny` | 等該層任何一格完成即可 |
| `LayerOnSimFrame` | 模擬專用 |

**`FrameByFrame` 對長序列特別有價值** —— 不必等整層算完，
第 1 格的 USD 好了就能開始算第 1 格的圖，整體時間大幅縮短。
