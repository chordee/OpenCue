# 22 — 兩種部署路線：Portainer 與 docker compose

> **本篇是實測紀錄。** 正式部署的步驟整理在 [`notes/deploy/01-伺服器.md`](../deploy/01-伺服器.md)，
> 設定檔已從 `notes/sandbox/stack/` 搬到 [`notes/deploy/server/`](../deploy/server/)。

同一份 [`notes/deploy/server/opencue.portainer.yml`](../deploy/server/opencue.portainer.yml)，兩種部署方式都能用。
**部署人員依 IT 給的權限選擇其中一條**，不需要改任何 yml。

---

## 一、選擇路線

| 取得的權限 | 建議路線 |
|---|---|
| 只有 Portainer 帳號 | **A. Portainer** |
| 有 SSH，而且可以執行 `docker` | **B. docker compose**（最快） |
| 有 SSH，但 IT 不希望在共用主機上 build | **A**，image 在開發機上 build |

兩條路線的差別只在 **「image 從哪裡來」**：

```
A. Portainer         開發機 build   ──push──> registry ──pull──> 伺服器
                                             （自建或 GHCR）

B. docker compose    伺服器上 git clone ──build──> 直接啟動
                                        （不需要 registry）
```

| | A. Portainer | B. docker compose |
|---|---|---|
| 需要 registry | **要**（自建 `registry.portainer.yml` 或 GHCR） | 不用 |
| 需要 SSH / docker 權限 | 不用 | **要**（加入 docker 群組約等於 root） |
| 伺服器上會 build | 不會 | **會**：build cache 約 50 GB（見 [`15`](15-空間規劃.md)），build 時 CPU 會衝高 |
| 伺服器要能連外 | 只要連得到 registry | build 時要連 Maven / npm / PyPI |
| Portainer 能管理 | 完整 | 顯示「created outside of Portainer」，只能有限操作 |
| 站點差異（DNS 等） | 只能填環境變數；更多時要貼進編輯器 | 可以多疊一個 `site.yml` |

---

## 二、相關檔案

全部在 [`notes/deploy/server/`](../deploy/server/) 底下：

| 檔案 | 用途 | A | B |
|---|---|---|---|
| `opencue.portainer.yml` | **主檔**，兩條路線共用 | ✔ | ✔ |
| `env.example` | 環境變數範本，每一項都有說明 | ✔ | ✔ |
| `build.yml` | 疊在主檔上，加入 build 設定 | 在開發機用 | ✔ |
| `site.example.yml` | 站點專屬設定（DNS、多台 extra_hosts） | 需要時貼進編輯器 | 需要時疊上 |
| `init/` | 初始化容器的 Dockerfile 與腳本 | ✔ | ✔ |
| `registry.portainer.yml` | 自建 registry（用 GHCR 就不需要） | 視情況 | — |

## 三、路線 A：Portainer

### 1. 在開發機上 build 並推送

```bash
cd notes/deploy/server
cp env.example .env          # 把 OPENCUE_*_IMAGE 改成實際的 registry 位置

docker compose --env-file .env -f opencue.portainer.yml -f build.yml build
docker compose --env-file .env -f opencue.portainer.yml -f build.yml \
  push flyway cuebot rest-gateway cueweb init
```

**`push` 一定要列出服務名稱**，否則連 `postgres:15.1` 也會嘗試推到 registry。

`build.yml` 沿用主檔的 `OPENCUE_*_IMAGE` 當 image 名稱，所以 build 出來的 image
**直接帶著正確的 tag**，不需要另外 `docker tag`（[`14`](14-Registry流程.md) 裡手動 tag 的步驟可以省掉）。

### 2. 在 Portainer 建立 stack

- **Stacks → Add stack → Web editor**：貼上 `opencue.portainer.yml` 的內容
- **Environment variables**：逐項填入，或用「Load variables from .env file」上傳

**必填**的變數沒填，部署時會直接報錯並說明缺哪一個（yml 裡標 `:?` 的那幾項）：

```
required variable OPENCUE_FLYWAY_IMAGE is missing a value: 必須設定
```

其他都有預設值，不填也能起來。

### 實測結果

用 Portainer API `PUT /api/stacks/3` 把本機的 stack 換成新版 yml，
另外只加了三個環境變數（`OPENCUE_INIT_IMAGE`、`OPENCUE_INIT_SHOWS`、`OPENCUE_INIT_SERVICES`）：

```
opencue-db            Up (healthy)
opencue-flyway        Exited (0)
opencue-cuebot        Up (healthy)
opencue-rest-gateway  Up (healthy)
opencue-cueweb        Up (healthy)
opencue-init          Exited (0)      ← 初始化跑完後正常結束

建立 show initb
  建立 subscription local.general.initb（1000 核）
  建立 subscription local.desktop.initb（1000 核）
  建立 subscription cloud.general.initb（1000 核）
建立 service initsvc，tags=['general']
初始化完成
```

接著投遞一個 job 到 `initb`，指定 service `initsvc` → **SUCCEEDED**（在 Windows 節點上執行）。
`:?` 必填檢查、`:-` 預設值、巢狀的 `${A:-${B}}`，Portainer 都能正確解讀。

Portainer 的「Repository」模式（直接指向 Git repo）後來也實測了，見 [`23`](23-Portainer的Git模式.md)。

## 四、路線 B：docker compose

在伺服器上：

```bash
git clone https://github.com/chordee/OpenCue && cd OpenCue/notes/deploy/server
cp env.example .env          # 填密碼、路徑；image 名稱隨意取，例如 opencue/cuebot:local

docker compose --env-file .env -f opencue.portainer.yml -f build.yml up -d --build
```

需要站點專屬設定時：

```bash
cp site.example.yml site.yml   # 修改 DNS 或逐台 extra_hosts
docker compose --env-file .env -f opencue.portainer.yml -f build.yml -f site.yml up -d --build
```

升級：

```bash
git pull
docker compose --env-file .env -f opencue.portainer.yml -f build.yml up -d --build
```

### 路徑基準

多個 `-f` 疊加時，**相對路徑一律以第一個檔案所在目錄為基準**。
所以 `build.yml` 裡的 `context: ../../..` 指的是 repo 根目錄。
指令要在 [`notes/deploy/server/`](../deploy/server/) 目錄下執行，或第一個 `-f` 要指向 `opencue.portainer.yml`。

## 五、初始化容器 `init`

### 為什麼需要

新環境起來後，DB 只有 flyway 建立的預設資料（show `testing` 與預設 allocation）。
專案要用的 **show、subscription、service** 都要另外建立，以前要手動跑 Python。

`init` 和 `flyway` 一樣是**一次性容器**：等 Cuebot healthy 後執行，跑完就結束。

### 設定方式

全部透過環境變數，**不設就什麼都不做**：

| 變數 | 說明 | 預設 |
|---|---|---|
| `OPENCUE_INIT_SHOWS` | 逗號分隔的 show 名稱 | 空 |
| `OPENCUE_INIT_ALLOCS` | 新 show 要訂閱的 allocation | `local.general,local.desktop,cloud.general` |
| `OPENCUE_INIT_SUB_CORES` | 每個 subscription 的 size 與 burst（核心數） | `1000` |
| `OPENCUE_INIT_SERVICES` | service 定義，JSON 陣列 | 空 |

`OPENCUE_INIT_SERVICES` 的格式：

```json
[
  {"name": "houdini2204", "tags": ["houdini_22_0_429"], "min_cores": 1, "min_memory_gb": 4},
  {"name": "maya2027",    "tags": ["maya_2027"],        "min_memory_gb": 8},
  {"name": "nuke17",      "tags": ["nuke_17_0v1"],      "min_memory_gb": 4}
]
```

可省略的欄位：`min_cores`（1）、`max_cores`（0 = 不限）、`min_memory_gb`（4）、
`min_memory_increase_gb`（2）、`threadable`（false）。各欄位的意義見 [`21`](21-Service與資源模型.md)。

### 可重複執行

每次部署或更新 stack 都會再跑一次。**已存在的項目不會被修改**，
只會補上缺少的，避免蓋掉在 CueGUI / CueWeb 上手動做的調整：

```
== 第一次                                == 第二次
建立 show inita                          show inita 已存在
  建立 subscription local.general.inita    subscription local.general.inita 已存在
  建立 subscription cloud.general.inita    subscription cloud.general.inita 已存在
service houdini2204 已存在                service houdini2204 已存在
建立 service inittest                     service inittest 已存在
```

反過來說，**要修改既有的 service，不能靠改環境變數**，要到介面上改。

### 【重要發現】新 show 沒有 subscription 就永遠不會派工

實測中第一版的預設值只訂閱了 `local.general` 和 `cloud.general`。
投遞到新 show 的 job 就一直停在 **WAITING**，**沒有任何錯誤訊息**：

```
job:  facility=local, os=Windows, PENDING, 未暫停
layer: tags=general, 1 核, 1 GB
host: LAPTOP-ULJICLO8  tags 含 general, OS=Windows, 閒置 8 核, OPEN
      ↑ 全部條件都符合
```

原因是 **Windows 工作站被放在 `local.desktop` 這個 allocation**，
而新 show 沒有訂閱它。Cuebot 找工作時是從
「**這台 host 所屬 allocation 有訂閱的 show**」開始找
（`DispatchQuery.java` 的 `FIND_SHOWS`），沒訂閱就根本不會看到這個 show。

補上 `local.desktop` 的 subscription 後，**10 秒內**就 SUCCEEDED。

這也是為什麼預設值改成和 `testing` 相同的三個 allocation。
如果有自訂 allocation，記得加進 `OPENCUE_INIT_ALLOCS`。
排查方式見 [`17` 場景 22](17-故障排查與常見疏失速查.md#場景-22新建的-show-投遞的-job-永遠停在-waiting)。

### image 裡為什麼有一個「版本號替身」

repo 的 `.dockerignore` 排除了 `ci/`，但 `proto` 和 `pycue` 的打包設定要從
`../ci/generate_version_number.py` 讀版本號。
`init/Dockerfile` 在 build 時放一個只回傳版本號的替身檔（預設 `0.0.0`，
可用 `OPENCUE_VERSION` 覆寫），不影響功能。

## 六、主檔改了什麼：讓它「只填環境變數就能部署」

### 1. 必填與預設值

| 類型 | 變數 | 行為 |
|---|---|---|
| 必填（`:?`） | `POSTGRES_PASSWORD`、`JWT_SECRET`、`CUEWEB_NEXTAUTH_SECRET`、`CUE_FRAME_LOG_DIR`、五個 `OPENCUE_*_IMAGE` | 沒填就報錯，不會用弱密碼默默起來 |
| 有預設 | `POSTGRES_USER` / `POSTGRES_DB` = `cuebot`、兩個 port = `8443` / `3000` | |
| 有預設 | `FRAME_LOG_ROOT_WINDOWS` / `_LINUX` | 沒填就沿用 `CUE_FRAME_LOG_DIR` |
| 有預設 | `CUEWEB_LOG_ROOTS` = `/mnt/logs` | **以前沒設時等於不限制**，任何容器內檔案都讀得到（見 [`13`](13-CueWeb與RESTGateway.md)）。現在預設就是限縮的 |

### 2. 選用的掛載

`FRAME_LOG_MOUNT_SOURCE` / `RENDER_OUT_MOUNT_SOURCE` 沒設定時，
改掛一個空的 volume（`opencue-cueweb-empty`），CueWeb 照常啟動，只是看不到 log 或縮圖。

以前的寫法留空會直接部署失敗（已實測）：

```
invalid spec: ::ro: empty section between colons
```

### 3. 節點名稱解析：DNS 移出主檔

原本主檔裡有一段被註解掉的 `dns` / `dns_search`，要啟用就得改 yml。

一開始想改成 `dns_search: ${DNS_SEARCH:-}`，**實測發現這樣會出問題**：

```
# 不寫 dns_search                # 寫 dns_search: ${DNS_SEARCH:-}，且沒設定
nameserver 127.0.0.11            nameserver 127.0.0.11
options ndots:0                  search                ← 空的 search
                                 options ndots:0
```

空值會變成一行空的 `search`，Docker 把它當成「覆寫」，
**反而把容器從宿主繼承來的網域後綴清掉**。

所以最後的做法是：

- **主檔不寫 DNS**。容器會沿用宿主 `/etc/resolv.conf` 的 search 網域，
  宿主本身能解析 `RENDER01` 的話，Cuebot 容器內通常也能。這是最可能的情況。
- 宿主解析不到時，才用 `site.example.yml` 疊上 `dns` / `dns_search`。
- 單台測試用的 `extra_hosts` 保留，但沒設定時指向無害的 `opencue-placeholder → 127.0.0.1`。

**尚未實測**：在真正加入公司網域的 Linux 宿主上，容器是否確實繼承 search 網域。
這要到正式環境才能驗證，部署後用下列指令確認：

```bash
docker exec opencue-cuebot getent hosts RENDER01
```

## 八、把 image 放到 GHCR（取代自建 registry）

路線 A 的 registry 可以用 GitHub Container Registry（`ghcr.io`）取代：

- **公開的 package 任何人都能直接 pull，不需要登入**
- 要一致的是 **CPU 架構**（amd64 / arm64），不是 CPU 型號。
  Intel 與 AMD 都是 amd64。用 `docker buildx --platform linux/amd64,linux/arm64`
  可以一次推出兩種架構
- **由公開 repo 的 workflow 推送的 package，會自動繼承 repo 的公開可見性**（實測）。
  從本機用個人帳號推送的 package 則預設為 private，要到 package 設定頁手動改
- **image 裡不能有機密或站點資訊**。目前的設計符合：密碼與 secret 都在部署時用環境變數帶入。
  wrapper、公司路徑這類東西不要放進 image
- CueWeb 的 `NEXT_PUBLIC_*` 是 build 時寫死的。**目前決定採用不需要登入的版本**
  （`NEXT_PUBLIC_AUTH_PROVIDER` 留空）。其他人若要開啟登入功能，需要自己重新 build
  - 不需要登入代表**連得到 3000 port 的人都能操作**（kill / retry / pause job），不只是檢視
  - stack 裡的 `JWT_SECRET` 保護的是 CueWeb → REST Gateway 這段，與使用者登入無關
  - 要限制存取，靠防火牆只開放內網，或放在有認證的反向代理後面，image 不用改
- OpenCue 是 Apache 2.0，允許再散佈，image 內已附 LICENSE
- **前提是伺服器能連到 `ghcr.io`**，這要先問 IT

### GitHub Actions workflow

`.github/workflows/sandbox-images.yml`：

- **手動觸發**：GitHub → Actions → **Sandbox images** → Run workflow
- 直接用 `build.yml` build，與本機的結果一致
- 用內建的 `GITHUB_TOKEN` 推送，**不需要建立 PAT**
- 產出 `ghcr.io/<owner>/opencue/{cuebot,flyway,rest-gateway,cueweb,init}`，
  tag 為 `<版本>-<短 SHA>`（例如 `1.34.4-e79848a8`），另外標一個 `latest`
- 目前只 build **amd64**。arm64 要在 QEMU 模擬下編譯 cuebot，會非常慢；
  需要時改用 GitHub 的 arm64 runner 分開 build 再合併 manifest

fork 裡上游的 workflow 只在 `master`、`v*` tag 或 PR 時觸發，
這個分支的 push 不會啟動它們。

**tag 的來源**：`ci/generate_version_number.py` 在非 master 分支會輸出 `1.34.4-<SHA>`，
和 [`14`](14-Registry流程.md) 手動 build 時用的慣例相同。init image 裡的 pip 套件版本號要符合 PEP 440，
所以 workflow 另外換成 `1.34.4+<SHA>` 傳給 `OPENCUE_VERSION`（本機已模擬驗證）。

### 實測結果

第一次執行（commit `1d73523b`）約 **6.5 分鐘**，全部成功：

```
ghcr.io/chordee/opencue/cuebot:1.34.4-1d73523b
ghcr.io/chordee/opencue/flyway:1.34.4-1d73523b
ghcr.io/chordee/opencue/rest-gateway:1.34.4-1d73523b
ghcr.io/chordee/opencue/cueweb:1.34.4-1d73523b
ghcr.io/chordee/opencue/init:1.34.4-1d73523b
（另各有一個 :latest）
```

**不登入也能 pull**：用匿名 token 查詢五個 manifest 都回 200，
不需要到 package 設定頁手動改成 public。

```bash
# 匿名檢查的方式
t=$(curl -s "https://ghcr.io/token?scope=repository:chordee/opencue/cuebot:pull" \
    | sed -n 's/.*"token":"\([^"]*\)".*/\1/p')
curl -s -o /dev/null -w "%{http_code}\n" -H "Authorization: Bearer $t" \
  -H "Accept: application/vnd.oci.image.index.v1+json" \
  https://ghcr.io/v2/chordee/opencue/cuebot/manifests/1.34.4-1d73523b
```

### 在 Portainer 使用

環境變數只要把 image 改成 GHCR 的位置，**不需要自建 registry**：

```
OPENCUE_CUEBOT_IMAGE=ghcr.io/chordee/opencue/cuebot:1.34.4-1d73523b
OPENCUE_FLYWAY_IMAGE=ghcr.io/chordee/opencue/flyway:1.34.4-1d73523b
OPENCUE_REST_GATEWAY_IMAGE=ghcr.io/chordee/opencue/rest-gateway:1.34.4-1d73523b
OPENCUE_CUEWEB_IMAGE=ghcr.io/chordee/opencue/cueweb:1.34.4-1d73523b
OPENCUE_INIT_IMAGE=ghcr.io/chordee/opencue/init:1.34.4-1d73523b
```

正式環境請固定用帶 SHA 的 tag，不要用 `latest`（理由見 [`14`](14-Registry流程.md)）。

### 實測：本機 stack 換成 GHCR image

用 `PUT /api/stacks/3` 把五個 image 改成 GHCR 的位置（同時清掉 init 的測試變數）：

```
PUT 200   耗時 2024 秒（約 34 分鐘）

opencue-flyway        Exited (0)       ghcr.io/chordee/opencue/flyway:1.34.4-1d73523b
opencue-cuebot        Up (healthy)     ghcr.io/chordee/opencue/cuebot:1.34.4-1d73523b
opencue-rest-gateway  Up (healthy)     ghcr.io/chordee/opencue/rest-gateway:1.34.4-1d73523b
opencue-cueweb        Up (healthy)     ghcr.io/chordee/opencue/cueweb:1.34.4-1d73523b
opencue-init          Exited (0)       ghcr.io/chordee/opencue/init:1.34.4-1d73523b
兩個節點自動重新註冊，UP / OPEN
```

**時間幾乎都花在下載**。各 image 的大小：

| image | 大小 |
|---|---|
| cueweb | 2.52 GB |
| flyway | 2.15 GB |
| cuebot | 1.06 GB |
| init | 255 MB |
| rest-gateway | 156 MB |

觀察到的行為：

- **下載期間舊的容器持續運作**。Portainer 先把 image 全部拉完才替換容器，
  服務中斷只有最後替換的約 30 秒
- **API 呼叫會一直等到部署完成才回應**。從 Portainer 網頁操作時，頁面會轉很久；
  若 Portainer 前面有反向代理，可能會先逾時（部署本身仍會在背景完成）
- 第一次部署或 image 大改版時才會這麼久。之後的版本只下載有變動的 layer
