# 04 — 部署過程實錄

全程在 WSL2 Ubuntu 24.04 內操作，repo 位於 `/mnt/d/dev/OpenCue`。

## 步驟 1：建立必要目錄

```bash
mkdir -p /tmp/rqd/logs /tmp/rqd/shots /tmp/opencue ~/.opencue/sessions
```

## 步驟 2：Build image

```bash
cd /mnt/d/dev/OpenCue
docker compose build cuebot flyway rqd
```

結果：`rqd`、`flyway` 成功，**`cuebot` 失敗**。

### 坑 #1：CRLF 導致 cuebot build 失敗

第一次的錯誤訊息表層是一堆 `repo.spring.io` 的 HTTP 401：

```
Failed to get resource: GET. [HTTP HTTP/1.1 401 :
https://repo.spring.io/plugins-snapshot/...]
```

**這些是雜訊**，Gradle 有 fallback 到其他 repository，不是失敗原因。真正的原因在
log 更後面：

```
* What went wrong:
Execution failed for task ':spotlessJavaCheck'.
> The following files had format violations:
      src/main/java/com/imageworks/common/spring/remoting/CueServerInterceptor.java
          -package com.imageworks.common.spring.remoting;\r\n
```

**原因**：repo 是在 Windows 上 clone 的，git 全域設定 `core.autocrlf=true`，
所有 Java 原始碼被轉成 CRLF 換行。cuebot 的 Gradle build 有 `spotless` 格式檢查，
要求 LF，直接擋下。

repo 的 `.gitattributes` 只有一行 `*.sh text eol=lf`，**沒有涵蓋 Java 檔**，
所以擋不住這個問題。

**修法**（在 repo 內設定，不影響其他專案）：

```bash
git config core.autocrlf false
git rm --cached -r -q .
git reset --hard -q
```

驗證：

```bash
file cuebot/src/main/java/com/imageworks/common/spring/remoting/CueServerInterceptor.java
# 修正前：ASCII text, with CRLF line terminators
# 修正後：Java source, ASCII text
```

**對正式環境的意義**：Linux 宿主上 clone 不會有這問題，這純粹是 Windows 開發端的坑。
但如果團隊裡有人在 Windows 上改 cuebot 原始碼，就會一直踩到。
**這是可以回饋給上游的改進**：補一份完整的 `.gitattributes`。

修正後重 build，`cuebot` 成功。

### Build 結果

| Image | 大小 |
|---|---|
| `opencue-cuebot:latest` | 1.06 GB |
| `opencue-flyway:latest` | 2.15 GB |
| `opencue-rqd:latest` | 152 MB |

`flyway` image 有 2.15 GB（基底是 almalinux:9 加上 JDK），對一個「跑完就結束」的
one-shot 容器來說偏大，正式環境若在意 registry 空間可以考慮瘦身。

## 步驟 3：啟動核心服務

先確認 port 沒跟宿主上其他容器衝突：

```bash
docker ps --format "{{.Names}}\t{{.Ports}}" | grep -E "5432|8443|8444|3000|8448"
```

（本機這幾個 port 都空著。**正式宿主務必先做這個檢查**，因為上面還有別的服務。）

```bash
docker compose up -d
```

啟動順序符合預期，`depends_on` 的條件都有作用：

```
db Started → db Healthy → flyway Started → flyway Exited(0)
→ cuebot Started → cuebot Healthy → rqd Started
```

**`flyway` 顯示 Exited 是正常的**，它是 one-shot migration 容器。

結果：

```
NAME               STATUS                    PORTS
opencue-cuebot-1   Up (healthy)   0.0.0.0:8443->8443/tcp
opencue-db-1       Up (healthy)   0.0.0.0:5432->5432/tcp
opencue-rqd-1      Up             0.0.0.0:8444->8444/tcp
```

`docker compose logs rqd` 可看到 RQD 正在跟 cuebot 建立 gRPC(h2) 連線。

## 步驟 4：安裝 client 套件

### 坑 #2：Ubuntu 缺 `python3-venv`，且 sudo 需要密碼

```bash
python3 -m venv ~/opencue-venv
# → You may need to use sudo with that command. After installing the
#   python3-venv package, recreate your virtual environment.
```

Ubuntu 把 `venv` 的 `ensurepip` 拆成獨立套件 `python3-venv`。而且 Ubuntu 24.04 有
PEP 668 保護，不能直接 `pip install --user` 到系統 Python。

**繞過方式**（本機剛好有 `uv`，不需要 sudo）：

```bash
export PATH=$HOME/.local/bin:$PATH
uv venv ~/opencue-venv --seed --python 3.12
```

`--seed` 會一併裝進 pip。若正式環境沒有 uv，就得請 IT 裝 `python3-venv`。

**對正式環境的意義**：Linux 宿主上**不需要**裝 client 套件 —— client 是給 artist
的機器用的（cuegui / cuesubmit / cueadmin）。宿主只要跑 container 即可。
這裡裝 client 純粹是為了驗證 sandbox 通不通。

### 安裝

```bash
cd /mnt/d/dev/OpenCue
source ~/opencue-venv/bin/activate
./sandbox/install-client-sources.sh
```

這個腳本會依序裝：`proto/`、`pycue/`、`pyoutline/`、`cueadmin/`、`cueman/`、
`cuesubmit/`、`cuegui/`、`cuecmd/`、`cuenimby/`。

（腳本也會依 `VERSION.in` 的內容建一個 git tag，屬正常行為。）

## 步驟 5：驗證連線

```bash
source ~/opencue-venv/bin/activate
export CUEBOT_HOSTS=localhost
cueadmin -lh
```

第一次的結果：

```
Host                Cores  Mem     State  Alloc          Thread
fdc2:c6c:d60f:9::4  8.0    18.5G   UP     local.general  AUTO
```

**連線成功，但 host 名稱是一個 IPv6 位址** —— 這個異常後來證實是 frame 跑不動的元兇。

## 步驟 6：投 job 驗證完整流程

```bash
python sandbox/load_test_jobs.py simple -n 2 --sleep-seconds 1-2 --unique
```

送出成功，但 frame 全部卡在 RUNNING：執行 `/bin/sleep 1` 卻跑超過一分鐘、
記憶體 0K、`/tmp/rqd/logs` 是空的、容器內也查不到任何子行程
（`/proc` 裡只有 `/app/openrqd` 本身）。

### 坑 #3：RQD 回報 IPv6 位址，Cuebot 無法回連

排查過程：

1. RQD 的 log 只有 `Sending host report`，**完全沒有任何 frame 執行紀錄**
   → 推斷 RQD 根本沒收到 RunFrame。
2. 查 Cuebot 的 log，找到關鍵 WARN：

```
Launch of frame 0003-test_layer on fdc2:c6c:d60f:9::4 failed and the frame's state
could not be confirmed (RqdClientException: failed to obtain status for frame ...).
Keeping the booking to avoid double-booking; the orphaned-proc reaper will reclaim it
```

3. 從 cuebot 容器內實測連線，直接證實：

```
rqd:8444（service 名稱）             → OK
fdc2:c6c:d60f:9::4:8444（RQD 回報的） → Connection refused
```

**根因**：compose 設 `OPENRQD__MACHINE__USE_IP_AS_HOSTNAME=true`，RQD 挑了一個
**IPv6** 位址回報給 Cuebot，但 openrqd 的 gRPC server 只聽 IPv4。
於是「RQD → Cuebot」通（host report 正常送達），「Cuebot → RQD」不通
（派 frame 時回連必定失敗）。

這種單向不通很容易誤判成「RQD 沒連上」，但實際上 host 在 `cueadmin -lh` 裡
看起來完全正常、狀態 UP。**判斷依據要看 Cuebot 的 WARN，不是看 host 列表。**

修法：用 `docker-compose.override.yml` 覆寫（不動上游檔案）

```yaml
services:
  rqd:
    environment:
      - OPENRQD__GRPC__CUEBOT_ENDPOINTS=cuebot:8443
      - OPENRQD__MACHINE__USE_IP_AS_HOSTNAME=false
    hostname: rqd
```

改完後 host 以 `rqd` 名稱註冊，Cuebot 可經 Docker 內建 DNS 正常回連。

**附帶災情**：卡住的 booking 會累積，最後觸發
`trigger__verify_host_resources()` 的 `unable to allocate additional memory`；
而且殘留的 proc 記錄會讓 `cueadmin -delete-host` 因外鍵約束失敗。
sandbox 直接 `docker compose down -v` 重置最快。

### 坑 #4：RQD 建立使用者失敗（uid 衝突）

修好 #3 後，frame 終於會被執行並回報狀態，但 exit status 是 `299`
（`cuebot/src/main/java/com/imageworks/spcue/dispatcher/Dispatcher.java:68`
→ `EXIT_STATUS_FRAME_CLEARED`）。

Cuebot log 給出明確原因：

```
ABORTED: Not launching, user chordee(1000:0) could not be created.
× Failed to create user chordee: useradd: UID 1000 is not unique
```

**根因**（`rust/crates/rqd/src/frame/manager.rs:84-96`）：
只要 RunFrame 帶著 uid，RQD 就**無條件**呼叫 `create_user_if_unexisting`，
跟 `runner.run_as_user` 設定**無關**（該值預設 false，本例也沒開）。

而 `create_user_if_unexisting`（`rust/crates/rqd/src/system/linux.rs:921`）的邏輯是：

1. 先用**名稱**查，查到就直接回傳其 uid
2. 查不到才 `useradd --uid <uid>`

投 job 者 `chordee` 的 uid 是 1000，而 rqd 容器裡 uid 1000 已被 `rqd` 使用者佔用
→ `useradd` 失敗 → frame 被 abort。

繞過方式：利用「先用名稱查」這個邏輯，在 RQD 啟動前先用一個沒被佔用的 uid
把同名使用者建好：

```yaml
services:
  rqd:
    entrypoint:
      - /bin/sh
      - -c
      - 'id -u chordee >/dev/null 2>&1 || useradd --uid 2000 --gid 1000 -M chordee; exec /app/openrqd'
```

### 驗證結果

```
    str_name     | str_state | int_exit_status
-----------------+-----------+-----------------
 0001-test_layer | SUCCEEDED |               0
 0002-test_layer | SUCCEEDED |               0
 0003-test_layer | SUCCEEDED |               0
（兩個 job 共 6 個 frame 全部 SUCCEEDED）
```

**Sandbox 完整流程打通**：投 job → Cuebot 排程 → 派給 RQD → RQD 執行 → 寫 log →

## 附帶解答：frame log 的實際路徑結構

這項先前列為「待驗證、不預設答案」，現在有實測答案。

`CUE_FRAME_LOG_DIR=/tmp/rqd/logs` 是**根目錄**，實際展開成：

```
/tmp/rqd/logs/<show>/<shot>/logs/<job 名稱>--<job id>/<job 名稱>.<frame 名稱>.rqlog
```

log 檔開頭有完整的 JobSpec：

```
command      /bin/sleep 2
uid          2000
gid          20
log_path     /tmp/rqd/logs/testing/testshot/logs/.../....rqlog
render_host  rqd
```

**對 Windows render node 的意義**：這個路徑由 Cuebot 設定的根目錄展開，
但實際建立目錄、寫檔的是 **RQD**。所以根目錄必須是**每一台 render node 都
寫得到的同一個位置**。Linux 宿主上的 `/tmp/rqd/logs` 對 Windows 節點毫無意義，
正式環境必須改成所有節點都存取得到的共享儲存路徑。**frame log 這一項要用 UNC 正斜線**（因為 CueWeb 在 Linux 容器裡也要讀它），其他路徑可用磁碟機代號 —— 見 [`11` 第 2 點](11-正式部署風險與待辦.md#2-網路磁碟機代號可用但有一個例外)。
